# 原因調査（トラブルシュート）レシピ

Sherpa 管理のベーススキル（自作）。型は「症状語だけで検索を乱発せず具体語を特定する→設定ファイル・
ログ相当の原本を読取ツールで精読する→仮説と裏付けを分ける→関連部品を関係グラフで補う」（複数ファイルの
突き合わせなど定型外の作業だけ Python を使う）。

## 1. 最初に開くもの（当たりの付け方）

1. 症状語（落ちる/止まる/エラー/停止 等）だけで検索を乱発しない。まず症状に関係する**部品名・
   ジョブ名・設定キー名**など具体語を `ripgrep_search(query=...)` で特定する（原因調査のこのスキルの
   文脈では症状語での検索自体は許される。名前が定まらない段階は `es_search(query=...)` で自然文のまま
   探してよい）。
2. 部品名・ジョブ名が判明したら `graph_neighbors(name=...)` で関連部品（呼び出し元・参照先・関連文書）
   を辿り、疑わしい依存関係を広げる。

## 2. 中身の確認（読取ツールが第一）

トラブルシュートの核心は**原本を実際に精読すること**。検索でヒットした断片だけで仮説を確定しない。

設定ファイル・ジョブ定義・ソースコードなど、テキスト/コード系の原本は `read_doc(doc_id=...,
start_line=...)`（通読）か `file_head(doc_id=...)`（先頭だけの軽い確認）で直接読む（Python を書かない）。
Excel の設定シート・パラメータ一覧などは `xlsx_sheets(doc_id=...)` でシートを確認してから
`xlsx_range(doc_id=..., sheet=..., range=...)` で該当範囲を読む（investigate-spec スキルの Excel 節も
参照）。

### 定型外のとき（複数ファイルを突き合わせる）

複数の設定ファイルの同じキーの値を突き合わせる（設定の食い違いが原因の場合に有効）ような、読取ツールを
候補数ぶん呼ぶより Python で一括して開いたほうが速い作業は定型外——原本を直接開いてよい（読取専用）。

```python
# 複数ファイルの同じキーの値を突き合わせる例（設定の食い違いが原因の場合に有効）。
values = {}
for p in candidate_paths:
    with open(p, encoding="utf-8", errors="replace") as f:
        for line in f:
            if "TARGET_KEY" in line:
                values[str(p)] = line.strip()
for k, v in values.items():
    print(k, "->", v)
```

## 3. 完了条件と中断

- 症状を説明できる具体的な記述（設定値の食い違い・欠落・想定と異なる分岐条件など）を原本の中に
  1箇所以上見つけ、根拠のファイル・行を示せたら仮説として提示してよい。
- 複数の仮説が立った場合は、裏付けが強いもの（原本に明記された矛盾）を優先し、弱い仮説（状況証拠のみ）は
  「推定」と明示して併記する。
- 3〜4箇所の原本を精読しても矛盾・欠落が見つからないときは、探した範囲を書いたうえで
  「原因は資料からは特定できない（要確認）」と正直に答える（無理に断定しない）。
- 関連部品を「すべて」洗い出すよう求められた場合は、上の「1箇所以上見つけたら提示してよい」は適用しない
  ——対象範囲（graph_neighbors の経路・該当フォルダ）を辿り切ってから答える（検索3回・根拠1件では終えない）。
  `graph_neighbors` の結果に `truncated:true` が付いたら近傍は部分集合（`count` が総数・続きは取れない）
  ＝その範囲を未確認として明示し「すべて」と書かない。
- **中断**（利用者停止・通信エラー・既存の反復／情報量予算への到達）のときは、確認済みの仮説・
  未確認の範囲・中断理由を分けて書き、部分結果を断定的な原因と言い切らない。

## 4. 回答の形

- **仮説と裏付けを分けて書く**（「◯◯が原因と考えられる（根拠: パス・行番号にこの記述がある）」の形）。
  裏付けの無い仮説は「推定」と明示する。
- 確定した事実（原本に明記された設定値・矛盾）と推定（状況証拠からの推測）を混同しない。
- 関連部品の広がりを示す場合は `graph_neighbors` で確認した経路（辺ごとの種類と向き・from→to。本文では「A が B を呼び出している」のように平易語で示し内部のエッジ名は出さない）を
  根拠として添える。
- 本文の中に出典の一覧は書かない。回答の最後に『参照した資料:』の行を置き、実際に開いて根拠にした
  資料を1行1件、資料フォルダからの相対パスで列挙する。
