## 0. 設計の芯（タスク起点）

**「見せたいデータ」ではなく「ユーザのやりたいこと」を起点に、次の一手が自明な画面にする。**

1. ユーザの**やりたいことが入口**（データを陳列しない）。
2. **次の一手が迷わない**（ボタンは動詞ラベル＝意図が一目／アイコン単独にしない）。
3. **"するべきこと"まで示す**（情報提供で終わらない。例: 「今すぐ直す6件／確認7件」）。
4. **専門用語ゼロ**（内部の仕組み語は平文に翻訳＝§6 グロッサリ）。
5. **1画面1主タスク**（ごちゃ混ぜない。でも空っぽで意図不明にもしない）。
6. 迷うなら**「黙っていても正しいことが起きる」**（既定＝登録済みの範囲全体・即反映・確信度で並ぶ）。

> アンチパターン（M7 初版の反省）: 抽出ノードの素のテーブル＝"開発者が見せたいもの"。
> ユーザは「**何を直せばいい？安全？**」を知りたいのであって、ノード一覧が欲しいのではない。

---

## 1. やりたいこと → 画面が返す「答え＋次の一手」

| ユーザのやりたいこと | 画面が即返す**答え** | **するべきこと**（次の一手） |
|---|---|---|
| 変更の影響を知りたい | 「消費税率を変えると13件に影響。**今すぐ直す6／確認7／影響なし確認済3**」 | 要確認を1件ずつ判断・要望どおりのリストをExcelで持ち帰る |
| 障害の原因を知りたい | 原因候補（確度順）＋確認手順 | 候補を確認・該当ソースへ・影響範囲へジャンプ |
| 仕様を知りたい | 該当箇所の抜粋＋**出典** | 原本をひらく |
| どの資料が使えるか確認したい | ✓使えます／⏳処理中／⚠失敗（理由） | **失敗をやり直す**・資料を追加 |
| 自分の資料をチェックさせたい（Phase） | 規約・仕様との食い違い一覧 | 指摘を採否・レポート出力 |

## 2. 操作ストーリー（ユーザージャーニー）

> 設計は**この流れから逆算**する。画面は流れの各ステップで"次の一手"を1つだけ強く出す。

### 2.1 影響を把握して改修計画にする（UC-1・看板）
状況: 「来期から消費税率を変更。何を直す？漏れたら事故。」
1. チャットで「**消費税率を変えたい。影響は？**」（版＝最新を会話ヘッダで確認）。
2. 会話に**答えカード**: 見出し「消費税率(10%)を変えると **13件**に影響。**今すぐ直す6／要確認7／影響なし確認済3**」＋種別内訳。**末尾に必ず出典**（リンク→原本DL・§4）。
3. 実作業は2系統:
   - **確実6件**＝直すと確定 → 改修対象。
   - **要確認7件**＝判断が要る → 1件ずつ「**なぜ影響と見たか**（経路＋根拠の該当文）」を見て**該当/非該当を判断**（会話で triage）。
4. 1件深掘り: 「見積機能はなぜ？」→経路（消費税率←税計算ルール←見積機能）＋根拠「設計書§4『請求額は消費税率で算出』」＋**原本DL**。ユーザ「税抜のみ＝非該当」と外す。
5. 仕上げ: **改修対象リストをExcelで持ち帰る**。
   - **リストは固定フォーマットにしない**。ユーザが会話で要望を伝え、それを反映して出す（Agentic に組み立て）。
     例:「確実な6件だけ。担当チーム列を足して、経路は省いて、ファイル名を付けて」→その通りのリスト。
   - 既定の列はあるが**会話で増減・並べ替え・粒度変更できる**。

### 2.2 取り込まれたか確認・失敗を直す（検索ファースト・2TB規模）
状況: 「渡した設計書が検索に出ない。入ってる？」/ 管理「失敗してない？」
> 資料は**2TB超**＝全部ツリー表示しても探せない。**検索とフィルタが主**、ツリーは副。
1. 画面を開くと最初に出るのは**全ツリーではなく**「最近の取り込み」＋クイックフィルタ「**⚠失敗 N**」「⏳処理中 N」。
2. **検索ボックス**で資料名（「請求機能」）。フィルタ（種類／状態／更新日／版）。
3. ヒット行の状態: ✓使えます ／ ⏳処理中 ／ ⚠**失敗（理由: 開けませんでした＝破損の可能性）**。
4. 失敗なら **[やり直す]**（理由が出ているので原因も分かる）。
5. **原本DL**。フォルダで辿りたい人はツリーも併用。

### 2.3 障害の原因を探す（UC-3）
1. チャットで症状「夜間バッチ NIGHTLY が ABEND。原因候補は？」。
2. 会話に**原因候補カード**（確度順）: 各候補に なぜ（近傍/類似障害）・**確認手順**（運用手順より）・**出典**（原本DL）。
3. 候補の関連ソースへ、または「これを起点に影響範囲」へジャンプ（会話文脈を継ぐ）。

### 2.4 仕様を問い合わせる（qa）
1. チャットで「消費税の端数処理の仕様は？」。
2. 会話に**該当箇所の抜粋**＋**出典**（仕様書・リンク→原本DL）。確証が無ければ「該当見つからず」と正直に返す。

## 3. 画面（タスク起点で3つ）

### 3.1 チャット（主入口・3ペイン）＝利用者の中心
全レンズ（影響/トラブル/仕様問い合わせ）は**会話で依頼→会話に答えが返る**（12-ユースケース.md）。
- **左**: 会話履歴／新規作成（DB永続・`session_id` で継続）。検索。
- **中央**: 会話＋**答えカード**（§3.2）。**回答末尾に必ず出典フッター**（§4）。
- **右**: 「いま何を調べたか」＝経路・参照ファイル（任意・折りたたみ可）。
- **入力**: 自由文＋範囲セレクタ（取込ディレクトリ＝world・複数あるとき）＋（Phase）添付。**ユーザはレンズを選ばない** — システムが意図を判定して振り分ける。

### 3.2 影響の答えカード（中央に出る・全画面ビューは"奥"）
- **見出し＝答え＋するべきこと**: 「N件に影響。今すぐ直すA／要確認B／影響なし確認済C」。
- 種別内訳（機能/帳票/画面/ソース/バッチ…）。
- **要確認は会話で1件ずつ判断**（経路＋根拠の該当文を見せる）。
- **Excel出力は会話の要望を反映**（固定でない・§2.1-5）。
- 「全画面の結果ビュー（表・ソート/フィルタ）」は**深掘り用の二階**（既定では出さない）。

### 3.3 取り込み（検索ファーストのエクスプローラ）
- 既定: **最近の取り込み＋クイック状態フィルタ**（⚠失敗／⏳処理中）。**検索＋フィルタが主**。
- **フォルダツリーは副導線**だが役割は重要＝**構造の把握**（フォルダ＝意味のある区分）＋**参照範囲(scope)の選択**（取込ディレクトリ＝world／その中の活動・工程をドリルダウン/複数選択）。範囲＝フォルダ prefix は [03-鏡モデル.md](03-鏡モデル.md) 準拠。
- 状態は**3つだけ**: **✓使えます**（検索・影響分析の対象）／**⏳処理中**／**⚠失敗（理由＋[やり直す]）**。
- **原本DL**。共有KBは**読取専用バナー**（追加・削除は管理者）。
- フォルダ名は平文（「設計書・仕様書／プログラム（COBOL等）／自分のアップロード」）。`uploads/md/src` は出さない。
- **A17 抽出プレビュー**（名寄せ・関係・廃止ラベルの監査）は**管理者の「詳細」に分離**＝通常画面には出さない（精度監査用の二階）。

### 3.4 確認カードが出る場面（ask_user）
会話の途中で AI が選択肢つきの「確認カード」を出すことがある。出る場面は次の2つだけ：
- **① AI が判断に迷ったとき**：調査の範囲・対象・目的が複数候補に割れ、確認しないと答えが大きく変わる場合（例: 影響分析で起点や影響先が複数に割れる／確実な波及が0件で要確認だけになった、等）。
- **② 依頼で確認を求めたとき**：依頼文に「確認してから進めて」（同義: 確認してから／聞いてから進めて）と書くと、AI は調査より先に必ず確認カードを出す（利用者が発動を制御できる確実な手段）。

回答済みの確認カードは**履歴に残る**（選んだ内容が反映された状態で表示される）。

## 4. 出典・ダウンロード（全レンズ共通の絶対ルール）

- すべての回答の**末尾に「出典」セクションを必ず付ける**。
- 各出典は**リンク**。クリックで **原本（`uploads/` の元 Office ファイル／`src/` の原文）をDL**。
  **MD化版は出さない**（ユーザが欲しいのは元資料）。
- **出典の無い断定をしない**。根拠ゼロなら「確証なし」と明示する。

---

## 5. 文章・ボタンの作法

- **ボタン＝動詞**（「やり直す」「Excelで出す」「原本をひらく」「資料を追加」）。アイコン単独禁止。
- **状態＝結果の言葉**（「使えます」）。工程名（MD化／静的解析／公開／索引）を画面に出さない。
- 数値は tabular-nums。確信度は **●確実 / ○要確認** の符号で一貫。
- エラーは**平文で理由＋次の一手**（「開けませんでした → [やり直す]」）。

---

## 6. 専門用語 → 画面の言葉（グロッサリ）

| 内部（仕組み）の語 | 画面に出す言葉 |
|---|---|
| 決定的MD化／静的解析(S)／LLM意味層(L)／ES索引／Neo4j投入／publish | すべて **「✓ 使えます」**（検索・影響分析の対象）に集約 |
| doctype | **種類**（PDF / Word / COBOL …） |
| ソース枝／Office枝／トラック | 出さない（状態1列に集約） |
| 名寄せ／canonical_id／REALIZES／抽出プレビュー(A17) | 通常は**隠す**。管理者の「詳細」でのみ表示（精度監査） |
| Parameter/DataItem/Copybook 等のラベル | 種別の平易語（パラメータ／項目／…）。生ラベルは出さない |
| 起点エンティティ解決／逆向き推移たどり | 「影響を調べています」 |

## 7. ビルド順序（改訂・タスク起点）

> 最新の実装進捗は開発リポジトリ内部の資料で追跡している。以下は初期の縦切り順。

- **済（"奥の部品"として活用）**: 抽出・統合グラフ・3レンズ（impact/troubleshoot/qa）・結果ビュー部品・抽出プレビューAPI（M0–M7）。
- **M8 会話の器**: `conversations`/`messages`（DB永続・trace・lens・analysis_id・Codex `session_id`）＋**薄い `/chat` ルーティング**（意図判定→既存 `run_*`。後で Codex/ローカルLLM 判定に差し替え可能な seam）。
- **M9 チャットUI**: 3ペイン・**答えカード**（答え先頭＋するべきこと）・**出典フッター（原本DL）**・要確認の会話 triage・要望反映の Excel。
- **M10 取り込みエクスプローラ**: 検索ファースト・状態3つ・**やり直す**・原本DL／A17 を管理者「詳細」へ。
- **Phase**: UC-2 添付チェック（一時embed）・UC-4 スコープ参照・共有・管理ダッシュボード。

> M7 のフォーム画面は**この設計に置き換える**（結果ビュー/preview API は"奥"として再利用）。
