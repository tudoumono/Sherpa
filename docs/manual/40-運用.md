# 40. 運用・デプロイ

## 構成の原則：ストアだけコンテナ、アプリ核はホスト直

- **コンテナ化するのは DB（PostgreSQL / Neo4j / Elasticsearch）だけ**。
- **アプリ核（FastAPI・取り込み・静的解析・Office→MD 変換・AI 実行）は恒久的にホスト直**で動かします。
- 理由: Codex の安全実行（ホストネイティブのサンドボックス）と、取り込みの WSL→`/mnt` アクセスを壊さないため。コンテナに包むと内側サンドボックスと衝突します。

詳細は [08-実行権限と隔離.md](../08-実行権限と隔離.md)。

## 起動・停止・状態（一枚看板）

配布された Sherpa は、初回も日常も同じ1コマンドで動かせます。`./scripts/start.sh`（＝`make start`）が
前提チェック → 依存の用意 → ストア起動 → アプリ起動までを一括で行い、アプリは**バックグラウンド**で常駐します。

| 用途 | コマンド | 説明 |
|------|----------|------|
| **起動（初回＝日常）** | `make start` | 依存（変更時のみ）→ ストア起動＋healthy 待ち → アプリをバックグラウンド起動。二重起動しない |
| 停止 | `make stop` | アプリ＋Caddy＋ストアを**全部停止**（`KEEP_STORES=1 make stop` でストアは残す） |
| 再起動 | `make restart` | アプリ（＋Caddy）を停止して起動し直す（ストアは維持） |
| 状態 | `make status` | ストア3つ・アプリ（healthz）・LAN/Caddy・URL を1画面で表示 |

- 起動後は `http://127.0.0.1:8000/ui/chat.html` を開きます。
- アプリはバックグラウンドで動くため、**ターミナルを閉じてもアプリは止まりません**（`setsid` で新セッション化）。
  ログは `data/run/api.log`、PID は `data/run/api.pid` です。`tail -f data/run/api.log` で追えます。
- 依存関係（`requirements.txt`）は**ハッシュを記録して変更時だけ再インストール**します（毎回 pip install しません）。
- モード: 既定は `serve`（本番相当・fixtures 非参照）。開発用に fixtures を使うなら `make start MODE=dev`
  （＝`./scripts/start.sh dev`）。ログを前面で直視したい開発時は `make serve` / `make api` の前面起動も従来どおり使えます。
- **動作確認済みは Linux/WSL2 です。macOS は best-effort**（`setsid` が無い環境では `nohup` にフォールバックします）。

常駐運用（サーバに置いて自動起動・監視付き）では、下の systemd 手順を使ってください。

### 画像内の文字を読む（OCR）

資料に貼り込まれた画面キャプチャや図の中の文字も検索できるようにする機能です。**既定で有効**で、
`make start` がストアと一緒に読み取りワーカーを起動します。

初回だけモデルの取得が要ります（約134MB）。

```bash
make ocr-models     # モデルを data/ocr-models へ取得
make start          # ワーカーも一緒に起動する
make status         # ワーカーが動いているか確認
```

前提が足りないときは**起動を止めずに理由を表示して先へ進みます**（モデル未取得・資料フォルダ未登録など）。
OCR は検索や取り込みの必須部品ではなく、無ければ「画像内の文字が読まれない」だけだからです。

| | |
|---|---|
| 読み取りの担当 | 別コンテナのワーカー（依存がアプリ本体と両立しないため分離） |
| ワーカーに渡すもの | 資料フォルダとモデルは**読み取り専用**。書き込めるのは `data/observations` だけ |
| 外部との通信 | **遮断**（ローカル推論のみ・閉じたネットワークに置く） |
| 止めたいとき | `.env` に `SHERPA_OCR_ENABLED=0` |

閉域（インターネットに出られない）環境では、ネットに出られる端末で `make ocr-models` を実行し、
できた `data/ocr-models` フォルダを丸ごとコピーして同じ場所に置いてください。

**コードを更新したときは `make start`（または `make up`）を通してください。** ワーカーのイメージには
アプリのコードが焼き込まれるため、起動し直さないとワーカーだけ古いコードのまま動きます。
2回目以降のビルドは数秒です。

### 入れたての状態に戻す（`make nuke`）

試用で溜まったデータを全部消して、まっさらから試し直したいときに使います。**元に戻せません。**

```bash
make nuke          # 消す対象を一覧表示 → yes と入力すると実行
make nuke YES=1    # 確認を省略（スクリプトから呼ぶとき）
```

| | |
|---|---|
| **消えるもの** | アカウント・会話履歴・監査ログ・台帳（ストアのデータ）／MD化した派生物／OCR観測／個人領域（アップロードした個人ファイルと出力物）／ローカルKB・pid・ログ |
| **消えないもの** | **登録した資料フォルダの中身**／`.env`（接続先やAPIキー）／`fixtures/`／`data/eval-*`（評価資産） |

実行後は `make start` で起動し、**管理者アカウントの作り直しと資料フォルダの再登録**から始めます。

消す先は `.env` の `SHERPA_DERIVED_DIR` などの設定を見て決めます。`/srv/sherpa/derived` のように
リポジトリの外へ置いている場合も、その場所が対象になります（`data/derived` だけ消して「初期化した」と
誤解しないため）。実行前に**消す対象を一覧表示する**ので、目で確かめてから `yes` と入力してください。

念のため、次のいずれかに当てはまると実行せずに止まります。

- 消す先が**登録済みの資料フォルダ**そのもの、またはそれを含む場所
- 消す先がファイルシステムのルート・ホーム・リポジトリそのもの、または `/data` のような最上位直下

ストアが停止していると資料フォルダの照会ができないため、その旨を表示します（この場合は一覧を
自分の目で確認してください）。

### バックアップと復元（`make backup` / `make restore`）

更新の切替前や、大きな取り込み・設定変更の前に、データを1点まるごと退避します。
`make nuke` はバックアップ置き場（`data/backups`）を消さないので、初期化前に取っておけば戻せます。

```bash
make stop                                   # ストアを止める（動いていると取れません）
make backup                                 # → data/backups/<日時>/ に退避
make backup ARGS=--stop                     # 止めるところから自動で
make backup ARGS=--with-derived             # 派生物（MD化など・再取り込みで再生成できるもの）も含める
make backup ARGS=--dry-run                  # 何をどこへ取るかの計画だけ表示

make restore FROM=data/backups/<日時>        # 内容を表示 → yes で復元（YES=1 で確認省略）
make start
```

| | |
|---|---|
| **取るもの** | ストアのボリューム3つ（`sherpa-mvp_pg` / `_neo4j` / `_es`）＝アカウント・会話・監査ログ・台帳・グラフ・検索索引／個人領域（`SHERPA_USERS_DIR`）／`.env` のコピー／`MANIFEST`（版・日時・元パス・イメージID・各ファイルの sha256） |
| **取らないもの** | 資料フォルダの中身（読み取り専用の原本）／派生物（`--with-derived` で含める）／Docker イメージ |
| **前提** | **アプリとストアが停止中**（動作中のボリューム/個人領域を固めると不整合になり得るため、通常実行は拒否（終了コード 3）、`--stop` 付きなら自動停止＝`make stop` 相当でコンテナを**外す**（`docker stop` で残すのではなく down。残っていると次の `make restore` が「参照しているコンテナがあります」で止まる））。tar は手元の既知の Docker イメージ（`postgres:16` 優先）で実行するので閉域でも動きます |
| **置き場** | `SHERPA_BACKUP_DIR`（既定 `data/backups`）。`.env` の秘密を含むので `0700/0600` で作られます。長期保管は別ディスクへコピーしてください |

復元は次の順で進みます: 完成印と MANIFEST の sha256 を照合し、未登録ファイル/所定外の volume 名/tar 破損を拒否
（1つでも合わなければ何もせず止まる）→ アプリとストアの停止を確認 →
ボリュームを**消して作り直し**て展開 → 個人領域は今の内容を `<dir>.before-restore-<日時>` へ退避してから展開 →
`.env` は**上書きせず**差分のあるキー名だけを表示（秘密値は表示しない）。今の内容を残したいなら、復元の前にもう1つ
`make backup` を取ってください。sha256 は転送破損や MANIFEST を変えない単独改ざんの検出用で、署名ではありません。

**更新手順への組み込み**: `scripts/install_offline_kit.sh --target-dir …` で**更新**（`current` が既存の版を指している）
するとき、導入スクリプトは `current` を切り替える直前に自動で `backup.sh` を実行し、ログに置き場
（既定 `<target-dir の親>/backups/<日時>/`）を出します。**ストアが動いていると取らずに警告して続行**するので、
更新前に `make stop` してから導入を実行するのが安全な手順です（`SHERPA_BACKUP_BEFORE_SWITCH=0` で抑止）。
停止中にもかかわらず env/volume/image の不備でバックアップに失敗した場合は、版の確定と切替を中止します。
アプリを `--rollback-to` で旧版へ戻すときは、この時点のバックアップを `make restore` で戻せば DB も揃います。

## LAN 公開（同じネットワークの他端末から使う）

既定ではアプリは `127.0.0.1`（このマシンだけ）で待ち受けます。同じ LAN の別端末（同僚の PC・スマホ）
からも開きたい場合は **LAN 公開モード**で起動します。

```bash
LAN=1 make start           # その場限りで LAN 公開（0.0.0.0）
LAN=1 make start MODE=dev   # 動作確認用（fixtures 参照の開発モード）
```

LAN 公開が既定です（`SHERPA_LAN=1`）。このホストだけに閉じたいときは `.env` に **`SHERPA_LAN=0`** と書くか `LAN=0 make start` を使います
（コマンドラインの `LAN=` の方が優先）。

`LAN=1` はアプリを `0.0.0.0:<SHERPA_PORT>`（既定 8000）にバインドします。**平文 HTTP のままで
ログインして使えます**（閉域網の社内 LAN はこの形が標準）。さらに `caddy` コマンドと `deploy/Caddyfile` が
あれば **Caddy（HTTPS リバースプロキシ）も自動起動**します（`https://<host>/`）。HTTPS が要るのは
LAN を信用しない環境（他部署と共用・無線 LAN 等）だけで、閉域の社内 NW では必須ではありません。

### cookie の Secure 属性（HTTP と HTTPS の両方で動く理由）

セッション cookie の `Secure` 属性は、**そのログイン要求が HTTPS で来たときだけ**付きます
（2026-08-17 変更）。平文 HTTP で来たログインには付かないので、ブラウザは HTTP でも cookie を送り、
ログインできます。HTTPS（Caddy 経由）で来たログインには従来どおり付きます。

| 配備 | 起動 | cookie |
|------|------|--------|
| 閉域 LAN・平文 HTTP（標準） | `LAN=1 make start` | Secure なし＝HTTP でログイン可 |
| Caddy で HTTPS 終端（同一ホスト） | `LAN=1 make start`（Caddy 自動起動） | Secure あり |
| HTTPS 終端が別ホスト（アプリには http で届く） | `.env` に `SHERPA_COOKIE_SECURE=1` | Secure を強制 |

以前は「serve モードは常に Secure」だったため、平文 `http://<IP>` ではログインできず、回避が
「dev モードで起動」（fixtures 参照・本番相当ではない）しかありませんでした。いまは serve モードのまま
HTTP で公開できます。dev モードを LAN 公開のために使う必要はもうありません。

### WSL2 の2枚の壁

Windows 上の WSL2 で動かしている場合、LAN の他端末から届くまでに **2枚の壁**があります。
どちらか一方の方式を選びます（PowerShell は「管理者として実行」で開きます）。

**方式A: ミラーモードネットワーク（推奨・WSL 2.0 以降）**
WSL を Windows ホストと同じ IP に見せる方式。`C:\Users\<あなた>\.wslconfig` に次の2行を書き、
`wsl --shutdown` で WSL を再起動します。

```ini
[wsl2]
networkingMode=mirrored
```

これで Windows の LAN IP（`ipconfig` で確認）に対して、WSL 内の待受ポートへ直接届きます。

**方式B: ポートフォワード（netsh portproxy）**
従来の NAT モード向け。Windows 側のポートを WSL の IP に転送します（WSL の IP は再起動で変わることがあります）。

```powershell
# WSL の IP を確認（WSL 内: hostname -I）してから、Windows 側で転送を追加する
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=8000 connectaddress=<WSLのIP> connectport=8000
# 確認 / 削除
netsh interface portproxy show all
netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=8000
```

**両方式に共通: Windows ファイアウォールの受信許可**
LAN からの着信をファイアウォールで許可します（PowerShell・管理者）。

```powershell
New-NetFirewallRule -DisplayName "Sherpa 8000" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8000
# Caddy(HTTPS) 経由なら 443 も許可する
New-NetFirewallRule -DisplayName "Sherpa 443" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 443
```

> このリポジトリは Windows 側の設定を自動では変更しません（上のコマンドは手動で実行してください）。

### Caddy の導入

Caddy は 1 バイナリのリバースプロキシで、ローカル CA による HTTPS を自動化できます。

1. <https://caddyserver.com/> から `caddy` を導入します。
2. `cp deploy/Caddyfile.example deploy/Caddyfile` して、`<host>` を自分のホスト名か LAN の IP に書き換えます。`.env` で `SHERPA_PORT` を 8000 以外にしている場合は、`reverse_proxy 127.0.0.1:8000` の **8000 も同じ値に**書き換えてください（Caddyfile は .env を読みません）。
3. `LAN=1 make start`（`caddy` と `deploy/Caddyfile` があれば自動起動）。単体なら `caddy run --config deploy/Caddyfile`。

`deploy/Caddyfile.example` は `tls internal`（ローカル CA）で証明書を自動発行し、SSE（チャットのストリーミング）が
そのまま流れる設定です。クライアント端末では Caddy のローカル CA を信頼させる必要があります。443 バインドや CA 導入に
管理者権限が要る場合があります。

## 運用者向けの起動

| 用途 | コマンド | 説明 |
|------|----------|------|
| ストア起動 | `make up` | Postgres / Neo4j / Elasticsearch を docker で起動 |
| 初期化 | `make bootstrap` | `.env` 用意＋ローカル利用ディレクトリ作成＋ストア待ち |
| アプリ起動 | `make serve` | `scripts/run-api.sh serve` 経由。`.env` を読み、`SHERPA_ENV=production`・fixtures 無効を強制 |
| 本番点検 | `make prod-check` | `SHERPA_ENV_FILE` で指定した env の必須項目・依存関係を確認 |
| 全消去 | `make nuke` | ストアをボリュームごと削除 |

> ⚠ `make nuke` は保存済みデータを削除します。**会話履歴・ユーザー・取り込み済みデータも消える**ため、
> 実行前に管理者に確認してください。

> **本番⇄テストの分離**: 通常起動は fixtures（架空のテストデータ）を参照しません。`SHERPA_ENV=production` と fixtures 設定の同時指定は**設定ミスとして起動拒否**（fail-closed）。配布物（`make dist`）にも fixtures/tests は同梱されません。

`scripts/run-api.sh` は `SHERPA_ENV_FILE` があればその env ファイルを読みます。未指定時はリポジトリ直下の `.env` を読みます。
本番の systemd 起動では `/etc/sherpa/sherpa.env` を使う想定です。

## 本番展開の標準手順

アプリ本体は**版ごとのフォルダ**（`/opt/sherpa/releases/<版>`）に展開し、`/opt/sherpa/current` はその
フォルダを指す**リンク**として、リンクの張り替え一発で切り替えます（設計経緯:
開発時のレビューで決定）。設定は
`/etc/sherpa/sherpa.env`、データは `/srv/sherpa`（`current` の外）に分けます。**データを
`releases/<版>` の中に置かないでください**——リリース切替のたびに新しい版フォルダへ入れ替わるため、
中に置いたデータは切替直後に「消えた」ように見えます（`scripts/check-production.sh` がこの誤配置を
検出して起動前に失敗させます）。systemd 等は常に `/opt/sherpa/current` だけを参照するため、下記の
切替を行ってもユニット設定の変更は不要です。

**核心は次の3点**:
- **リンクの張り替えは全工程の一番最後**。取得・展開・依存導入・検証を新しい版フォルダに対して
  全部終わらせてから、最後の一歩として `current` を切り替えます。途中のどこかで失敗すれば
  `current` は元の版のまま無傷です（依存導入に失敗した「壊れた版」を指したまま systemd が
  再起動して起動不能になる、という事故を避けるため）。
- **`releases/<版>` は完成すれば immutable**（マーカーを消した後は書き換えない）。tar 展開は
  `releases/` 配下の一時名（staging）だけで行い、展開直後に**未完成マーカー**を付けたまま
  `releases/<版>` という最終パスへ据え付けます。**venv の作成・依存導入・最終検証はこの最終パスに
  対して行います**（venv は shebang・`pyvenv.cfg` に絶対パスを埋め込むため、作成後に場所を移すと
  壊れます）。全部成功して初めてマーカーを消し、その版を「完成版」として確定します。同じ版名が
  マーカー無しで既にある場合は**既存版の中身の置換はせず、その場でエラーにします**（稼働中の版を
  誤って壊すレースが構造的に起こらないようにするため）。マーカー付きで残っている場合は前回の
  失敗導入の残骸なので、同じ版名で安全に作り直せます。
- **プリフライトはデータ配置のその場検査が主・`check-production.sh` は補助**。データ系パス
  （`SHERPA_USERS_DIR`/`SHERPA_DERIVED_DIR`）が `current`/`releases` の配下を指していないかは、
  **旧スクリプトに頼らないその場の `realpath` 検査**で確認します（初回導入・更新・旧方式からの
  初回移行のいずれでも、切替の前に必ず実行します）。`current` が既にある場合は、加えて
  `/opt/sherpa/current/scripts/check-production.sh`（=今動いている版のスクリプト）も補助的に
  実行します（新しい版自身のパスから直接実行すると、判定基準が新しい版の実体パスにすり替わって
  `current` 相対の誤配置を見逃すため、必ず `current` 経由で呼びます）。

**同時に複数の導入作業をしない**でください（この手順自体には多重実行の排他機構がありません。
メンテナンス時間帯を確保し、単一のオペレータが1つずつ実行してください）。

まず展開先の変数を定義します（以下の手順はこの2行の変数を**この端末セッションを通して**参照します。
セッションを分けて作業する場合は、その都度この2行を先に実行し直してください）。

> **このページの標準手順では展開先は `/opt/sherpa/current` 固定です**。同梱の systemd ユニット
> （後述）が `WorkingDirectory`・`ExecStart` 等をこのパスで固定しているためで、変数はあくまで
> 手順内のコマンドを読みやすくするためのものです。別パスで運用したい場合は、systemd を使わない
> [offline-kit.md](offline-kit.md) のスクリプト経路（`--target-dir`）を使ってください
> （その場合もユニットファイルを自前で用意しない限り常駐化はできません）。

```bash
TARGET_DIR=/opt/sherpa/current   # 標準手順では固定（上の注意を参照）
RELEASES_DIR="$(dirname "$TARGET_DIR")/releases"
```

設定ファイルを用意します（**初回のみ**）。`.env.example`（開発・本番共通の唯一の例）は配布
tarball の中に入っているため、どこか作業用ディレクトリで一時展開して取り出してください。既に
`/etc/sherpa/sherpa.env` がある場合（＝更新、または旧方式からの移行で以前から使っていた設定が
ある場合）は**上書きしません**。

```bash
sudo install -d /etc/sherpa
if [ ! -e /etc/sherpa/sherpa.env ]; then
  sudo cp <一時展開した .env.example> /etc/sherpa/sherpa.env
  sudo editor /etc/sherpa/sherpa.env   # まず冒頭「0. 本番チェックリスト」節を設定する
else
  echo "/etc/sherpa/sherpa.env は既に存在するため上書きしません（前回の設定をそのまま使います）"
fi
```

**データ系パスのその場検査**（初回導入・更新・旧方式からの初回移行のいずれでも、切替の前に
必ず実行します。`$TARGET_DIR`/`$RELEASES_DIR` の実体がまだ無くても `realpath -m` は文字面の
正規化だけで判定できるため、`$TARGET_DIR` に置かれている（かもしれない古い版の）
`check-production.sh` の有無や中身に依存しません）:

```bash
( set -euo pipefail
  set -a
  . /etc/sherpa/sherpa.env
  set +a
  CURRENT_REAL="$(realpath -m "$TARGET_DIR")"
  RELEASES_REAL="$(realpath -m "$RELEASES_DIR")"
  for name in SHERPA_USERS_DIR SHERPA_DERIVED_DIR; do
    v="${!name:-}"
    if [ -z "$v" ]; then
      echo "エラー: $name が未設定です" >&2
      echo "  （未設定時の既定は data/users・data/derived のような相対パスで、systemd の" >&2
      echo "   WorkingDirectory=$TARGET_DIR を基準に解決されるため release の中を" >&2
      echo "   指してしまいます。/srv/sherpa/... のような固定の絶対パスを明示してください）" >&2
      exit 1
    fi
    case "$v" in
      /*) : ;;
      *)
        echo "エラー: $name が相対パスです（$v）" >&2
        echo "  （プロセスの作業ディレクトリ＝systemd の WorkingDirectory=$TARGET_DIR" >&2
        echo "   を基準に解決されるため release の中を指してしまいます。絶対パスにしてください）" >&2
        exit 1
        ;;
    esac
    v_real="$(realpath -m "$v")"
    case "$v_real" in
      "$CURRENT_REAL"|"$CURRENT_REAL"/*|"$RELEASES_REAL"|"$RELEASES_REAL"/*)
        echo "エラー: $name（$v）が $TARGET_DIR または $RELEASES_DIR の配下を" >&2
        echo "  指しています（release 切替のたびに新しい版フォルダへ入れ替わるため、データが" >&2
        echo "  見えなくなります）。/srv/sherpa/... のような current/releases の外の固定パスに" >&2
        echo "  変更してください。" >&2
        exit 1
        ;;
    esac
  done
  echo "OK: データ系パスの配置を確認しました（$TARGET_DIR / $RELEASES_DIR の配下ではありません）"
)
```

以降の手順は、`/etc/sherpa/sherpa.env` が既に用意されている（初回導入直後、または更新の場合は
前回のものがそのまま）という前提で進みます。

```bash
( set -euo pipefail   # 対話シェルでも1コマンドの失敗で確実に中断する（続行して事故らないため）

  # 取得は GitHub Release から（本番ホストでの `make dist` は使わない: リリースゲート
  # （release.yml のテスト成功が前提の release job）を経ていない、ローカル HEAD をそのまま
  # 配備できてしまうため。オフライン閉域環境は docs/manual/offline-kit.md の経路を使う）。
  VER="v0.1.0"   # GitHub の Releases ページで確認した、実際に使う版のタグに置き換える
  REPO="tudoumono/Sherpa"
  curl -fsSLO "https://github.com/$REPO/releases/download/$VER/sherpa-$VER.tar.gz"
  curl -fsSLO "https://github.com/$REPO/releases/download/$VER/sherpa-$VER.tar.gz.sha256"
  sha256sum -c "sherpa-$VER.tar.gz.sha256"

  # venv 作成・tar 展開・各種ファイル作成は、実行時の umask に依存してパーミッションが
  # 決まる。呼び出し環境の umask が厳しい設定（例 077）だと、release ルートだけ 755 に
  # 揃えても中身のファイル（.venv/bin/python 等）が別ユーザーから読めない/実行できない
  # ままになり得るため、この構築区間は umask 022（644/755 相当）を明示する
  # （ディレクトリ作成より前に設定すること）。
  umask 022

  RELEASE_DIR="$RELEASES_DIR/sherpa-$VER"
  sudo install -d "$RELEASES_DIR" /etc/sherpa /srv/sherpa
  # releases/ 自体が既存（旧い導入・別 umask での導入等）だった場合に備え、明示的に
  # 755 へ揃えておく（mkdir/install -d は既存ディレクトリのパーミッションを変えない）。
  sudo chmod 755 "$RELEASES_DIR"

  # releases/<版> の状態は3通り: (1) 無ければ新規に進める。(2) 未完成マーカー付きで存在＝
  # 前回の失敗導入の残骸＝安全に作り直せる。(3) マーカー無しで存在＝完成済みの版＝
  # 置換せず中止する（別の版名にするか、稼働中でないことを確認のうえ手動で削除してから
  # 実行し直す）。
  if [ -e "$RELEASE_DIR" ]; then
    if [ -e "$RELEASE_DIR/.sherpa-incomplete" ]; then
      echo "$RELEASE_DIR は前回の失敗導入の残骸です（未完成マーカーあり）。作り直します..." >&2
      sudo rm -rf "$RELEASE_DIR"
    else
      echo "エラー: $RELEASE_DIR が既に存在します（同じ版の再導入・上書きはしません）" >&2
      exit 1
    fi
  fi

  # 展開は staging（releases/ 配下の tar 展開専用の一時フォルダ）で行う。venv 等はここでは
  # 作らない（作成後に場所を移すと壊れるため、後で最終パスに対して作る）。
  STAGING_DIR="$(sudo mktemp -d "$RELEASES_DIR/.staging-sherpa-$VER-XXXXXX")"
  sudo tar -xzf "sherpa-$VER.tar.gz" -C "$STAGING_DIR" --strip-components=1
  sudo touch "$STAGING_DIR/.sherpa-incomplete"   # 未完成マーカー（mv で一緒に運ばれる）
  sudo mv -T "$STAGING_DIR" "$RELEASE_DIR"        # 最終絶対パスへ据え付け（まだ未完成のまま）

  # mktemp -d は umask に関わらず常に 0700 で作る。mv はディレクトリ自身のモードを変えない
  # ため、そのままだと別ユーザー（例 systemd の User=sherpa-api）が traverse できない
  # release になってしまう。据え付け直後に 755 へ戻す（中身の各ファイル/ディレクトリの
  # 権限は上で設定した umask 022 のもとで tar 展開されるため、release ルート自身のみでよい）。
  sudo chmod 755 "$RELEASE_DIR"

  # 依存導入・検証はここから、最終パス（$RELEASE_DIR）に対して行う。venv の shebang・
  # pyvenv.cfg の絶対パスは最初からこの最終パスで焼かれる（＝再度 mv しない）。
  # ここで失敗すれば current は既存の版のまま無傷（切替は全部成功した後、最後に一度だけ行う）。
  sudo python3 -m venv "$RELEASE_DIR/.venv"
  sudo env PYTHON_BIN="$RELEASE_DIR/.venv/bin/python" \
    "$RELEASE_DIR/.venv/bin/python" -m pip install -r "$RELEASE_DIR/requirements.txt" -c "$RELEASE_DIR/constraints.txt"
  sudo env PYTHON_BIN="$RELEASE_DIR/.venv/bin/python" \
    "$RELEASE_DIR/.venv/bin/python" -m pip check

  # サービスユーザーの用意と、そのユーザーで実際に venv が読めることの確認も、マーカーを
  # 消す（＝完成版として確定する）前にここで済ませる（「全部検証してから最後に切替」の
  # 原則に合わせる）。current 経由ではなく $RELEASE_DIR を直接指定する（current はまだ
  # 旧版のままか、初回導入では存在しないため）。
  sudo "$RELEASE_DIR/scripts/setup-runtime-users.sh"
  sudo -u sherpa-api "$RELEASE_DIR/.venv/bin/python" -c 'import fastapi'

  # 切替の前に、"今 current が指している" check-production.sh を補助的にプリフライトする
  # （データ系パスの配置そのものは、上で既に実行したその場検査が主。ここでの check-production.sh
  # は DB 疎通・admin 初期パスワード等、その場検査ではカバーしない項目の確認が目的）。
  # 新しい版自身のパスからではなく、必ず $TARGET_DIR 経由で実行する。$ROOT の解決が
  # current という symlink パスのまま行われるため、current 相対の誤配置検出が正しく効く
  # ——新版自身の絶対パスから実行すると $ROOT が新版の実パスにすり替わり、見逃す。
  # sudo は既定で環境変数をリセットするため、`VAR=val sudo cmd` ではなく
  # `sudo env VAR=val ... cmd` の形で明示的に渡す（PYTHON_BIN 無しだと system python3 を
  # 検査してしまい、健全な venv があっても「依存不足」と誤判定する）。
  if [ -e "$TARGET_DIR" ]; then
    sudo env SHERPA_ENV_FILE=/etc/sherpa/sherpa.env PYTHON_BIN="$TARGET_DIR/.venv/bin/python" \
      "$TARGET_DIR/scripts/check-production.sh"
  else
    echo "初回導入のため current 経由の補助チェックは対象がなく省略します（データ配置は上の" >&2
    echo "その場検査で既に確認済みです）。" >&2
  fi

  # ここまで全部成功して、初めてマーカーを消す（これが「完成版」を名乗る唯一の瞬間。
  # 以後 releases/<版> の中身は二度と書き換えない＝ immutable）。
  sudo rm -f "$RELEASE_DIR/.sherpa-incomplete"

  # current の切替はここから。一時リンクの準備（mktemp・ln -s）を先に済ませてから旧方式の
  # 退避を行う（退避を先にしてから一時リンクを準備する順序だと、mktemp/ln -s の失敗が
  # 「退避後・current 欠損」というタイミングで起きてしまう。準備を先に済ませておけば、
  # ここで失敗しても current にはまだ何も触れていない）。
  TMP_LINK_DIR="$(sudo mktemp -d "$(dirname "$TARGET_DIR")/.sherpa-current-tmp.XXXXXX")"
  sudo ln -s "$RELEASE_DIR" "$TMP_LINK_DIR/current"

  # 旧方式（symlink でない実フォルダ＝直接展開したもの）が残っている場合は、ここで退避する。
  LEGACY_BACKUP=""
  if [ -e "$TARGET_DIR" ] && [ ! -L "$TARGET_DIR" ]; then
    LEGACY_BACKUP="$TARGET_DIR.pre-versioned.$(date +%Y%m%d%H%M%S)"
    sudo mv "$TARGET_DIR" "$LEGACY_BACKUP"
  fi

  # 最後の一歩: 一発の rename で current を切り替える（ln -sfn は「削除→作成」の2手順で
  # 途中状態が生じうるため使わない）。ここが失敗した場合だけ退避を戻す。
  if sudo mv -T "$TMP_LINK_DIR/current" "$TARGET_DIR"; then
    sudo rmdir "$TMP_LINK_DIR" 2>/dev/null || true
  else
    echo "エラー: current の切替に失敗しました" >&2
    if [ -n "$LEGACY_BACKUP" ]; then
      sudo mv "$LEGACY_BACKUP" "$TARGET_DIR"
      echo "退避していた旧フォルダを $TARGET_DIR へ戻しました（無傷）" >&2
    fi
    exit 1
  fi
)
```

> 退避した旧フォルダ（`current.pre-versioned.<日時>`）はアプリ本体のみが対象の想定で、データは
> 既に `/srv/sherpa` 側にある前提です。ただし **バックアップの確認とデータ監査が終わるまでは
> 削除しないでください**。

（サービスユーザーの用意と `import fastapi` での実地確認は、上のブロック内でマーカー削除・
`current` 切替より前にもう済んでいます。）

認証は既定で有効です。初回の `admin` ログインには `SHERPA_ADMIN_PASSWORD` を使います。未設定の場合はローカル配布用の既定初期パスワード `Sherpa2026!` が使われます。
初回ログイン後は必ずパスワード変更が必要です。本番では初期パスワードのまま運用しないでください。
ログイン後、ユーザー管理画面で通常ユーザーや追加管理者を作成します。

`.venv` は版フォルダごと（`releases/<版>/.venv`）に作られます。systemd の
`PYTHON_BIN=/opt/sherpa/current/.venv/bin/python` は `current` 経由でそのまま参照できます
（`current` はリンクなので実体は `releases/<版>/.venv` を指します）。

**ロールバック**は旧版フォルダが `releases/` に残っているため、リンクを戻すだけです（再展開・
再インストール不要）。手順は [41-運用Runbook.md](41-運用Runbook.md) の「S7. デプロイ（更新）に失敗した」を
参照してください。

常駐起動する場合は同梱の unit 例を使います。**`enable --now` は既に稼働中のユニットを
再起動しません**（更新のたびに `enable --now` だけで済ませると、新しい版に切り替えたのに
プロセスは古い版のまま動き続けてしまいます）。初回導入・更新のどちらでも同じ手順で済むよう、
`enable` と明示的な `restart` を分けます。

```bash
sudo cp /opt/sherpa/current/deploy/systemd/sherpa-api.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable sherpa-api.service
sudo systemctl restart sherpa-api.service    # 初回は起動、更新時は明示的な再起動になる
sudo systemctl status sherpa-api.service
curl -fsS http://127.0.0.1:8000/healthz
```

手動で確認する場合は次です。

```bash
SHERPA_ENV_FILE=/etc/sherpa/sherpa.env /opt/sherpa/current/scripts/run-api.sh serve
curl -fsS http://127.0.0.1:8000/healthz
```

## ディレクトリ（ローカル利用と本番）

| 項目 | ローカル利用 | 本番 |
|------|-----|------|
| アプリ本体 | clone したリポジトリ | `/opt/sherpa/current`（`/opt/sherpa/releases/<版>` への symlink。実体は版ごとに使い捨て） |
| 設定ファイル | `.env` | `/etc/sherpa/sherpa.env` |
| データ基点 | リポジトリ内 `./data` | `/srv/sherpa`（`current`/`releases` の外・版切替の影響を受けない） |
| 共有KB（参照元） | 登録フォルダ（例 `/mnt/c/...`） | 登録フォルダ |
| 派生（写しMD/RAG正本/中間の3層＝`md/`・`rag/`・`ir/`） | `data/derived/{world}` | `/srv/sherpa/.../derived`（`SHERPA_DERIVED_DIR`） |
| 個人領域（書込可） | `data/users/{user}/workspace` | `/srv/sherpa/users/...`（`SHERPA_USERS_DIR`） |
| 権限分離 | 単一ユーザー | `sherpa-ingest`/`sherpa-api`/`sherpa-agent`/`sherpa-workspace` ＋ systemd 硬化 |

`data/`（ローカル利用のランタイム）は Git 管理外で、**派生物は再生成可能**です。個人領域（`users/.../workspace`）だけは成果物なので、削除時は注意します。

個人領域の配下には、会話ごとに Codex とのやり取りを続けるためのセッションファイル（`.codex-sessions/{会話ID}`）も保存されます。保持期間はシステム全体設定 `codex_session_retention_days`（既定 0=無期限）で調整でき、期限切れ分は自動で掃除されます。

本番の「アプリ本体」は `releases/<版>` ごと丸ごと入れ替わる使い捨てディレクトリです。データ系
（`SHERPA_USERS_DIR`／`SHERPA_DERIVED_DIR` 等）を誤って `current`/`releases` の内側（例 `/opt/sherpa/current/data`）
に置くと、次のリリース切替で新しい版ディレクトリに置き換わった瞬間にデータが見えなくなります。
`scripts/check-production.sh` はこの誤配置を検出して起動前に失敗させます。

## 取り込みの運用

- 取り込みは画面から明示実行します（登録／[取り込み開始]／再取り込み）。**常時ファイル監視はしません**。定期的に変更を取り込みたい場合は任意のポーリング（`SHERPA_POLL_SECONDS>0`・既定OFF）を有効にします。
- 取り込み・削除・参照先変更のたびに、**孤児派生物は自動で掃除**されます（[30-しくみ](30-しくみ.md) の自己修復）。管理者が整合を手動で取る必要はありません。
- 万一サービス（ES/Neo4j）が一時的に落ちていた状態で削除しても、次回の取り込み・削除・起動時に取りこぼしが自動回収されます。

### パイロット期間の運用ガード

取り込みが動いている最中に対象フォルダのファイルが一瞬だけ変化する（保存し直し・一時ファイルの
生成など）と、ごく稀に取り込み結果と実際のファイルの中身がずれることがあります。パイロット評価
期間はこの影響を運用でゼロに近づけるため、次の4点を徹底してください（コード側の対応はまだ行って
おらず、当面は運用でカバーする方針です）。

1. **取り込み中は対象フォルダの編集を止める**: 「今すぐ更新」や再取り込みを実行している間は、
   対象の共有フォルダへの保存・削除・移動を控えてもらうよう、関係者へ事前に周知します。
2. **参照先の切り替えは稼働中に行わない**: 資料フォルダ管理画面の「参照先を変更」（登録済みの
   フォルダを別の場所に差し替える操作）は、利用者からの検索を止めたメンテナンス時間帯だけに
   限定します。稼働中の切り替えは行いません。
3. **評価の直前に「今すぐ更新」を実行する**: 評価に使うデータが最新かつ安定していることを、
   評価の直前に手動更新して確認してから進めます。
4. **取り込み時刻の記録を残す**: いつ取り込んだかは、資料フォルダ管理の取り込み状況（最終同期
   時刻）で確認できます。評価結果と突き合わせられるよう、実施記録に書き残しておきます。

## Linux サーバでのホスト（他 PC からのアクセス）

ここまでの手順・LAN 公開は Windows 上の WSL2 前提で書いていますが、Sherpa 本体は Linux ネイティブに
動くため（WSL 必須依存はありません）、**素の Linux サーバに常駐させて、他の PC からブラウザでアクセス
する構成も正式にサポート**します。以下は Ubuntu Server 24.04 を例にした一本道の手順です。

### 1. 前提

- Ubuntu Server 24.04（他の Linux ディストリビューションでも構成の考え方は同じです）。
- `sudo` が使えること。
- LAN 内へポート 443（HTTPS。Caddy を使わない場合は 80/8000 等）を開放できること。

### 2. 導入

`LAN=1 make start` は起動時点で `caddy` コマンドと `deploy/Caddyfile` が両方揃っていないと HTTPS
を起動しません（平文 HTTP 公開になります）。そのため **先に Caddy を導入してから** `LAN=1 make start`
を実行します。

```bash
git clone <URL> Sherpa
cd Sherpa
scripts/install-docker.sh   # Docker 未導入なら（Postgres/Neo4j/Elasticsearch 用）

# (1) 先に Caddy を導入する
sudo apt install caddy   # または https://caddyserver.com/ の手順
cp deploy/Caddyfile.example deploy/Caddyfile
# deploy/Caddyfile の <host> を実際のホスト名/IP に書き換える

# (2) その後にアプリを起動する（初回は .env の用意など前提チェックが案内される）
LAN=1 make start
```

`make start` の流れ（依存インストール→ストア起動→アプリ起動）は WSL でも Linux サーバでも同じです。
[完全オフライン（閉域）向け配布資材キット](offline-kit.md)に同梱の Caddy 資材を流用しても構いません。
既にアプリを起動した後から Caddy を導入した場合は、`LAN=1 make start` は「起動済み」を検知して
何もしないため、代わりに `make restart` で反映します。

### 3. `SHERPA_BROWSE_ROOTS` の設定（Linux サーバでは必須級）

フォルダ選択（取り込み登録画面のエクスプローラー）が辿れるルートは既定 `/mnt`（WSL の Windows ドライブ
自動マウント前提）です。**素の Linux サーバでは `/mnt` は通常空**なので、`.env`（または
`SHERPA_ENV_FILE` で指定した env）に資料フォルダの親ディレクトリを指定します。

```bash
SHERPA_BROWSE_ROOTS=/srv/sherpa-data
```

資料の置き方（Windows 共有をそのまま見せる／サーバへ同期コピーする）は次の節を参照してください。
この設定が無いまま起動すると、既定ルート（`/mnt`）が1つも存在しない場合に起動ログへ警告が出ます
（`SHERPA_BROWSE_ROOTS` を促す内容・起動は止めません）。

### 4. 資料フォルダの見せ方（Windows 共有のマウント／同期コピー）

業務文書が Windows のファイルサーバ（`\\fileserver\資料` のような共有）にある場合、Linux サーバから
それをどう見せるかは2通りあります。**登録の仕組み自体はどちらでも同じ**です（サーバ上のフォルダを
画面から選ぶだけ。Sherpa は登録フォルダを読み取り専用でしか扱いません）。

**方式A: SMB マウント（推奨・更新がそのまま反映される）**

Windows の「ネットワークドライブ割り当て（Z:）」の Linux 版です。共有がサーバ上のフォルダに見える
ようになるため、共有側の更新が変更チェック（「今すぐ更新」/ポーリング）でそのまま鏡に反映されます。
IT 部門には (1) 共有のパス、(2) サーバからの到達可否（同一 LAN・ポート445）、(3) **読み取り専用**の
接続アカウント、の3点を確認してください。

```bash
sudo apt install cifs-utils
sudo mkdir -p /srv/sherpa/mounts/shiryo

# 認証情報は root だけが読めるファイルに置く（fstab にパスワードを直書きしない）
sudo tee /etc/sherpa-smb-cred >/dev/null <<'EOF'
username=<読み取り専用アカウント>
password=<そのパスワード>
domain=<ドメイン名（あれば）>
EOF
sudo chmod 600 /etc/sherpa-smb-cred
```

`/etc/fstab` に1行追加します（`<起動ユーザー>` は Sherpa を動かす Linux ユーザー）:

```
//fileserver/資料 /srv/sherpa/mounts/shiryo cifs credentials=/etc/sherpa-smb-cred,ro,vers=3.1.1,iocharset=utf8,uid=<起動ユーザー>,gid=<起動ユーザー>,file_mode=0444,dir_mode=0555,_netdev,x-systemd.automount,nofail 0 0
```

```bash
sudo systemctl daemon-reload && sudo mount /srv/sherpa/mounts/shiryo
ls /srv/sherpa/mounts/shiryo    # 共有の中身が見えればOK
```

- `ro`＝マウント自体を読み取り専用に（登録フォルダ read-only の契約を OS 側でも担保）。
- `iocharset=utf8`＝日本語ファイル名対応。`vers=3.1.1` で繋がらない古いサーバは `3.0` を試す。
- `_netdev,x-systemd.automount,nofail`＝ネットワーク断後の自動再接続・起動時に共有が無くても OS 起動を
  ブロックしない。
- あとは `.env` に `SHERPA_BROWSE_ROOTS=/srv/sherpa/mounts` を設定し、画面から登録するだけです。
- **共有に一時的に到達できなくなっても、取り込み済みの鏡は消えません**（参照元不可は fail-closed 設計。
  画面には「参照元フォルダにアクセスできません」と出て、復旧すれば元通り。
  [41-運用Runbook](41-運用Runbook.md) のトリアージ参照）。

**方式B: 同期コピー（共有への常時接続が許可されない/遅すぎる場合の代替）**

サーバのローカルディスク（例 `/srv/sherpa-data/資料`）へ定期同期し、そのローカル側を登録します。
検索・取り込みはローカルディスク速度で安定しますが、**鏡の鮮度は同期間隔まで落ちます**（夜間同期なら
翌朝反映）。同期経路は環境に合わせて選びます（例: Windows 側タスクスケジューラの `robocopy /MIR` で
サーバ上の受け皿共有へ push、またはサーバ側で方式Aのマウントから `rsync` でローカルへ pull）。

**登録の単位 — マウントを並べた親を1回登録する**

**登録できる資料フォルダは全体で1本だけ**です（決定 2026-08-15・2本目は拒否され、入れ替えは
「削除してから登録」）。サブシステムごとに共有が分かれている場合は、マウントをサブシステム数ぶん張った
上で（例 `/srv/sherpa/mounts/販売管理`・`在庫管理`・`経理`）、**それらを並べた親（`/srv/sherpa/mounts`）を
1回登録**します。ファイルは動かさず、コード変更もありません。

- 質問は常に全サブシステム横断で検索でき、絞りたいときはチャットの範囲指定でフォルダを選ぶ
- 1つの共有だけ障害になると、親は生きているため該当部分木が「削除された」と誤認され**一時的に検索から
  消える**（共有復旧後の「更新」で自動的に戻る）。障害時の見え方は [41-運用Runbook](41-運用Runbook.md) を参照
- 見せる範囲を絞りたい共有は、親の下にマウントしなければ登録範囲に入らない

### 5. 他 PC からのアクセス

`https://<サーバ名または IP>` で開きます。WSL2 の「2枚の壁」（ミラーモード/ポートフォワード）は
Linux サーバには存在しません（Linux はホスト OS 自身が LAN に直接繋がっているため）。

- Caddy の既定設定（`tls internal`）はローカル CA による自己署名証明書のため、初回アクセス時に
  ブラウザで警告が出ます。組織の CA がある場合は Caddyfile 側で証明書を差し替え可能です。
- 平文 `http://<IP>:<PORT>` の直アクセスでも**ログインできます**（cookie の Secure は HTTPS で来た要求に
  だけ付く・2026-08-17 変更）。閉域の社内 NW では Caddy 無しの HTTP 公開が標準で、Caddy は LAN を
  信用しない環境の選択肢です（上の「cookie の Secure 属性」節を参照）。

### 6. ファイアウォール指針

外部（LAN）に許可するのは、**平文 HTTP で公開するなら `SHERPA_PORT`（既定 8000）**、Caddy で HTTPS 化
するなら **443（80 も使うなら合わせて）だけ**で、その場合はアプリのポートを外部から閉じます。

`LAN=1` はアプリ自体を `0.0.0.0:<SHERPA_PORT>` で待受します。閉域の社内 NW で平文 HTTP 公開する標準構成では
このポートをそのまま LAN に開けます。Caddy 経由に切り替えたら、**アプリのポートはファイアウォール（ufw 等）で
外部から閉じてください**（HTTPS 側だけを入口にする）。
DB/検索エンジンのポート（PostgreSQL 5432・Neo4j 7474/7687・Elasticsearch 9200）は `docker-compose.yml`
で `127.0.0.1` バインド済みのため、そもそも外部到達できません。

```bash
ss -tlnp | grep -E '5432|7474|7687|9200|:8000|:443'
# → 5432/7474/7687/9200 は 127.0.0.1:xxxx で待受していれば OK
# → 8000 は 0.0.0.0:8000 で listen するのが正常（アプリの仕様）＝ファイアウォールで遮断する
# → 443 は Caddy が 0.0.0.0:443（または該当 IP）で listen していれば OK
```

ufw を使う場合の例（既定で deny・許可したポートのみ通す）:

```bash
sudo ufw default deny incoming
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp    # 80 も使う場合（HTTP→HTTPS リダイレクト等）
sudo ufw enable
```

## 旧形式（.doc / .xls / .ppt）の変換 — Office 連携

古い Office 形式（.doc / .xls / .ppt）を読み取るには、新しい形式へ変換する「変換バックエンド」を選びます（システム管理画面の「旧形式の変換」）。選択肢は次の3つです。

| 選択肢 | 動く場所 | 特徴 |
|--------|----------|------|
| 使わない（既定） | — | 古い形式は読み取り対象にしません（挙動不変）。 |
| LibreOffice で変換 | WSL 内で完結 | 追加ソフト（LibreOffice）だけで動きます。図の配置がずれることがあります。 |
| Office 連携（office_com） | 同じ Windows の Office（既定）／別マシンのワーカー | 本物の Office で最も忠実に変換します。**同じ Windows に Office があれば設定不要**で使えます。 |

「Office 連携」は、`deploy/office-com-worker.ps1`（PowerShell スクリプト）で本物の Office を自動化して変換します。COM（Office 自動化）に触れるのはこのスクリプトだけで、WSL/Linux コアは Office を直接操作しません（INGEST-MD §5.6 の設計境界）。呼び出し形態は2つあります。

### (A) 同じ Windows の Office を直接使う（既定・設定不要）

WSL と同じ Windows に Office が入っていれば、**追加の設定は不要**です。WSL 連携（`/mnt/c/.../powershell.exe`）でスクリプトをそのつど 1 回だけ起動して変換します（常駐ワーカーも接続先 URL も共有トークンも要りません）。

- システム管理画面の「旧形式の変換」で「Office 連携」を選ぶだけで、同じ Windows の Office が使われます（画面には「このパソコンの Office を直接使用」と表示され、検出できた Office のバージョンも出ます）。
- WSL 連携で `powershell.exe` が見つからない環境（WSL でない・interop 無効）では自動的に「変換しない（未対応表示）」へ倒れます（fail-safe）。`powershell.exe` の場所を明示したい場合のみ `.env` で `SHERPA_POWERSHELL_BIN` を設定します（通常は不要）。
- 変換は 1 件ずつ直列で処理し、1 件が既定 60 秒（`SHERPA_LEGACY_TIMEOUT`）を超えたらそのスクリプトの子プロセスを停止します。マクロは強制無効・読み取り専用で開き、原本には一切書き込みません。⚠ PowerPoint の単一インスタンス性（下記）にも同じ配慮が効きます。

### (B) 別マシンの Office をワーカー経由で使う（`SHERPA_OFFICE_COM_URL` 設定時）

WSL のホストに Office が無い（別の Windows マシンの Office を使う）／WSL でない Linux から使う場合は、その Windows 側で常駐 HTTP ワーカーとしてスクリプトを起動し、`SHERPA_OFFICE_COM_URL` を設定して呼び出します（`SHERPA_OFFICE_COM_URL` を設定した時点で、同一マシンの直接呼び出しよりこちらが優先されます）。

#### ワーカーの手動起動（Windows 側の PowerShell）

```powershell
# 1) 共有シークレット（任意の長い秘密の文字列）を設定（WSL 側の SHERPA_OFFICE_COM_TOKEN と一致させる）
$env:SHERPA_OFFICE_COM_TOKEN = "<任意の長い秘密の文字列>"

# 2) ワーカーを起動（127.0.0.1 の 8091 で待ち受け・STA 推奨）
powershell -NoProfile -ExecutionPolicy Bypass -STA -File .\deploy\office-com-worker.ps1

# ポートを変える場合: -Port 9000 / -Token を引数で渡す場合: -Token "..."
```

- ワーカーは既定で **127.0.0.1 のみ** で待ち受け、共有シークレット（HTTP ヘッダ `X-Sherpa-Token`）が一致しないリクエストは 401 で拒否します。`-BindAddress` で非 loopback アドレスを明示すると起動時に警告が出ます（LAN 露出の注意喚起・下記 NAT の節参照）。
- 変換は **1件ずつ直列**で処理し、1件が既定 120 秒を超えたらワーカーの子プロセスを停止します。マクロは強制無効・読み取り専用で開き、原本には一切書き込みません。
- ⚠ **PowerPoint の単一インスタンス性**: すでに PowerPoint を開いている状態で変換がタイムアウトした場合、ワーカーは**その既存の PowerPoint プロセスを絶対に停止しません**（未保存の作業を守るため・変換が呼び出したインスタンスだけを識別して停止する設計）。そのためタイムアウトが起きても既存の PowerPoint はハングしたまま残ることがあり、その場合は**ワーカーの再起動**（and 必要ならタスクマネージャーで手動終了）が必要になることがあります。
- 「アクセスが拒否されました」で起動できない場合は、管理者権限の PowerShell で実行するか、URL ACL を追加します（`netsh http add urlacl url=http://127.0.0.1:8091/ user=<ユーザー名>`）。

#### WSL コア側の設定と疎通確認

`.env`（または `SHERPA_ENV_FILE`）に接続先と共有シークレットを設定します。ネットワーキングモードによって手順が変わります。

**(a) mirrored networking（推奨）**: Windows 11 の mirrored モードでは WSL の `localhost`/`127.0.0.1` が Windows 側とそのまま繋がるため、ワーカーの既定（127.0.0.1 bind）のままで届きます。

```bash
SHERPA_OFFICE_COM_URL=http://127.0.0.1:8091
SHERPA_OFFICE_COM_TOKEN=<Windows 側と同じ秘密>
```

**(b) 従来 NAT のまま使う場合**: NAT モードでは WSL から Windows の `127.0.0.1` へは届きません（127.0.0.1 は各ネットワーク名前空間に閉じているため）。ワーカー自身を、WSL 側から見える Windows ホストのアドレス（vEthernet (WSL) アダプタの IP）に明示的に bind する必要があります。

```powershell
# Windows 側（管理者 PowerShell）: vEthernet (WSL) の IP を確認（WSL からの既定ゲートウェイと同じ値）
(Get-NetIPAddress -InterfaceAlias "vEthernet (WSL)" -AddressFamily IPv4).IPAddress
# 例: 172.20.0.1

# 1) その IP に対して URL ACL を追加
netsh http add urlacl url=http://172.20.0.1:8091/ user=<ユーザー名>

# 2) 到達元を WSL のサブネットだけに絞るファイアウォール規則（<WSL のサブネット> は ip route 等で確認）
New-NetFirewallRule -DisplayName "Sherpa Office COM Worker (WSL only)" -Direction Inbound `
  -Protocol TCP -LocalPort 8091 -RemoteAddress <WSL のサブネット。例 172.20.0.0/20> -Action Allow

# 3) その IP に bind してワーカー起動（非 loopback なので起動ログに警告が出る＝想定どおり）
$env:SHERPA_OFFICE_COM_TOKEN = "<任意の長い秘密の文字列>"
powershell -NoProfile -ExecutionPolicy Bypass -STA -File .\deploy\office-com-worker.ps1 -BindAddress 172.20.0.1
```

```bash
# WSL 側（.env）: bind したのと同じ IP を指す（WSL からの既定ゲートウェイと一致するはず）
#   ip route show | awk '/default/{print $3}'   →  例 172.20.0.1
SHERPA_OFFICE_COM_URL=http://172.20.0.1:8091
SHERPA_OFFICE_COM_TOKEN=<Windows 側と同じ秘密>
```

WSL 側からヘルスチェックで疎通確認します（`ok` と各 Office のバージョンが返れば OK）。

```bash
curl -s -H "X-Sherpa-Token: $SHERPA_OFFICE_COM_TOKEN" "$SHERPA_OFFICE_COM_URL/healthz"
# 例: {"ok":true,"versions":{"word":"16.0","excel":"16.0","powerpoint":"16.0"},"worker":"1"}
```

疎通できると、システム管理画面の「旧形式の変換」で「Office 連携」を選べるようになり（到達不可なら選択肢は無効＝起動案内を表示）、以降の取り込みで .doc/.xls/.ppt が新形式へ変換されてから読み取られます。ワーカーが落ちている場合は自動的に「変換しない（未対応表示）」へ倒れます（fail-safe）。なお `SHERPA_OFFICE_COM_URL` を設定しなければ (A) の同一マシン直接呼び出し（設定不要）が使われます。

## 認証・ユーザーの運用

- 認証は既定で有効です。
- 初回 `admin` は自動作成され、`SHERPA_ADMIN_PASSWORD` または既定初期パスワード `Sherpa2026!` でログインします。
- 初期 `admin` は `must_change_password=true` のため、初回ログイン後に必ず変更します。
- 開発・検証で認証を無効化する場合だけ `SHERPA_AUTH_DISABLED=1` を設定できます。通常運用・本番運用では使いません。
- ユーザーは削除せず、必要に応じて**無効化**します。無効化しても個人 workspace は保持します。
- 監査ログにはログイン、ログイン失敗、初期 admin 作成、初回パスワード変更、共有、ユーザー管理、個人ファイル操作、出典ダウンロード、監査ログエクスポートなどが記録されます。
- `scripts/check-production.sh` は `SHERPA_AUTH_DISABLED=1` と初期 admin の初期パスワード残存を検出します。

接続情報は `.env` または `SHERPA_ENV_FILE` で指定した env ファイル（[90-リファレンス](90-リファレンス.md) の設定一覧）。
ストアのポート変数も同じファイルに書きます（`make`/scripts が `--env-file` で docker compose に渡すため、
`SHERPA_ENV_FILE=/etc/sherpa/sherpa.env` のような本番配置でも 1 か所で済みます。`.env.example` の「ポート」節にひな型あり）。
変更後は `make down` → `make up` で反映されます。

### ポート衝突の検査（`make check-ports`）

`make start` はストア起動の前に `scripts/check-ports.sh` を自動で呼び、次を表で確認して問題があれば起動を止めます
（`make prod-check` も同じ検査を含みます）。単体でも `make check-ports` で実行できます。

- **整合**: アプリの接続先（`DATABASE_URL`/`SHERPA_PG_DSN`・`ES_URL`・`NEO4J_URI`）が localhost を指すとき、そのポートが
  compose の公開ポート（`PGPORT`・`SHERPA_ES_PORT`・`SHERPA_NEO4J_BOLT_PORT`）と一致すること。不一致は「compose は 5433 で
  公開・アプリは 5432 へ接続＝別の PostgreSQL に繋ぎに行く」事故になるため NG（どの変数をどう直すかを表示）。
- **占有**: 各公開ポート（PG/ES/Bolt/HTTP/アプリ `SHERPA_PORT`）を既に他のプロセスが聴いていないこと。自分たちの
  compose project label と一致するコンテナや、PIDまで一致する起動済み自アプリなら OK。docker/PIDで所有者を確認できないときは安全側に NG とし、
  確認のうえ `SHERPA_SKIP_PORT_CHECK=1` で占有検査だけ省略できます。

## バックアップの考え方

- **一次データ**: 登録フォルダ（原本）＝外部の正本。PostgreSQL（会話・台帳・レジストリ）。個人ファイル（`SHERPA_USERS_DIR`・既定 `data/users`）。これらを守ればよい。
- **派生物**（Neo4j グラフ・ES 索引・`data/derived/{world}/` の写しMD・RAG正本・中間表現の3層＝`md/`・`rag/`・`ir/`）は**再生成可能**。最悪、再取り込みで復元できます。
- 具体的なバックアップ/リストアのコマンド・頻度の目安（RPO/RTO）・障害時の復旧手順は [41-運用Runbook](41-運用Runbook.md)。
