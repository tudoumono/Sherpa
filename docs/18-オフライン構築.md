# 18. オフライン構築（閉域・Linux）— 資材の網羅と導入順序の一次情報

**目的**: インターネットに一切出られない Linux 環境で、Sherpa をスムーズに（追加取得ゼロ・手戻りゼロで）構築する。
そのために、**オンライン側で OS 本体のライブラリまで含めた全依存を収集しきる**こと、**依存の向きどおりの導入順序**、
**「＊で一括」がこける類のコマンドの落とし穴**を、この1枚に固定する。

- **実装**（実行するもの）: 収集＝`scripts/make_offline_kit.sh` ／ 導入＝`scripts/install_offline_kit.sh`
- **操作手順書**（読みながら作業するもの）: `docs/manual/offline-kit.md`
- **この文書**: 何を・なぜ・どの順で。スクリプトと手順書が従う根拠。実装と食い違ったら実装を直すか、ここを直す

## 1. 前提（想定する閉域環境）

| 項目 | 想定 |
|------|------|
| OS | **インストール直後の Ubuntu 24.04 LTS（x86_64）**。`apt update` すら実行していない |
| ネットワーク | 外部到達ゼロ。apt リポジトリ・PyPI・Docker Hub・GitHub すべて不可 |
| 入っているもの | coreutils（tar/sha256sum）・systemd・sudo 可能な一般ユーザー。**それだけを前提にする** |
| 入っていないもの | `make`・`git`・`curl`（server minimal は無い）・`python3-venv`・`pip`・Docker・unzip・xz・fontconfig |
| 土台の一致 | キット同梱の `BASELINE`（収集元コンテナの ID / VERSION_ID / CODENAME / arch / 収集日 / イメージ digest）と閉域側の `/etc/os-release`・`dpkg --print-architecture` を**導入の最初に照合**する（`install_offline_kit.sh` 0.5）。不一致は即中止（`SHERPA_OFFLINE_ALLOW_BASELINE_MISMATCH=1` で警告に緩和可） |

「入っていないもの」は全部キットに同梱する。**閉域側で1つでも `apt install` が要る＝設計の失敗**として扱う。
git は同梱しない（配布は `make dist` の tarball で、版は `VERSION` ファイルから取れる＝git 不要で動く設計）。

### オンライン側（収集環境）

収集は **Ubuntu 24.04（x86_64）の Linux 上で実行する**。それがクラウドの VM か、物理機か、WSL2 の
Ubuntu かは問わない——**次の要件を満たすことだけが条件**で、手順は1本（§6 の1コマンド）。

収集前に1回、そのまま流して確認する:

```bash
uname -m            # → x86_64（arm64 で集めた資材は x86_64 の閉域側で全滅・持ち込むまで気づけない）
lsb_release -rs     # → 24.04（閉域側と同版。.deb の依存関係が版で変わる）
python3 --version   # → 3.12系（閉域側と同版。wheel が Python 版に紐づく）
docker run --rm hello-world   # → 成功（イメージの pull/build/save・素のコンテナでの apt 収集に必須）
df -h /             # → 空き 20GB 以上（キット約15GB＋作業領域）
```

搬出の規律は1つだけ: **tar.gz に固めてから運び、閉域側で展開するまで解凍・再圧縮しない**。
固める前のファイルを Linux の外（別ファイルシステム・別 OS のツール）に触らせない——実行ビット・改行・
symlink を壊す経路は、すべてここから生まれる。

### 収集の最終成果物

**tar.gz が1個**（＋照合用の `.sha256` が1個）。中身は「収集済みの `dist/offline-kit/` を含む、
このリポジトリのチェックアウト丸ごと」。閉域側はこれを展開したルートで `install_offline_kit.sh` を
1回実行するだけ、という形が導入側の前提になっている。

```bash
# 収集が終わったら（チェックアウトが ~/Sherpa の場合）
cd ~
tar -czf sherpa-offline-$(cat Sherpa/VERSION).tar.gz Sherpa/
sha256sum sherpa-offline-*.tar.gz > sherpa-offline.sha256   # 搬入後に閉域側で照合する
```

| 成果物 | 内容 |
|--------|------|
| `sherpa-offline-<版>.tar.gz`（約15GB） | チェックアウト全体＝アプリのソース・`scripts/`・`dist/offline-kit/`（§3 の資材11種） |
| `sherpa-offline.sha256` | 搬入時の破損・すり替え検知用 |

これで**足りないものは1つだけ**: ローカルLLM を使う場合の **ollama 本体バイナリ**（§3 #11・キット唯一の例外）。
使わないなら成果物は上の2ファイルで完結する。

## 2. 依存を「網羅しきる」ための原則

### 原則1: apt 系の収集は**素の対象OSコンテナ**で行う

`apt-get install --download-only` は、**実行したマシンの導入済み状態を基準に依存解決する**。
収集マシンに既に入っているパッケージの .deb は集まらない＝閉域側で必ず欠ける。これが「オンラインでは動いたのに
閉域で依存不足」の最大の原因。

対策として、収集は `docker run --rm ubuntu:24.04` の**素のコンテナ内**で行う（`make_offline_kit.sh` の
`_apt_collect_debs`）。これで**収集マシンの汚染**は防げる。ベースイメージ（`APT_BASE_IMAGE`）は**閉域側の OS
バージョンと必ず揃える**。

**ただし「素のコンテナ＝インストール直後の Ubuntu と同じ基準」は成立しない**（2026-08-17 実測で訂正）。
`ubuntu:24.04` タグはイメージ再ビルドで**土台（libc6/perl-base/zlib1g/gcc-14-base/dpkg 等）が noble-updates 版に
更新済み**であり、リリース当日版のままの閉域ホストより新しい。しかも土台は「導入済み」なので download-only の
閉包に**入らない**。結果、集めた .deb は「土台＝更新後版」への厳密依存（`Depends: libc6 (= 2.39-0ubuntu8.8)`）を
持ち、閉域側では `X (= 新版) but 旧版 is to be installed`／`libdb5.3t64 but it is not installable` の unmet で
apt が中止する（旧土台コンテナで再現・診断ログ 04/07）。閉包を本当に閉じるには次の 2 つが要る:

1. **土台の閉包も集める**（`make_offline_kit.sh` ステップ 12「土台の閉包」＝素のコンテナの導入済みパッケージ全部を
   `--reinstall --download-only` → `base/debs/`。`--skip-base` で除外可）。
2. **apt に索引を持たせる**（ステップ 13＝`apt-ftparchive` で `dist/offline-kit/` 直下に `Packages`/`Release` を生成）。
   導入側はこれを `deb [trusted=yes] file:<kit_root> ./` のフラット repo として読み、`./*.deb` 全列挙（＝版の強制）
   ではなく**トップレベル名**（各 `debs/PACKAGES`）を apt に解かせる。土台の .deb も候補に載るので、apt が土台ごと
   矛盾なく解決できる（旧土台ホストで「18 upgraded, 138 newly installed, 0 to remove」・削除ゼロを実測）。

**「土台の閉包」も、最小イメージの導入済み集合だけでは足りないことがある**（2026-08-18 閉域実機報告①）。
搬入先の実機（Ubuntu Server として構築済み）には `ubuntu-server`/`ubuntu-standard` 系メタが要求する群
（`libglib2.0-bin` / `packagekit` / `software-properties-common` 等）が最初から導入されている。キット側の
.deb（例: Chromium 依存の `libglib2.0-0t64` 新版）がそれらの**上げ先**を要求すると、索引に上げ先が無い場合
apt は「その群を削除して `ubuntu-server` ごと削除」で辻褄を合わせようとし、`--no-remove` により fail-close
する（実機は無傷だが、その群＝Chromium 依存が入らない。`apt-get -s` の実出力: `The following packages will
be REMOVED: libglib2.0-bin packagekit software-properties-common ubuntu-server`）。対策として、収集ステップ
12（土台の閉包）は最小イメージの閉包に加えて `BASE_CLOSURE_PACKAGES`（既定: `ubuntu-minimal ubuntu-standard
ubuntu-server`）も `--download-only` で**追加収集**する（導入はしない＝候補として索引に載せるだけ）。
実機の手当てで `base/debs` が 92→583 個に増え、削除提案は解消した（`scripts/verify_offline_kit_apt.sh` の
出荷ゲートで再現・是正を確認済み・§6）。

**土台の閉包の収集が失敗しても、以前は warn で続行し「直したつもりの壊れたキット」が完成し得た**
（2026-08-18 のレビューで指摘: 今回の実機不具合そのものが土台の閉包の欠落だったため、ここを非致命のままにする
理由が無い）。`--skip-base` による明示的な省略を除き、収集失敗（`$BASE_CLOSURE_PACKAGES` の typo・
無効なパッケージ名で apt が「見つからない」と失敗する場合を含む）は**キット生成そのものを止める**
（非0終了）。また `$BASE_CLOSURE_PACKAGES` は収集側の `docker … bash -c "…"` 文字列へそのまま埋め込まれる
（外側の bash が展開してからコンテナへ渡す）ため、パッケージ名として許される文字（半角英小文字・数字・
`+`/`-`/`.`）以外を含む値は収集開始前に拒否する（シェルのメタ文字による埋め込みを防ぐ）。

**土台の閉包は docker が無い収集機でも集められる**（2026-08-18 のレビューで指摘・是正）。
「収集失敗を致命化した」ことの副作用で、`docs/manual/offline-kit.md` が案内している「docker の無い
収集機」経路（他の apt 系グループが持つ `_apt_collect_debs_fallback`）が土台の閉包だけ使えず、
`--skip-base`（＝報告①の実機不具合を再導入）以外に道が無くなっていた。他の apt 系グループと同じ作法
（sudo・`Dir::Cache::Archives` を一時ディレクトリへ差し替え）で、**収集機自身が対象 OS（既定
Ubuntu 24.04 x86_64）であること**を前提に、収集機の導入済み集合＋`$BASE_CLOSURE_PACKAGES` の閉包を
`--download-only` で集めるフォールバックを追加した（`_apt_collect_base_closure_fallback`）。素の
対象OSコンテナのような分離はできないため、収集機の OS が閉域ホストと異なる場合は正しい閉包にならない
＝docker のある機体での収集を引き続き推奨する（フォールバック使用時は警告を表示する）。

### 原則2: 収集環境と閉域環境を揃える

| 揃えるもの | 理由 | ずれた時の転び方 |
|-----------|------|----------------|
| OS 系統・バージョン（Ubuntu 24.04 ⇔ 24.04） | .deb のパッケージ名・依存関係が版で変わる | `apt-get install ./*.deb` が依存不足で失敗 |
| Python のメジャー.マイナー（3.12 ⇔ 3.12） | wheel は収集時の Python に紐づく | `pip install --no-index` で「一致する wheel が無い」 |
| CPU アーキテクチャ（x86_64） | wheel・.deb・Docker イメージすべてに効く | 導入も起動も全滅 |

**wheel の収集は既定で「対象 OS の素のコンテナ内 python3」で行う**（`SHERPA_WHEELS_IN_CONTAINER`・docker があれば
既定 ON）。閉域側の python3 と major.minor が構造的に一致する（同じ `$APT_BASE_IMAGE` の中で pip download する
ため）。使った python3 の版は毎回 `COLLECTED-WITH-PYTHON-VERSION.txt` に記録する。

以前は収集側の python3 版を**記録するだけ**だったため、3.9/3.11 の収集機で作ったキットが検証も無いまま
完成し、閉域で `--no-index` install して初めて「一致する wheel が無い」と気づいた（2026-08-18 閉域実機報告②）。
**端末の Python で集める経路**（`SHERPA_WHEELS_IN_CONTAINER=0`）を使う場合は、対象 OS（`$APT_BASE_IMAGE`）の
python3 版と major.minor を突き合わせ、**不一致なら収集そのものを止める**（`SHERPA_ALLOW_PY_MISMATCH=1` で
警告のみに緩和可）。コンテナ収集（既定）は版がそもそもずれ得ないため、この照合は行わない。

対象 OS の python3 版は、**docker が使えるなら毎回対象イメージへ直接問い合わせて読み直す**
（`docker run --rm $APT_BASE_IMAGE apt-cache policy python3`）。以前は前回収集時点の `BASELINE` の
`IMAGE=` タグ文字列が一致すれば流用していたが、タグは digest を保証しないため、ローカルの
`$APT_BASE_IMAGE` タグが同じ名前のまま差し替わっていたり `BASELINE` が古いまま残っていると照合が
黙って通ってしまう＝false pass（2026-08-18 のレビューで指摘）。`BASELINE` を見るのは docker も `apt-cache` も
無い機体でのみ、最後の手段として（かつ警告を出したうえで）に限る。

### 原則3: バージョンを固定し、内容を照合する

「最新を取る」収集はしない。Node は版ピン（v22.22.3）＋公式 `SHASUMS256.txt` 照合、OCR モデルは
`docker/ocr-models.lock.json` の tree hash 照合（合わないとワーカーが起動を拒む）、wheel は `SHA256SUMS` を残す。
照合できない資材は「集めたつもりで別物」になり得る＝閉域に持ち込んでから気づくと往復が発生する。

### 原則4: 閉域側で**ネットワーク源へ** `apt-get update` を叩かない

インデックス取得はネットワーク必須なので**失敗するだけ**。「まず apt update」というオンラインの習慣を閉域へ
持ち込まない。導入スクリプト（`scripts/lib/apt_offline.sh`）が行う `apt-get update` は、一時 sourcelist
（`Dir::Etc::sourcelist`＋`sourceparts=-`＋`Dir::State::lists=一時dir`）で**キット内の file: repo だけ**を読む
ものであり、`/etc/apt` を汚さずネットへも出ない。

### 原則5: 出荷前に「搬入先相当のホスト＋ネットワーク無し」で実際に導入してみる

原則1〜4はどれもコードレビューや `bash -n` では検出できない。報告①（土台の閉包漏れ）は「搬入先と同じくらい
古いホスト＋ネットワーク無し」で実際に apt を走らせて初めて出た不具合であり、実装を直しただけでは同種の
穴（新しい apt グループを足した時に上げ先が抜ける、等）の再発を防げない（2026-08-18 閉域実機報告③）。

そのため、収集したキットは**出荷前に必ず `make verify-kit`（`scripts/verify_offline_kit_apt.sh`）を通す**。
搬入先に近いホスト像（インストール直後の Ubuntu Server 24.04 GA 相当＝`ubuntu-minimal`/`ubuntu-standard`/
`ubuntu-server`＋カーネルを導入し apt lists を空にした docker イメージ・初回だけオンラインで構築し以後は
再利用）から `--network none` でコンテナを起動し、キットと `scripts/lib/apt_offline.sh` を実物ごと持ち込んで
apt グループを実導入する。**導入経路は `install_offline_kit.sh` と同じ `apt_offline_install` をそのまま使う**
（別経路を作らない）。削除提案・カーネル消失・導入失敗が1つでもあれば非0で止まる。docker が無い環境では
「検証できません」と明示して非0にする（黙って成功にしない）。詳細は §6。

## 4. 導入順序（依存の向きで一列）

`./scripts/install_offline_kit.sh` がこの順で実行する。手で行う場合も**この順を崩さない**。

| 順 | 作業 | なぜこの位置か（前提） | 順序を崩した時の転び方 |
|----|------|----------------------|----------------------|
| 1 | アプリ本体 tar 展開 | — | — |
| 2 | **Python 実行系 .deb**（`apt_offline_install`＝**`-s` 先行→Remv 検出で中止→`--no-remove` 本導入→稼働カーネル残存確認**） | すべての Python 作業の前提。素の環境は `python3-venv` が無く**最初にここで転ぶ** | venv 作成が `ensurepip` エラー |

## 5. コマンドの落とし穴（実際にこける書き方と、正しい書き方）

### .deb の一括導入 — `dpkg -i *.deb` は使わない

```bash
# ✗ こける: dpkg は依存解決しない。ワイルドカード展開＝アルファベット順に処理するため、
#    依存される側より先に依存する側が来ると「依存関係の問題」で失敗する。
#    二度打ちで収束させる流儀は再現性が無い（並びと欠け方に依存する）。
sudo dpkg -i *.deb

# ✗ こける: ./ が無いと apt は「パッケージ名」として解釈し、インデックスの無い閉域では
#    「パッケージが見つかりません」で即失敗する。
sudo apt-get install -y *.deb

# △ 依存グラフは解けるが**危険**（2026-08-17 実測で降格）: 閉包に穴があると apt の問題解決器は
#    「既存パッケージの削除」で辻褄を合わせようとし、-y はそれを黙って承認する（postfix.deb で exim4 3個が
#    無言で Remv された実測あり）。連鎖が initramfs-tools → linux-image-* に及ぶと稼働カーネルの削除
#    （紫の debconf 画面）に至り得る（実閉域機の報告・経路は推測）。土台ずれの unmet／降格でも全停止する。
sudo apt-get install -y ./*.deb

# ○ 正（scripts/lib/apt_offline.sh）: 必ず -s（シミュレーション）を先行し Remv があれば中止、
#    本導入は --no-remove（削除は構造的に禁止）＋非対話（DEBIAN_FRONTEND=noninteractive・
#    --force-confdef/--force-confold・NEEDRESTART_MODE=l を sudo の内側で渡す）。
#    索引付きキットは file: repo として名前指定（降格が起きない・土台の閉包も候補に載る）。
#    導入後に linux-image-* が消えていないことを確認する。
bash scripts/lib/apt_offline.sh install "python/debs" "$PWD/dist/offline-kit" "$PWD/dist/offline-kit/python/debs"

# 参考: ライブラリが内部でやっていることを生の apt-get で書くと（`install` を忘れない・パスは絶対か ./ 始まり）
sudo DEBIAN_FRONTEND=noninteractive LC_ALL=C.UTF-8 apt-get -s -y --no-remove install ./*.deb   # 削除が要ると非0で止まる
sudo DEBIAN_FRONTEND=noninteractive LC_ALL=C.UTF-8 apt-get -y --no-remove \
  -o Dpkg::Options::=--force-confdef -o Dpkg::Options::=--force-confold install ./*.deb
```

※ 実 apt では `--no-remove` 付きの `-s` は削除が要る時点で「Packages need to be removed but remove is
disabled」で非0終了する（`Remv` 行は出ない）。ライブラリはこの形も「削除を伴うため中止」として扱い、
何を消そうとしたか（`will be REMOVED:` の一覧・`linux-image` を含むか）を表示する。

`install_offline_kit.sh` の `_apt_install_local_debs` は `apt_offline_install`（`scripts/lib/apt_offline.sh`）の
薄いラッパ。単体でも `bash scripts/lib/apt_offline.sh install <desc> <kit_root> <group_dir>` で実行できる
（Docker での検証・契約テスト `tests/contract/test_offline_apt_safety.py` は実コードを叩く）。

### その他の定番

| 落とし穴 | 症状 | 正 |
|---------|------|----|
| 閉域で（ネット源へ）`apt-get update` | ネットへ行って失敗するだけ | 叩かない。キット内 file: repo への update は一時 sourcelist で行う（原則4） |
| `apt-get install -y ./*.deb` の削除提案 | 閉包に穴があると**削除提案（稼働カーネルを含み得る）を黙って通す**／土台ずれで unmet・降格の全停止（2026-08-17 再現） | 必ず `-s` 先行＋`--no-remove`＋索引付き名前指定＋BASELINE 照合（`apt_offline.sh`） |
| 収集イメージの土台が閉域より新しい | `Depends: libc6 (= 新版) but 旧版 is to be installed`／`not installable` | 土台の閉包（`base/debs`）を同梱し索引で解かせる。不足名は導入側が抽出して表示する |
| 実機の導入済み集合（ubuntu-server 系）の上げ先が閉包に無い | `The following packages will be REMOVED: libglib2.0-bin packagekit software-properties-common ubuntu-server` を `--no-remove` で fail-close（2026-08-18 実機報告①） | `BASE_CLOSURE_PACKAGES`（既定 `ubuntu-minimal ubuntu-standard ubuntu-server`）を土台の閉包に含める（既定で有効・原則1）。出荷前に `make verify-kit` で再現がないことを確認する |
| `usermod -aG docker` 直後に docker コマンド | permission denied | **再ログイン**（または `newgrp docker`）。スクリプトは当面 `sudo docker` で続行する設計 |
| `pip install -r requirements.txt` | PyPI へ出ようとして失敗 | `--no-index --find-links=dist/offline-kit/wheels` を必ず付ける |
| OCR の wheel をコア venv へ入れる | numpy が上書きされ**コアが壊れる**（実際に踏んだ） | 専用 venv（`.venv-ocr`）または同梱イメージを使う |
| root で `install_offline_kit.sh` を実行 | Chromium/Ollama が `/root` 配下に入り自動検出から消える | 一般ユーザーで実行（内部で必要な所だけ sudo する。スクリプトは root 実行を拒否する） |

| コンテナ収集した .deb が root 所有で再収集に失敗 | `rm -rf` が permission denied | 収集側で対処済み（コンテナ内で `chown` してから出る） |

## 6. 検証（「入った」ではなく「動く」を見る）

### 出荷前（オンライン側・`make verify-kit`）

**キットを閉域へ搬入する前に、必ず `make verify-kit`（`scripts/verify_offline_kit_apt.sh [キットのパス]`。
既定 `dist/offline-kit`）を通す**（M7・2026-08-18・原則5）。docker で「搬入先に近いホスト」（インストール
直後の Ubuntu Server 24.04 GA 相当・初回だけオンラインで構築し以後は再利用）を用意し、そこへ
`--network none` で実際にキットを apt 導入してみて、削除提案・カーネル消失・導入失敗が無いことを確かめる。
導入経路は閉域側が使うのと同じ `apt_offline_install`（`scripts/lib/apt_offline.sh`）をそのまま使う。
1つでも問題があれば非0で止まる。docker が使えない機体では「検証できません」と表示して非0になる
（黙って成功にしない＝出荷判断を誤らせない）。実機報告①（§2 原則1）はこのゲートが無かった時期に
コードレビューをすり抜けて出た不具合であり、以後の変更（新しい apt グループの追加等）でも毎回このゲートを
通すことで同種の再発を防ぐ。

**検証対象の5グループ（Python実行系/Docker Engine/Chromiumシステム依存/LibreOffice/Noto Sans CJK JP）は
既定で全部「必須」＝未収集なら NG**（2026-08-18 のレビューで指摘: 以前は未収集を無条件に `[未収集]` 表示のまま
rc=0 で通していたため、`--skip-*` で作った／収集が途中で失敗した欠けたキットがそのまま出荷ゲートを
通ってしまっていた。実導入では Python 実行系が無いと後段（`.venv` 作成・`pip install --no-index`）が
最初に転び、Docker Engine が無いとストア自体を起動できない）。`--skip-*` で意図的に作った部分キットを
このゲート単体で検証したいとき（例: python + chromium 依存だけの縮小キット）だけ、
`--allow-missing-groups`（`make verify-kit ARGS="--allow-missing-groups"`）を付けると従来どおり
`[未収集]` 表示のまま許容する。

**検証用ホスト像は「存在すれば中身を見ずに再利用」しない**（2026-08-18 のレビューで指摘: ローカルに古い／別内容の
同名イメージが残っていると、ゲートが別物のホストで通ってしまう）。ビルド時に来歴（レシピ版・ベースタグ・
snapshot 時刻）を docker label として像へ刻み、次回起動時にこれを照合して**不一致なら作り直す**
（`SHERPA_WFTEST_REBUILD_HOST=1` で常に強制再構築も可）。加えて、実機 Ubuntu Server の導入済み集合の
代表（`libglib2.0-bin`/`packagekit`/`software-properties-common`/`ubuntu-server`/`linux-image-generic`。
実機報告①で `ubuntu-server` 系メタが要求していた上げ先そのもの）が実際に導入されていることも、
再利用の可否判定と構築直後の両方で明示的に確認する。ホスト像の構築は `--no-install-recommends` を
**外し**、apt の既定（`Install-Recommends=yes`）と同じ recommends 込みで行う（判断: 実機の Ubuntu Server
標準導入に近づけることを、像が肥大するコストより優先した。この検証の目的自体が「搬入先の導入済み集合の
近似」なので、過小評価より過大評価の方が安全側）。

これらは docker を使う実導入・実ホスト像構築の検証として手元で実行して確認済み（縮小キットで
「必須グループ欠落→NG」「`--allow-missing-groups`→従来どおり許容」、旧世代（来歴 label 無し）の
既存ホスト像に対する自動的な作り直し、を実測）。
通すことで同種の再発を防ぐ。

### 閉域側（`install_offline_kit.sh` の最終検証）

`install_offline_kit.sh` の最終検証が、各資材を**実際に実行して** OK/NG/未収集の表を出す
（python/venv・docker・イメージ4つ・node/marp・chrome 起動・soffice・fc-list・OCR イメージ＋モデル配置）。
未収集（意図的スキップ）は NG にしない。1つでも NG なら版は確定されず、`current` は切り替わらない。

導入の全出力は **`data/install-logs/install-offline-<日時>.log` に1本**で残る（`make nuke` でも消えない）。
途中で失敗すると、最後に「どのステップで・どのコマンドが・終了コード何で」止まったかとログの場所を
まとめて表示する。**閉域で原因が分からないときは、このログ1本を持ち出せばオンライン側で調査できる。**

起動後のスモーク（手動・5分）:

```bash
make status                       # ストア3つ・アプリ・OCR ワーカーの一枚看板
curl -sf http://127.0.0.1:8000/healthz
# 画面: 資料フォルダ登録 → 取り込み → チャットで1問 → 出典から原本DL
```

## 7. 更新（2回目以降の搬入）— 既存資材・データとの関係

更新は「新しいキットを**別ディレクトリ**に展開し、同じ導入コマンドをもう一度」。既存資材とは混ぜない。
成り立つ前提は **`--target-dir` 方式（本番標準・`docs/manual/40-運用.md`「本番展開の標準手順」）**で、
データ系パスを `/etc/sherpa/sherpa.env` で `/srv/sherpa/...`（`current`/`releases` の外）に出していること。

手順（閉域側）:
```bash
mkdir -p ~/sherpa-kits/<新版> && tar -xzf sherpa-offline-<新版>.tar.gz -C ~/sherpa-kits/<新版>   # 旧展開先へ上書きしない
cd ~/sherpa-kits/<新版>/Sherpa
./scripts/install_offline_kit.sh --target-dir /opt/sherpa/current     # releases/<新版> へ展開→検証→current 切替
```
旧展開先へ上書き展開しないのは、tar は「消えたファイル」を消さない（旧版の残骸が混ざる）ため。
オンライン側の収集も**毎回フル**（`--fetch`）。一部グループだけの再収集は世代混在を招く（§3 #13）。

| 既存のもの | 更新時の扱い |
|-----------|-------------|
| DB（PostgreSQL/Neo4j/ES） | **引き継がれる**。compose のプロジェクト名が `sherpa-mvp` 固定＝ボリューム `sherpa-mvp_pg` 等はどのチェックアウトから起動しても同じ。スキーマは起動時に追記型（`CREATE IF NOT EXISTS`／`ADD COLUMN IF NOT EXISTS`）で前進 |
| 派生物・個人領域・OCR 観測・モデル | `SHERPA_*_DIR` が `/srv/sherpa/...` を指していれば触られない |
| アプリ本体 | `releases/<新版>` に**別フォルダ**で展開→検証成功後に `current` を切替。旧版は残り `--rollback-to` で戻せる |
| Python venv・Node/marp | 版フォルダごとに新規作成（in-place 更新はしない） |
| Docker イメージ | `docker load` でタグが新版へ。旧レイヤは残る（`docker image prune` は任意） |
| OS パッケージ | apt が必要な分だけ上げる（`--no-remove`・カーネル残存確認・§5） |
| Chromium・フォント・Ollama モデル | 共有場所へ上書き（同じ版なら実質無変更） |
| 旧キット（前回の `dist/offline-kit`） | 使わない。切替成功後に消してよい。旧 `releases/<版>` は戻す用に残す |

**制約**:
- **既定モード（チェックアウト内で完結）は更新に向かない**。`.env` と `data/` がチェックアウトの中にあるため、
  新しい tar を別ディレクトリに展開すると引き継がれない。試用を超えて使うなら**最初の更新の前に**
  `--target-dir` 方式へ移すか、少なくとも `SHERPA_*_DIR` を `/srv/sherpa` 等の外へ出す。
- **DB は前進のみ**。アプリは `--rollback-to` で戻せるが、スキーマは追記型なので旧版でも概ね動くものの
  保証はない。そのため**切替前にデータを退避する**: `make backup`（`scripts/backup.sh`・ストア停止中に
  ボリューム3つ＋個人領域＋.env を `data/backups/<日時>/` へ・MANIFEST に sha256）／戻すのは
  `make restore FROM=<dir>`（`scripts/restore.sh`・sha256 照合→ボリューム作り直し→展開・.env は上書きしない）。
  更新（`--target-dir` が既存の完成版 symlink）では、導入スクリプトが **current 切替の直前に自動で `backup.sh` を実行**する
  （ストア停止中のみ。稼働中なら「未取得」と警告して続行、停止中の取得失敗は切替中止・`SHERPA_BACKUP_BEFORE_SWITCH=0` で抑止・出力先の既定は
  `<target-dir の親>/backups/`）。tar 用のワークコンテナは手元のイメージ（`postgres:16` 優先）を使うので閉域でも動く。
  手順の詳細は `docs/manual/40-運用.md`「バックアップと復元」。
- 更新後は資料フォルダの**「更新」（再取り込み）を1回**回す。変換器の変更は派生物に自動では反映されない
  （アーム構成の変化は自動検知するが、変換コードの変更は検知しない）。
- **重要度スキーマの版上げを含む更新**（v0.1.x→重要度列の台帳格納・IMPORTANCE_SCHEMA_VERSION=2）では、
  この「更新」1回が**全既存フォルダの全再構築**になる（1回だけ・成功後は通常の「変化なし＝即完了」へ戻る）。
  2TB 級では時間と I/O 負荷が大きいため**保守時間を確保**すること。再構築中は資料一覧・ダウンロードが
  待たされる時間帯がある（取り込みと同じロックを共有するため）。
