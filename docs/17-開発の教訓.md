# 開発の教訓

> 位置づけ: **現役（参照）**。一般化できる開発の教訓を1箇所に溜める（決定 2026-08-22）。
> コードコメントには「現在の仕様・不変条件・非自明な理由」だけを残し、修正の経緯・レビュー番号・実装日は
> Git/PR を基準とする（コードコメントの運用規約）。
> 形式: 1教訓＝1節（事象 → 型 → 出典）。固有の経緯・障害の詳細は書かない（Git を辿る）。

## 載せる基準（4問すべて Yes なら載せる）

1. **別の場所で再発しうるか** — 特定ファイル固有の不具合ではなく、別モジュール・別機能でも同じ「型」の失敗をやり得る。
2. **再発見コストが高いか** — コードや git log を普通に読んでも気づきにくい（ライブラリの暗黙仕様・環境の性質・直感に反する挙動）。
3. **行動が変わる「型」を書けるか** — 「〜する時は〜せよ」という命令形1文に落ちる。落ちないならまだ教訓ではなく感想。
4. **今も有効か** — 解消済みの一回性バグの説明は載せない（それは Git）。仕様の説明も載せない（それは as-built docs）。

載せないもの: 単なるバグ修正の記録／現行仕様の解説／好み・スタイルの話／このプロジェクトでしか起きない事情。
追記のタイミング: レビュー完了時・障害対応完了時に「教訓に載せる型はあるか」を1回問う。

## 負値の環境変数がスライス上限を反転させ、制限を無効化する

- **事象**: 上限値の env に負値を渡すと `calls[:-1]` のようにスライスが反転し、「末尾1件を除いて全部通す」＝上限が実質無効になった。
- **型**: 外部入力（env・設定値）を上限・範囲・スライスに使う時は、必ず `[lo, hi]` でクランプする共通関数を通す。既定値自体もクランプする（動的既定が cap を素通りした前例あり）。
- **出典**: `sherpa/agentic_search.py::_env_int`

## デフォルト引数は def 時に束縛され、monkeypatch が効かない

- **事象**: 上限定数を関数のデフォルト引数値にすると、テストの `monkeypatch.setattr(module, "CAP", …)` が効かない（def 時に値が固定済み）。
- **型**: テストで差し替えたい定数は、デフォルト引数ではなく**関数本体でモジュール属性を都度読む**。
- **出典**: `sherpa/ingest/ooxml/excel.py`（`DEFAULT_CAP_ROWS` 等の参照方式）

## ThreadPoolExecutor の非 daemon スレッドがプロセス終了を塞ぐ

- **事象**: 並列化に使った ThreadPoolExecutor のワーカースレッドが非 daemon のため、例外経路でプロセスが終了しない・残留する。
- **型**: 並列実行の導入時は、異常系でも回収される終了経路（shutdown・タイムアウト・daemon 性）を先に設計する。
- **出典**: 取り込みアーム並列化（コミット 32d83cb 前後）

## openpyxl の read_only ワークシートは構造情報を持たない

- **事象**: `read_only=True`（ストリーミング読み）では `merged_cells`／`row_dimensions`／セル単位 `hyperlink`・`comment` が取れない。
- **型**: ライブラリの「軽量モード」は何を捨てるかを必ず確認し、必要な情報と引き換えなら通常モードのコスト（メモリ・2回ロード）を明示的に払う判断を docstring に残す。
- **出典**: `sherpa/ingest/ooxml/excel.py`（`load_two` の設計判断）

## ラッパー越しの検証は、ラッパー自体が結果を汚す

- **事象**: 外部 CLI をサンドボックス／バックグラウンド経由で検証したところ、ラッパーの交絡で「壊れている」と誤結論しかけた。
- **型**: まず「素で動く呼び出し形」を確立 → 変数を1つずつ変える → 成果物は別プロセスで観測 → 「壊れている」と結論する前に対照実験（動くケースを同じ手法に通す）を挟む。
- **出典**: 開発リポジトリ内部の調査記録（2026-07-01）

## レビュー中に「実在しないコード」を発見してしまう

- **事象**: レビューで、実在しないコード片を問題として「発見」しかけた。
- **型**: 指摘の裏取りは Read／git の正規出力のみを信頼する。記憶・要約・他エージェントの報告からコードを引用しない。
- **出典**: 開発リポジトリ内部のレビュー記録（2026-07-13）

## セキュリティのチョークポイントは新設経路がバイパスする

- **事象**: URL 検証等をチョークポイント関数に集約しても、後から足した新設シンク（サブループ等）が素通しし、SSRF の穴が再発しうる。
- **型**: 「必ずこの関数を経由する」という不変条件はコメントで契約化し、新設経路のレビュー観点に含める。可能なら直叩きをテストで検出する。
- **出典**: `sherpa/llm.py::assert_ollama_url_allowed`

## 共有 DB を使うテストの並列実行は偽失敗を作る

- **事象**: `tests/api` 等（共有 dev PostgreSQL 利用）を2本同時に走らせると `audit_log` で deadlock し、無関係なテストが落ちた（偽失敗5件）。
- **型**: pytest は1本ずつ。サブエージェント委譲時も「開始前に `ps` で確認」を指示に含める。
- **出典**: 開発リポジトリ内部の引き継ぎ記録（2026-08-21）§3

## 検収レビューを省略すると実害バグが残る

- **事象**: 作成物ごとの Codex によるレビューで、毎回、実害のある欠陥が検出されている（設定保存の焼き付け・出荷ゲートの素通り・base URL 検証の迂回 等）。
- **型**: レビューは作成物ごとに必ず実施する。ただし指摘は無条件に飲まず、現在の実装・テスト・公式仕様で裏取りして採否を理由付きで決める。
- **出典**: 開発リポジトリ内部の引き継ぎ記録（2026-08-21）§4

## 外部 API の「正常応答に付く注意フィールド」を失敗と誤検知する

- **事象**: Azure OpenAI は正常応答にも `content_filter_results`（`filtered: false`）を必ず付けるため、フィールド名の存在だけで判定した検査が成功を NG にした。
- **型**: 外部 API の検査は「フィールドの存在」ではなく「値の意味」で判定する。判定条件は公式仕様の該当記述と対で書く。
- **出典**: `scripts/azure_smoke.py`

## import 時に env を読み切るモジュール定数は、per-test の隔離では制御できない

- **事象**: `sherpa.llm` の URL 定数のように「import 時に一度だけ env を読む」値は、per-test の monkeypatch/autouse fixture では手遅れ（既に束縛済み）で、開発機の実 env がテスト結果を変えていた。
- **型**: env 由来のモジュールレベル定数を制御したいテストは、**テスト収集開始前（conftest のモジュールレベル）で env を正規化**する。per-test fixture はその上の二重防御。
- **出典**: `tests/conftest.py`（セッション開始時の AI 系 env 一括除去）・`tests/_ai_env_isolation.py`

## 未設定時のフォールバックが実環境の機密を指す env は、削除しても隔離にならない

- **事象**: `CODEX_HOME` を delenv すると、コード側フォールバックが `~/.codex`（開発機の実 `auth.json`）を指し、むしろ実機密を参照してしまった。
- **型**: フォールバック先が実環境の状態・機密を指す env は、削除ではなく**実在しないセンチネル値へ差し替える**。
- **出典**: `tests/_ai_env_isolation.py::CODEX_HOME_SENTINEL`

## エラー詳細の秘密マスクは、文字数切断より前に行う

- **事象**: エラー整形が「切断（`[:400]`）→呼び出し元でマスク」の順だったため、切断境界をまたぐキーの断片が完全一致置換をすり抜けた。URL エンコードされたキーも素通りしていた。
- **型**: 秘密を含みうる文字列は「**整形 → マスク（素の値＋URLエンコード形）→ 切断**」の順序を**1つの安全整形関数の中で保証**し、呼び出し元に順序を委ねない。適用漏れを防ぐため、整形関数の直接呼び出しを禁じて安全関数だけを入口にする。
- **出典**: `sherpa/ingest/graph_extract.py::_safe_detail`・`sherpa/agents.py::_safe_bedrock_detail`

## 「冗長に見える防御」を消す前に、それを単独検証するテストが契約かを確認する

- **事象**: 呼び出し先（probe）が安全になったので呼び出し元の重複マスクを削ったところ、既存テストが失敗した——そのテストは「probe 自体が差し替えられても呼び出し元が独立に防げること」を意図的に固定する契約だった。
- **型**: 多層防御の一層を「冗長」と判断して消す前に、**その層だけを単独検証するテストの有無**を確認する。あればそれは冗長ではなく契約。
- **出典**: `tests/api/test_bedrock_settings.py`（probe 差し替え下の caller 側 redaction 検証）

## 新しい索引ソースを足すときは「署名・ID・帰属・破損・上限」を最初に問う

- **事象**: 検索索引へ新ソース（サイドカーファイル）を追加した実装が、①切替フラグが鮮度署名に入らず反転が反映されない ②ソース由来 ID をそのまま `_id` にして衝突が無警告上書き ③サイドカーの帰属（どの原本のものか）未検証 ④部分破損の黙認 ⑤全読みで上限なし、の5点を一度に踏んだ（レビューで検出）。
- **型**: 索引ソースの追加では最初に5問を確認する——(1) ソース選択に影響する**設定は鮮度署名に入っているか** (2) **ID は名前空間化**されているか（外部由来 ID を `_id` に直用しない） (3) ソースの**帰属検証**（source ↔ 原本の突合）があるか (4) 部分破損は**ファイル単位で fail-closed** か（黙って部分成功しない・縮退は計数報告） (5) **サイズ/件数上限**が明示定数であるか。
- **出典**: `sherpa/es_index.py`（SEARCH-CUT-2・`search_chunk_mode` 署名／`_rag_chunk_es_id`／`_validate_rag_chunks`）

## 検証と使用で同じ解決を2回行うと、その間の差し替えで食い違う

- **事象**: read_around が「検証時」と「open 時」に同じ優先順位解決を独立に2回呼んでおり、間に派生の世代切替が挟まると検証したファイルと読むファイルが食い違い得た（in-run ABA の変種・レビューで静的に検出）。
- **型**: 検証→使用の間で対象が変わりうるものは、**解決を1回だけ行い、その結果（root・相対名・検証済みパス）を一体で持ち回す**。テストは spy で「解決が正確に1回」を固定する。
- **出典**: `sherpa/agentic_search.py::_safe_doc_path`（3-tuple 契約）・`tests/unit/test_agentic_search.py::test_read_around_resolves_target_exactly_once`

## 共有ストアの in-place アップグレードは、旧ブランチの検証環境を壊す

- **事象**: 共有 dev の Elasticsearch を 8.19 へ更新（データ形式も 8.19/Lucene912 に不可逆変換）した後、更新前に分岐したブランチの worktree で `make start` すると、compose が旧タグ（8.15）を起動してデータを読めず即死した（`Could not load codec 'Lucene912'`・ダウングレード不可）。
- **型**: データ形式が非可逆なストアを in-place 更新したら、**この更新に関わる変更がマージされるまで旧ブランチの起動は壊れている**と認識する。回避は「旧タグを新バイナリへ一時 retag」（ファイルを汚さず全 worktree に効く・マージ後に自然消滅）か、検証ガイドへの明記。更新作業の報告にも「未マージブランチの検証への影響」を含める。
- **出典**: `docker tag sherpa/es-kuromoji:8.19.20 sherpa/es-kuromoji:8.15.0`（2026-08-22・8.15 実体は `:8.15.0-orig` に退避）

## 上流 API が「部分マスク済み」で返すエコーは、完全一致の秘密マスクをすり抜ける

- **事象**: OpenAI の 401 は `Incorrect API key provided: AbCd1234****…****Zz99` と**キーの先頭8字＋末尾4字**を部分マスクしてエコーする。完全一致・URLエンコード形・Bearer/api-key/sk- パターンのいずれにも一致せず、キー材料12字が画面に露出した（機械テスト1,500件＋独立レビュー4巡の後、**人の実機確認1回**で発見）。
- **型**: 秘密のマスクは「完全一致」だけでなく、**(1) アスタリスク列を含むトークンの丸ごと除去、(2) 既知 secret の接頭辞/接尾辞断片（7字以上）の除去、(3) マスク済みトークンに隣接する短い随伴断片の除去**、を重ねる。上流の出力形式は自分の制御外＝「どう壊れて返ってくるか」を実機で1度は観測する。
- **出典**: `sherpa/ingest/graph_extract.py::_mask_secrets`（`_MASKED_TOKEN_RE`／`_mask_secret_fragments`）・`tests/unit/test_graph_extract_probe_redaction.py`

## 実機で観測した秘密の断片を、契約書・コメント・テスト・教訓へ「そのまま」写さない

- **事象**: 実機の 401 エラーに含まれていた**実キーの部分マスク断片**（先頭8字＋末尾4字）を、現象の説明としてエージェントへの指示・コードコメント・回帰テストのダミー値・教訓集へそのまま転記し、そのままコミット/push した（置換＝ダミー化で是正・キーはローテーション対象）。
- **型**: 観測した秘密（断片・マスク済み・ハッシュの一部を含む）は、記録の前に**必ず形だけ残した架空値へ置き換える**（例: `AbCd1234****Zz99`）。「マスク済みだから安全」「一部だから安全」と判断しない。指示文・報告・コミットメッセージも同じ（エージェントは受け取った文字列をそのまま成果物に埋める）。
- **出典**: 2026-08-22 の是正コミット（`ba18253`）・`tests/unit/test_graph_extract_probe_redaction.py` のダミー値

## 文字列置換による文書/コードの機械編集は、置換件数を検証してからコミットする

- **事象**: `str.replace` 前提の機械編集で、対象文字列が想定とわずかに違い**置換0件のまま**「ok」を表示してコミットした（他ファイルの変更と同じコミットに乗ったため `nothing to commit` にもならず、台帳の追記が3回分欠落していた）。
- **型**: 置換系の編集は「置換件数 ≥1 を assert」「編集後に `grep`/`git diff --stat` で対象ファイルが実際に変わったことを確認」してからコミットする。複数ファイルを1コミットに束ねるときは、ファイルごとの差分有無を個別に見る。
- **出典**: 開発リポジトリ内部のドキュメント整備記録（2026-08-22）#11〜13 の追記やり直し（2026-08-23）

## ストリーミング本文に制御トークンを混ぜない（帯域内タグ＝漏れ・境界バグの温床）

- **事象**: 回答の「根拠」帰属を取るために、LLM の最終出力末尾へ `<used_evidence>…</used_evidence>` の制御行を書かせ、ストリーム配信側で末尾行を保留して除去する方式を採った。レビュー4巡にわたり、行頭空白・CRLF・終端空行・長大行・壊れたタグ・早期確定後の上書き・停止/例外時の欠落など、**境界条件の指摘が尽きなかった**（配信本文の byte 同等仕様とも常に緊張）。
- **型**: 表示本文と機械向け制御情報は**帯域を分ける**。帰属・分類・メタ情報は、本文ストリーム完了後の**小さな非ストリーム構造化呼び出し**（tool/JSON schema）で取る。追加コストは1呼び出し分だが、保留ロジックと漏れの検証が丸ごと不要になる。「本文にタグを書かせて後で剥がす」設計は、最初から不採用にする。
- **出典**: 2026-08-23 の設計変更（複数回のレビューを経て後段の帰属呼び出し方式へ変更）

## 外部エージェントへの指示文をシェル引数で渡すときはバッククォートを使わない

- **事象**: Codex レビューの指示文（ダブルクォート内）に `` `git diff a..b` `` を書いたため、シェルがコマンド置換として実行し、ジョブが起動せずに待ちループだけが残った（発見まで1巡分の時間を失った）。
- **型**: シェル経由で渡す長文はシングルクォート/ファイル渡しにするか、バッククォート・`$(`・`$var` を含めない。起動直後に**ジョブのメタ（開始記録）が存在するか**を必ず確認してから待つ。
- **出典**: 2026-08-23 のレビュージョブ起動失敗

## レビューの「強化案」は脅威モデルに照らして採否を決める（同じ受け手が既に見ている情報を隠す層を足さない）

- **事象**: 回答後の帰属呼び出し（同じクラウド LLM へ digest＋回答を送る）に対し、レビューで「生 doc_id/パス/CID を別名化し、残存検査で漏れを止める」提案があった。採用したところ、別名の境界・同名・連鎖・日本語直結・残存検査の誤検知…と4巡にわたり指摘が増殖し、帰属が過剰にスキップされる副作用まで出た。実際には送信先はツール結果として**既に原文・パス・CID を全部受け取っている同じモデル**で、隠す意味がなかった（秘密は既存の redaction で十分）。
- **型**: 是正を採る前に「誰から何を守るか」を一文で書く。受け手が既に同じ情報を得ている経路（同一 LLM・同一セッション）に対する匿名化/難読化は採らない。閉域 LAN 前提も同じ判断軸。レビューが手直し要求を繰り返すときは、是正の積み増しではなく**層そのものの必要性**を疑う。
- **出典**: 2026-08-24 の設計変更（複数回のレビューを経て別名化層を撤去）


## アドホック検証スクリプトは実DBに素通しになる（検証も pytest の分離の中で）

- **事象**: サブエージェントが動作確認のために heredoc の python スクリプトで store 層を直接呼んだところ、pytest の `conftest` にある DB 分離（`sherpa_test` への差し替え）を通らないため、**実 dev DB に書き込んでいた**（テストユーザー・API キー）。後始末はできたが、hash-chain 付き監査台帳には消せない行が残った。
- **型**: 「ちょっと確かめるだけ」の直接実行は分離境界の外にいる。検証コードは必ず pytest のテストとして書いて実行する（分離 fixture の中で動く）。素の python から store/API を叩く場合は、接続先が `sherpa_test` であることをスクリプト冒頭で assert する。委譲契約にもこの1行を含める。
- **出典**: 部品API の実装作業（2026-08-24・復旧済み）

## サブエージェントはテストをバックグラウンド起動して停止しない（再開契機が消える）

- **事象**: 複数の並行作業で、サブエージェントが長いテストスイートをバックグラウンド起動し「完了通知を待つ」と報告して停止した。サブエージェント自身の停止後は通知を受け取る主体がいないため、コーディネータが気づいて再開指示を送るまで作業が無期限に止まった（同日中に3回発生）。
- **型**: テストは常にフォアグラウンド（timeout 付き）で一発完走する。枠が塞がっているときは pgrep の実プロセス確認＋sleep ループで**同一ターン内で**待つ。バックグラウンド化と「通知待ちでの停止」は禁止。委譲契約にこの1行を含める（「10分級前提で一発完走」の具体化）。
- **出典**: 2026-08-27（3回の停止をコーディネータの働きかけで再開）
- **追記（2026-08-28）**: 停止の直接原因は「意図的なバックグラウンド化」だけでなく、**Bash の上限（590秒）を超えた実行が harness により自動でバックグラウンド化される**ことだった（長い待機ループも同様）。型の具体化: 1回の pytest は 590 秒以内に収まるよう対象を分割（unit 2〜3分割・api 3分割）し、待機ループも 540 秒以内で自己終了させて繰り返す（`for i in $(seq 1 18); do pgrep … || break; sleep 30; done`）。委譲契約にはこの分割規律まで書く。

## テストの並走可能化は、関わる全資源の分離可能性を洗ってから範囲を決める

- **事象**: 作業単位ごとの PG DB（`sherpa_test_<lane>`）と2スロット制を導入し「2つまで並走可能」として実装したが、レビューで tests/api を含む多くのテストが固定 world `pytest-v1` で Neo4j/ES を共有しており（`tests/_world_setup.py::ensure_v1`）、各 pytest session 終了時に同じ world の Neo4j/ES を削除する（`tests/conftest.py`）ことが判明した。PG だけ分離できていても、一方の作業が他方の実行中 world を消せるため2スロット制は安全ではなかった。
- **型**: 一部の資源（この場合 PG）を分離できたからといって並走できると早合点しない。関わる全資源（PG・Neo4j・ES・`data/derived` 等）それぞれの分離可能性を洗ってから並走範囲を決める。分離できる資源は作業単位ごとに用意して「毎回クリーンな状態で走る」用途に使い、固定 world 等で分離できない共有資源が1つでも残るなら、並走の入口全部を単一のグローバルロックで直列化する（部分的な分離を並走の根拠にしない）。
- **出典**: 2026-08-30〜31 の実装→2026-09-01 の追加実装。最初の実装時点では PG のみ作業単位別 DB（`sherpa_test_<lane>`）で、固定 world により Neo4j/ES が共有のままだったため3入口を単一 flock で全直列化した。追加実装で `SHERPA_TEST_WORLD_ID=pytest-<lane>` 注入により Neo4j/ES も作業単位別 world に分離し、**全資源の分離が揃った時点で初めて**単一ロックを撤廃して作業単位別ロック＋共有2スロットの並走へ移行した（型のとおり「部分的な分離では直列化・全分離で並走化」を段階どおり実行した実例）。
