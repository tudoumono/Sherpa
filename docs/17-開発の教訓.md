# 開発の教訓

> 位置づけ: **現役（参照）**。一般化できる開発の教訓を1箇所に溜める（決定 2026-08-22）。
> コードコメントには「現在の仕様・不変条件・非自明な理由」だけを残し、修正の経緯・レビュー番号・実装日は
> Git/PR を基準とする（コードコメントの運用規約）。
> 形式: 1教訓＝1節（事象 → 型 → 出典）。固有の経緯・障害の詳細は書かない（Git を辿る）。
> 書き方: **見出しと型は一般論で書く**（このプロジェクトの部品名・関数名・道具名・製品名を使わず、別の案件・別の作業で読んでも「自分の作業にも当てはまるか」を判断できる言葉にする）。**事象は事実をそのまま書いてよい**（どのプロジェクトのどこで、何が起き、どう見つかったか。部品名・数字も可。ただし実環境の固有名は書かない）。ファイルや関数の場所は「出典」に置く。似た作業（合流・試験・縮退の設計・説明文書の更新など）を始める前に、見出しを流し読みして当てはまるものを確かめる。

## 載せ方（学びは全部載せる）

見つけた学びは全部載せる（取捨はしない）。次の 4 問は、載せるかどうかを決めるためではなく、**書き方を整えるための確かめ**に使う。

1. **別の場所で再発しうるか** — 見出しと型を、別のモジュール・別の機能・別の案件でも当てはまる言葉で書けているか。
2. **気づきにくい点が書けているか** — コードや git log を普通に読んでも気づきにくい所（ライブラリの暗黙の仕様・環境の性質・直感に反する挙動）を事象に書く。
3. **行動が変わる「型」を書けるか** — 「〜する時は〜せよ」という命令形の 1 文にする。まだ落ちないときは、事象だけでも載せ、型は後で足す。
4. **今も有効か** — 解消済みの一回性の事象でも、型が今も通じるなら載せる。型も通じなくなった節は、消さずに見出しに「（今は不要）」を付ける。

追記のタイミング: レビュー完了時・障害対応完了時に「教訓に載せる型はあるか」を1回問う。

## 外から来る上限値は、範囲に収めてから使う（負の値でスライスが反転し、上限が消える）

- **事象**: 上限値の env に負値を渡すと `calls[:-1]` のようにスライスが反転し、「末尾1件を除いて全部通す」＝上限が実質無効になった。
- **型**: 外部入力（環境変数・設定値）を上限・範囲・スライスに使うときは、必ず `[lo, hi]` に収める共通の関数を通す。既定値もその関数に通す（動的に決めた既定値が上限を素通りした前例がある）。
- **出典**: `sherpa/env_int.py::env_int`

## 関数の既定引数は定義した時点で値が決まり、試験での差し替えが効かない

- **事象**: 上限定数を関数のデフォルト引数値にすると、テストの `monkeypatch.setattr(module, "CAP", …)` が効かない（def 時に値が固定済み）。
- **型**: 試験で差し替えたい定数は、既定引数に置かず、**関数の本体でモジュールの属性をそのつど読む**。
- **出典**: `sherpa/ingest/ooxml/excel.py`（`DEFAULT_CAP_ROWS` 等の参照方式）

## 並列実行のワーカーが、異常時にプロセスの終了を塞ぐ

- **事象**: 並列化に使った ThreadPoolExecutor のワーカースレッドが非 daemon のため、例外経路でプロセスが終了しない・残留する。
- **型**: 並列実行を入れるときは、異常時にも回収される終わり方（停止の呼び出し・時間切れ・デーモンにするか）を先に設計する。
- **出典**: 取り込みアーム並列化（コミット 32d83cb 前後）

## ライブラリの軽量モードは、何を捨てるかを確かめてから使う

- **事象**: `read_only=True`（ストリーミング読み）では `merged_cells`／`row_dimensions`／セル単位 `hyperlink`・`comment` が取れない。
- **型**: ライブラリの「軽量モード」「高速モード」は、何を捨てるかを必ず確かめる。必要な情報と引き換えになるなら、通常モードの費用（メモリ・2 回読み）を払うと明示的に判断し、その判断をコードの説明に残す。
- **出典**: `sherpa/ingest/ooxml/excel.py`（`load_two` の設計判断）

## ラッパー越しの検証は、ラッパー自体が結果を汚す

- **事象**: 外部 CLI をサンドボックス／バックグラウンド経由で検証したところ、ラッパーの交絡で「壊れている」と誤結論しかけた。
- **型**: まず「素で動く呼び出し方」を確立する → 変える条件を 1 つずつにする → 成果物は別のプロセスから観測する → 「壊れている」と結論する前に対照実験（動く例を同じ手順に通す）を挟む。
- **出典**: 開発リポジトリ内部の調査記録（2026-07-01）

## レビューで、実在しないコードを指摘してしまう

- **事象**: レビューで、実在しないコード片を問題として「発見」しかけた。
- **型**: 指摘の裏取りは、ファイルを直接読んだ結果や版管理の出力など、実物を見た結果だけを信じる。記憶・要約・他のエージェントの報告からコードを引用しない。
- **出典**: 開発リポジトリ内部のレビュー記録（2026-07-13）

## 安全の検査を 1 か所に集めても、後から足した経路が素通りする

- **事象**: URL 検証等をチョークポイント関数に集約しても、後から足した新設シンク（サブループ等）が素通しし、SSRF の穴が再発しうる。
- **型**: 「必ずこの関数を通る」という決まりはコメントで契約として書き、新しく足した経路をレビューするときの観点に含める。できれば、関所を通らずに直接呼んでいる箇所を試験で検出する。
- **出典**: `sherpa/llm.py::assert_ollama_url_allowed`

## 共有の資源を使う試験は、関わる資源を全部分離できるまで並べて走らせない

- **事象**: (1) `tests/api` 等（共有 dev PostgreSQL 利用）を2本同時に走らせると `audit_log` で deadlock し、無関係なテストが落ちた（偽失敗5件）。 (2) 作業単位ごとの PG DB（`sherpa_test_<lane>`）と2スロット制を導入し「2つまで並走可能」として実装したが、レビューで tests/api を含む多くのテストが固定の資料フォルダ `pytest-v1` で Neo4j/ES を共有しており（`tests/_world_setup.py::ensure_v1`）、各 pytest session 終了時に同じ資料フォルダの Neo4j/ES を削除する（`tests/conftest.py`）ことが判明した。PG だけ分離できていても、一方の作業が他方の実行中の資料フォルダを消せるため2スロット制は安全ではなかった。
- **型**: 一部の資源（DB など）を分けられたからといって、並べて走らせられると早合点しない。関わる資源（DB・検索エンジン・グラフ DB・派生物の置き場など）の**全部**について分けられるかを洗ってから、並べる範囲を決める。分けられる資源は作業単位ごとに用意して「毎回まっさらな状態で走る」用途に使う。分けられない共有の資源が 1 つでも残るなら、試験は 1 本ずつにし、並べて走らせる入口を全部 1 つの排他ロックで順番にする（部分的な分離を並べる根拠にしない）。作業を任せるときも「始める前に、同じ資源を使う試験が走っていないか確かめる」を指示に含める。
- **出典**: (1) 開発リポジトリ内部の引き継ぎ記録（2026-08-21）§3 (2) 2026-08-30〜31 の実装→2026-09-01 の追加実装。最初の実装時点では PG のみ作業単位別 DB（`sherpa_test_<lane>`）で、固定の資料フォルダにより Neo4j/ES が共有のままだったため3入口を単一 flock で全直列化した。追加実装で `SHERPA_TEST_WORLD_ID=pytest-<lane>` 注入により Neo4j/ES も作業単位別の資料フォルダに分離し、**全資源の分離が揃った時点で初めて**単一ロックを撤廃して作業単位別ロック＋共有2スロットの並走へ移行した（型のとおり「部分的な分離では直列化・全分離で並走化」を段階どおり実行した実例）。

## 作成物ごとのレビューを省くと、実害のある欠陥が残る

- **事象**: 作成物ごとの Codex によるレビューで、毎回、実害のある欠陥が検出されている（設定保存の焼き付け・出荷ゲートの素通り・base URL 検証の迂回 等）。
- **型**: レビューは作成物ごとに必ず行う。ただし指摘は無条件に飲まず、今の実装・試験・公式の仕様で裏を取り、採るか採らないかを理由付きで決める。
- **出典**: 開発リポジトリ内部の引き継ぎ記録（2026-08-21）§4

## 外部 API が正常な応答にも付ける「注意の欄」を、失敗と取り違える

- **事象**: Azure OpenAI は正常応答にも `content_filter_results`（`filtered: false`）を必ず付けるため、フィールド名の存在だけで判定した検査が成功を NG にした。
- **型**: 外部 API の検査は「欄があるか」ではなく「値が何を意味するか」で判定する。判定の条件は、公式の仕様の該当箇所と対にして書く。
- **出典**: `scripts/azure_smoke.py`

## 読み込みの時点で環境変数を読み切る定数は、試験ごとの差し替えでは制御できない

- **事象**: `sherpa.llm` の URL 定数のように「import 時に一度だけ env を読む」値は、per-test の monkeypatch/autouse fixture では手遅れ（既に束縛済み）で、開発機の実 env がテスト結果を変えていた。
- **型**: 環境変数から作るモジュールの定数を制御したい試験は、**試験の収集が始まる前**（試験全体の初期化ファイルのモジュールの最上位）で環境変数を正規化する。試験ごとの差し替えは、その上に重ねる二重の守りにする。
- **出典**: `tests/conftest.py`（セッション開始時の AI 系 env 一括除去）・`tests/_ai_env_isolation.py`

## 未設定時の既定値が実環境の秘密を指す環境変数は、消しても隔離にならない

- **事象**: `CODEX_HOME` を delenv すると、コード側フォールバックが `~/.codex`（開発機の実 `auth.json`）を指し、むしろ実機密を参照してしまった。
- **型**: 未設定時の既定値が実環境の状態・秘密を指す環境変数は、消すのではなく**実在しない目印の値へ差し替える**。
- **出典**: `tests/_ai_env_isolation.py::CODEX_HOME_SENTINEL`

## エラー詳細の秘密の伏せ字は、文字数の切り詰めより前に行う

- **事象**: エラー整形が「切断（`[:400]`）→呼び出し元でマスク」の順だったため、切断境界をまたぐキーの断片が完全一致置換をすり抜けた。URL エンコードされたキーも素通りしていた。
- **型**: 秘密を含みうる文字列は「**整形 → 伏せ字（素の値＋URL エンコード形）→ 切り詰め**」の順を**1 つの安全な整形関数の中で保証**し、順序を呼び出し元に任せない。適用漏れを防ぐため、整形関数を直接呼ぶことを禁じ、安全な関数だけを入口にする。
- **出典**: `sherpa/ingest/graph_extract.py::_safe_detail`

## 「冗長に見える守り」を消す前に、それだけを単独で確かめる試験が契約かを見る

- **事象**: 呼び出し先（probe）が安全になったので呼び出し元の重複マスクを削ったところ、既存テストが失敗した——そのテストは「probe 自体が差し替えられても呼び出し元が独立に防げること」を意図的に固定する契約だった。
- **型**: 多層の守りの一層を「冗長」と判断して消す前に、**その層だけを単独で確かめる試験があるか**を見る。あれば、それは冗長ではなく契約。
- **出典**: 接続テストの caller 側 redaction を検証していたテスト（Bedrock の撤去に伴い削除済み。考え方は残る）

## 検索の索引に新しい入力元を足すときは「署名・ID・帰属・破損・上限」を最初に問う

- **事象**: 検索索引へ新ソース（サイドカーファイル）を追加した実装が、①切替フラグが鮮度署名に入らず反転が反映されない ②ソース由来 ID をそのまま `_id` にして衝突が無警告上書き ③サイドカーの帰属（どの原本のものか）未検証 ④部分破損の黙認 ⑤全読みで上限なし、の5点を一度に踏んだ（レビューで検出）。
- **型**: 索引の入力元を足すときは、最初に 5 問を確かめる。(1) 入力元の選び方に影響する**設定は鮮度の署名に入っているか** (2) **ID は名前空間で区切られているか**（外から来た ID を索引の ID にそのまま使わない） (3) 入力元が**どの原本のものかを突き合わせているか** (4) 一部が壊れていたら**ファイル単位で止めるか**（黙って一部だけ成功しない・縮退したら件数を報告する） (5) **大きさ・件数の上限**が明示の定数になっているか。
- **出典**: `sherpa/es_index.py`（SEARCH-CUT-2・`search_chunk_mode` 署名／`_rag_chunk_es_id`／`_validate_rag_chunks`）

## 検証と使用で同じ解決を 2 回行うと、その間の差し替えや実装の食い違いが抜け穴になる

- **事象**: (1) read_around が「検証時」と「open 時」に同じ優先順位解決を独立に2回呼んでおり、間に派生の世代切替が挟まると検証したファイルと読むファイルが食い違い得た（in-run ABA の変種・レビューで静的に検出）。(2) 未登録拡張子のソース到達可否で、判定側（内容判定・完全パスの `lstat`）と配信側（原本ダウンロード・dir_fd 相対で1段ずつ open）が別々にパス正規化を実装しており、`.` 要素の扱いが片方だけ緩く、判定側が「読み取り不可」扱いで通した書き方（`./blob.zzz` 等）を配信側は実ファイルを開いて返してしまう秘匿ファイル漏洩の穴になっていた（2026-09-21・S10）。
- **型**: 検証（判定）と使用（実行・配信）が対象の**同一性**に頼るときは、解決・正規化を**1 回・1 つの関数**で行い、その結果を両方で使う（別々に書かない）。時間差（TOCTOU）だけでなく、**同じ検証の条件を 2 か所に書くこと自体**が食い違いの元になる——片方だけ後から緩めたり厳しくしたりして、またずれる。試験は、解決が正確に 1 回であることを呼び出しの記録で固定するか、両方の呼び出し元が同じ関数を使っていることを固定する。
- **出典**: `sherpa/parts/read/tools.py::_safe_doc_path`（3-tuple 契約）・`tests/unit/test_agentic_search.py::test_read_around_resolves_target_exactly_once`・`sherpa/ingest/world_graph.py::valid_rel_parts`（判定・配信の正規化を1関数へ統一）

## データ形式を戻せない共有ストアをその場で上げると、古いブランチの検証環境が壊れる

- **事象**: 共有 dev の Elasticsearch を 8.19 へ更新（データ形式も 8.19/Lucene912 に不可逆変換）した後、更新前に分岐したブランチの worktree で `make start` すると、compose が旧タグ（8.15）を起動してデータを読めず即死した（`Could not load codec 'Lucene912'`・ダウングレード不可）。
- **型**: データ形式を戻せないストアをその場で上げたら、**その変更が合流されるまで、古いブランチの起動は壊れている**と認識する。回避は「古い版のイメージ名（タグ）を新しい版へ一時的に付け替える」（ファイルを汚さず全部の作業ツリーに効き、合流後には自然に要らなくなる）か、検証の手引きへの明記。上げる作業の報告にも「まだ合流していないブランチの検証への影響」を含める。
- **出典**: `docker tag sherpa/es-kuromoji:8.19.20 sherpa/es-kuromoji:8.15.0`（2026-08-22・8.15 実体は `:8.15.0-orig` に退避）

## 上流が「一部を伏せて」返すエコーは、完全一致の伏せ字をすり抜ける

- **事象**: OpenAI の 401 は `Incorrect API key provided: AbCd1234****…****Zz99` と**キーの先頭8字＋末尾4字**を部分マスクしてエコーする。完全一致・URLエンコード形・Bearer/api-key/sk- パターンのいずれにも一致せず、キー材料12字が画面に露出した（機械テスト1,500件＋独立レビュー4巡の後、**人の実機確認1回**で発見）。
- **型**: 秘密の伏せ字は「完全一致」だけにせず、**(1) アスタリスクの列を含むトークンを丸ごと消す、(2) 既知の秘密の先頭・末尾の断片（7 字以上）を消す、(3) 伏せ字済みのトークンに隣接する短い断片を消す**、を重ねる。上流の出力の形は自分では決められない＝「どう崩れて返ってくるか」を実機で 1 度は観測する。
- **出典**: `sherpa/ingest/graph_extract.py::_mask_secrets`（`_MASKED_TOKEN_RE`／`_mask_secret_fragments`）・`tests/unit/test_graph_extract_probe_redaction.py`

## 実機で観測した秘密の断片を、契約書・コメント・試験・教訓へ「そのまま」写さない

- **事象**: 実機の 401 エラーに含まれていた**実キーの部分マスク断片**（先頭8字＋末尾4字）を、現象の説明としてエージェントへの指示・コードコメント・回帰テストのダミー値・教訓集へそのまま転記し、そのままコミット/push した（置換＝ダミー化で是正・キーはローテーション対象）。
- **型**: 観測した秘密（断片・伏せ字済み・ハッシュの一部を含む）は、記録する前に**必ず形だけ残した架空の値へ置き換える**（例: `AbCd1234****Zz99`）。「伏せてあるから安全」「一部だから安全」と判断しない。指示文・報告・コミットメッセージも同じ（エージェントは受け取った文字列をそのまま成果物に埋める）。
- **出典**: 2026-08-22 の是正コミット（`ba18253`）・`tests/unit/test_graph_extract_probe_redaction.py` のダミー値

## 文字列の置き換えによる機械的な編集は、置き換えた件数を確かめてからコミットする

- **事象**: `str.replace` 前提の機械編集で、対象文字列が想定とわずかに違い**置換0件のまま**「ok」を表示してコミットした（他ファイルの変更と同じコミットに乗ったため `nothing to commit` にもならず、台帳の追記が3回分欠落していた）。
- **型**: 置き換えの編集は「置き換えた件数が 1 以上」を確かめ、編集後に検索や差分の統計（`grep`・`git diff --stat` など）で対象のファイルが実際に変わったことを見てからコミットする。複数のファイルを 1 つのコミットにまとめるときは、ファイルごとに差分があるかを個別に見る。
- **出典**: 開発リポジトリ内部のドキュメント整備記録（2026-08-22）#11〜13 の追記やり直し（2026-08-23）

## ストリーミングする本文に制御用のタグを混ぜない（帯域内のタグ＝漏れ・境界の不具合の元）

## 別プロセスのサンドボックスの中のファイル書き込みに契約を載せると、その版で黙って壊れる（催促の fail-open が原因を隠す）

## メモリとディスクの予算を最初に決めずに作ると、規模が上がった実環境で一度に破綻する

- **事象**: 原本 17GB（資料 7GB）・4.8 万ファイルの試験環境で取り込んだところ、メモリとディスクの両方が同時に足りなくなった。メモリでは、Web アプリが状態の問い合わせのたびに取り込みの記録を丸ごと読んで 3〜5GB に膨らみ、Neo4j と LibreOffice が OS に止められた。ディスクでは、派生物が約 28GB、埋め込みのキャッシュ（数の文字列のまま）が約 33GB に増えた。全文検索の索引も、取り込みを終えれば 100GB 以上になる見込みで、原本の約 9 倍が要る作りだった。原因は 1 つではなかった。チャンクを短く切った全件にベクトルを付けたこと、同じベクトルを 3 か所に持ったこと、同じ文字を 6〜7 か所に持ったこと、読み手のいない中間ファイル、ストアの既定の設定（元の値を残す・一時的な写しを残す・ログに上限が無い）が重なっていた。どれも手元の小さな資料では目立たず、「足りなくなったら直す」で後追いしてきた（以前にもディスク満杯の対処を一度している）。
- **型**: (1) 作る前に、**メモリとディスクの予算を設計の条件として決める**。例えば「派生物・索引・キャッシュの合計は原本の 2〜3 倍以内」「Web アプリは資料の件数に依らず一定のメモリ」など。各部品（DB・検索エンジン・グラフ・変換・OCR）には上限を割り振る。(2) **1 件あたりの大きさ × 想定の件数**を、部品ごとに最初に見積もる（チャンク 1 件・ベクトル 1 本・ログ 1 行が、本番の件数で何 GB になるか）。(3) 外部のストアは、既定の設定のままにしない。元の値を残すか、一時的な写しを持つか、ログの上限、メモリの上限を、使う前に確かめて決める。(4) 手元の小さな資料で問題が出ないことを根拠にしない。本番の件数での当てはめを、取り込みの前の見積もりと、容量の内訳を測る仕組みで、毎回確かめる。(5) 予算を超えたら取り込みを止めて知らせる（溢れて壊れる前に止める）。
- **出典**: 0.19.3〜0.19.6（2026-10-19〜22）の試験環境の取り込み。メモリの割り振り（`scripts/lib/mem_budget.sh`）、容量を調べるスクリプト（`scripts/disk_report.sh`）、取り込み前の見積もり（`sherpa/disk_estimate.py`）、ES の写しの扱いと 1 バイト化（`sherpa/es_index.py`）

## 説明・文書に書いた「こうすればよい」は、実装と突き合わせないと黙ってずれる

- **事象**: 検索の道具の説明とコメントに「続きが要るなら件数の上限を上げる」と書いてあったが、その件数は AI が渡せる引数になったことが一度も無かった（調べる深さと管理画面で決まる内部の値）。ページ送りを外す設計の判断の理由にも使われていた。ほかに、候補を切ったときは総件数を取らない実装なのに説明は「総件数を返す」と書いていた道具や、1 件の結果の上限を道具の既定値（256 KiB）で答えたが Codex の経路では 36,000 バイトに切られていた、という食い違いもあった。説明の文言を固定する試験は「文言が変わっていない」ことしか見ておらず、どれも気づけなかった。利用者が「上限に当たった後はどうなるのか」と道具を横に並べて問うまで、どの敵対レビューの範囲にも入らなかった。
- **型**: 説明・ヘルプ・設計書に「〜すればよい」と手段を書くときは、**その手段を、それを読む相手が本当に使えるか**（引数・権限・経路があるか）を確かめる。説明に出てくる引数や値が実装にあるかを機械で突き合わせる試験を置く。上限・既定値を答えたり設計の理由にしたりするときは、部品の既定値ではなく**実際に通る経路での実効値**を確かめる。設計の判断に「〜すれば足りる」と書くときは、誰がそれをするのかを書く。
- **出典**: `sherpa/agentic_search.py`（es_search・graph_resolve の説明）・`sherpa/providers/codex/usage.py`（経路ごとの結果の上限）

## 「全部は返していない」の印は、部品をまたいで 1 つの決まりにする

- **事象**: 道具ごとに打ち切りの印の形がばらばら（`truncated`・`has_more`・`candidates_total`・`count: null`）で、調査の記録と利用統計の分類は `truncated` しか見ていなかった。新しく作った名前の引き当ての道具は、近い名前の候補を上限で切ったことを別の欄（総件数）でしか示さず、調査の記録では「見つかった」と数えられていた。
- **型**: 打ち切り・省略・未確定を示す印は、**部品をまたいだ 1 つの決まり**（名前・意味・どう数えるか）にする。新しい部品はその決まりに合わせ、集計する側は決まりの印を全部見る。「切ったのに印が立たない」境界（上限ちょうど・別の欄だけで示す）を試験で固定する。
- **出典**: 大改修の `sherpa/parts/read/name_lookup.py`・`sherpa/mcp_coverage_outcome.py`・`sherpa/tool_call_log.py`（`candidates_truncated`）

## 「1 件でもだめなら全部をやり直す」縮退は、小さな試験データでは効いて見え、実データでは高速化を丸ごと無効にする

- **事象**: 一覧の道具を「台帳から出す（資料フォルダを歩かない）」に直したが、台帳の行が 1 行でも名前から種類を補えないと台帳を丸ごと諦めて資料フォルダを全部歩く作りだった。開発用データでは全行が補えるので効いて見えたが、試験環境では補えない行が 1 万件余りあり、一覧のたびにネットワークドライブの約 15 万ファイルを歩いて 20 秒かかっていた。直しは入っていたのに、どの経路を通っているかを試験環境で測る道具（回答の時間の調べ）を流すまで分からなかった。
- **型**: 速い経路から遅い経路へ倒れる縮退は、**倒れる単位を 1 件ごとにする**（だめな分だけを別に扱い、全体は速い経路のまま）。全体を倒すときは、倒れたこととその理由を数えて出す。高速化は「実データで本当に速い経路を通っているか」を、件数の多い実環境で測ってから効いたと言う。
- **出典**: `sherpa/doc_ledger.py::listing_documents`・`scripts/slow_turn_report.py`（一覧の出し方）

## 試験の中でプロセス共有の資源を作り直すときは、設定を戻してから作り直す

- **事象**: DB の接続プールを「1 本・待ち 1 秒」に絞って再現する試験が、後片付けで、環境変数を戻す前にプールを作り直していた。そのため 1 本のプールが同じプロセスの後の試験へ残り、API の試験が 170 件近く `PoolTimeout` で落ちた。その試験だけを流すゲートでは並びの関係で出ず、ほかの線と合流した形で全部を流したときに初めて出た。
- **型**: 試験の中で接続プール・キャッシュ・シングルトン・環境変数など**プロセスで共有するものを変えたときは、設定を元に戻してから資源を作り直す**（後片付けの順を決めて書く）。共有のものに触る変更は、ほかの変更と合わせた形で、同じプロセスで続けて流すまで「通った」と言わない。
- **出典**: `tests/api/test_outbox_delivery.py`（大改修・配送待ちの試験）

## 版管理の合流の衝突は、衝突した所だけを解く

- **事象**: 合流の衝突を解くとき、衝突したファイルを `git checkout --ours` で自分の側に丸ごとそろえたため、同じファイルの別の箇所に自動で入っていた相手の直しまで消えた（試験で気づいて衝突を作り直した）。別の合流では、衝突で止まったのに後ろにつないだ片付けのコマンド（ブランチの削除）まで走った。台帳の衝突を解いた後に、3 方式の区切りの印（`|||||||`）が残ったこともあった。
- **型**: 衝突は**衝突した区切りの中だけを解く**（ファイル丸ごと片側を採るのは、そのファイルに自動で入った変更が無いと確かめたときだけ）。解いた後は、使っている衝突の表し方の印が全部消えたかと、相手の変更の目印が残っているかを確かめる。合流と片付けは 1 つのコマンドにつながず、合流が終わったことを確かめてから片付ける。
- **出典**: 大改修への合流（2026-11-08）の手順
