# 20-開発ハーネス.md — 開発の型

> 位置づけ: **正典（開発の型）**。Sherpa の開発（本体・フォーク先とも）はこの型で行う。用語や構成は
> `CLAUDE.md` の振る舞い契約に従属し、取り込み／画面／グラフの正典（[03-鏡モデル.md](03-鏡モデル.md)・
> [04-画面の原則.md](04-画面の原則.md)・[05-グラフ語彙.md](05-グラフ語彙.md)）と矛盾する場合はそれらが優先する。

この文書は「何を作るか」ではなく「どう作るか」を定める。設計判断が必要なときは提案書（設計の裁定をまとめた
文書）を書き、実装は本書の型（提案→スライス→委譲→検収→敵対レビュー→ゲート→マージ→現在地への追随）で回す。

## 1. ループ（開発の型）

| 段 | 入力 | 出力 | 完了条件 |
|----|------|------|----------|
| 提案書 | 課題・要望 | 設計の裁定を表にした文書（状態行つき・「やらないこと」「リスク」「変わった前提」の節を持つ） | 裁定が番号付きで確定し、矛盾する既存記述との関係が明記されている |
| スライス | 提案書の1区画 | 1本＝1委譲の作業単位（受け入れ条件つき） | 対象ファイル・受け入れ条件・やらないことが1つの依頼文に収まる |
| 実装 | スライスの依頼文 | 差分（コード・文書・テスト） | 受け入れ条件のコマンドが期待どおりの結果を返す |
| 検収 | 差分 | 承認またはやり直し指示 | diff を読み、意図どおりか・スコープを超えていないかを確認する |
| 敵対 RV | 差分・前提・意図の要約 | 指摘の一覧（分類つき）＋クローズ可否 | 1巡以上を実施し、未処理の指摘がゼロになる |
| 是正 | 採用済みの指摘 | 最小差分 | 指摘した契約違反・データ破壊・セキュリティ上の問題が解消している |
| ゲート | 変更内容 | テスト実行の結果 | 該当する段階のゲートが緑 |
| マージ | 緑のゲート | 統合された変更 | ブランチが本流に入る |
| 現在地への追随 | マージ済みの変更 | 現在の実装状態を記す文書の更新 | 実装済み・未着手の記述が実装と一致する |
| 変わった前提 | 実装で分かった事実 | 短い1節 | 前提が変わっていなければ「変化なし」と明記する |

各スライスを終えるたびに「この実装で変わった前提」を1節書く。次のスライスの依頼文を書く前に、元の提案書の該当箇所を
読み直し、次の3点を確認する。

- 実測値が前提を覆していないか。
- 作ったものが後続のスライスを不要にしていないか。
- 既存の仕組みがすでに上位互換で、新設が重複でないか。

前提を撤回・差し替える場合は理由を添えて記録する（理由抜きの書き換えはしない）。

## 2. 役割と入出力

| 役割 | 実体 | 入力 | 出力 | 使う場面 |
|------|------|------|------|----------|
| 立案・契約管理・検収 | メインセッション | 課題・提案書 | スライスの依頼文・diff レビューの可否 | 常時。委譲は行わない工程 |
| コーディング実装 | `feature-implementer`（既定モデル） | self-contained な依頼文 | コード差分・テスト | 方針が決まったスコープ限定の実装 |
| 軽微・機械的な作業 | `light-task-runner`（軽量モデル） | 明確な置換・棚卸し依頼 | 機械的な差分・一覧 | 設計判断を伴わない文言修正・列挙・小さな置換 |
| 文書作成 | `doc-writer`（既定モデル） | 内容の方向性が決まった執筆依頼 | 文書差分 | 提案書・設計文書・マニュアルの執筆・改稿 |
| 設計判断が濃い例外 | 上位モデル | 通常の委譲では判断がつかない依頼 | 差分・判断根拠 | 迷ったら軽い役割から試し、届かない場合のみ使う（使った場合は理由を報告する） |
| 敵対レビュー | Codex CLI または Claude の `adversarial-reviewer` | 対象範囲・前提・正典・意図の要約・RV 台帳 | 指摘一覧（分類つき）＋クローズ可否 | マージ前の敵対 RV |

敵対レビューの出力形式は固定する。指摘は 1 件ごとに `[高/中/低] ファイル:行 — 症状 — 再現 — 最小修正` の 1 行、
末尾に「クローズ可」か「要修正」のどちらかを必ず書き、指摘が無いときは「指摘なし」と明記する（場所・再現・
最小修正の無い一覧はこの型に適合しない）。

役割は実体（どのツール・モデルで動くか）ではなく入出力の契約で決まる。敵対レビューは実装を2つ用意し、どちらを
使っても同じ入出力契約（後述 §3）でクローズまで完了できることを条件とする。

委譲の依頼文は次を必ず含める self-contained な形にする。

- 対象: リポジトリ・ブランチ・触ってよいファイル・触らないファイル。
- 既存規約: コメント規律・命名・構成上の制約。
- やること: 番号付きの手順。是正の場合は指摘ごとに意図を添える。
- テスト: 新規・変更するテストと実行コマンド。
- 受け入れ条件: 実行するコマンドと期待する結果。
- やらないこと: スコープ外を明記する。
- 報告項目: 変更ファイル・実行した検証コマンドと pytest 要約行と終了コード・迷った点。スモーク/サンプル実行の
  数値は SMOKE と明記する。メインは報告を根拠にせず、該当ゲートを自分で再実行してから検収する（並列レーンの
  型は `.claude/skills/lane/`）。
- 実行の作法: テストは同期実行で走り切らせる（待機目的の no-op 呼び出しを禁止）・再委譲を禁止する・pytest は1本ずつ実行する。

対象ファイルが重ならなければ複数の委譲を並行して走らせてよい。委譲・テストは十分な時間見積もりのもとで一発完走
させる前提とし、細切れの待ちやポーリングはしない。

## 3. 敵対レビュー（RV）

マージ前に敵対レビューを最低1巡実施する。クローズ条件は「指摘なし」、または残る指摘がすべて受容記録になって
いることのいずれかである。目安は数巡だが上限ではなく、超えてよい。コード・文書・画面など、作成物ごとに行う。

レビュアーには次の前提を定型で渡す。

- 実行環境は閉域 LAN、利用者は最大 20 人程度、単一 worker で動く。

この前提のもとでセキュリティ指摘の採否を判断する。採用を維持するのは、認証・認可、利用者間の情報分離、秘密の
非漏出、データ整合性、失敗を成功として表示しないこと、無期限の停止や資源枯渇の防止。逆に、サーバローカルの
攻撃者を前提にした強化やインターネット公開向けの強化は受容記録に回す。判断に迷ったら「正しさの問題として
言い換えられるか」を基準にする。

指摘は次の3分類で扱う。

| 分類 | 該当する指摘 | 扱い |
|------|--------------|------|
| 採用 | 契約違反・データ破壊・セキュリティ（上記の脅威モデルで） | 最小差分で是正する |
| 受容記録 | エッジケースの防御・表示上の粗さ・テスト強化の余地 | スコープに照らして受容記録に回すのが既定。採用するなら理由を残す |
| 却下 | 改善案（設計の好みの範囲） | 理由を残して却下する |

是正は最小にする。既存の仕組みを再利用できないか先に検討し、新しい仕組みを足す是正には代替案（仕組みを増やさず
撤去する・既存の経路へ統一する）を併記する。各スライスの最後に、増えた仕組みは何か・減らせるものはないかを見直す
簡素化の1巡を挟む。

レビュアーはこの会話の文脈を見られないため、依頼者が「ユーザーの意図・完成形の要点」を短く要約して同梱し、
品質面の指摘と意図からの逸脱の両方を見させる。

実行の作法は次のとおり。

- レビューは作業ツリーから切り離した worktree で行い、コミットされていない変更を混ぜない。
- レビュアーは対象の作業ツリーを変更しない（読み取り専用）。
- 続き実行には頼らず、毎回新規に起動する。前巡の文脈は台帳（次節）で渡す。
- 起動は `.claude/skills/rv/`（`rv` スキル）を使う。

## 4. RV 台帳

台帳は設計裁定文書（提案書）ごとに1ファイル、各リポジトリの `docs` 配下に `rv` というサブディレクトリを
設け、そこに `<対象名>.md` として置く（スライスは同一ファイル内の節で分ける。台帳は開発中の記録であり、
本体の公開版には台帳ファイル自体を含めない）。
台帳の行は次の列を持つ。

| 列 | 内容 |
|----|------|
| # | 通し番号 |
| 巡 | 何巡目の指摘か |
| 指摘の要約 | 症状の短い説明 |
| 分類 | 採用／受容／却下 |
| 理由 | 分類の根拠 |
| 是正コミット | 採用した指摘を是正したコミットの SHA。採用済みでも SHA が無い行は未処理として扱う |

次の巡のレビュー依頼には台帳を丸ごと同梱し、「受容・却下済みの項目は新しい事実がない限り再指摘しない。
再指摘するなら『台帳の該当番号に対して』と番号を付けて根拠を示す」と指示する。レビュー結果は台帳へ追記して
からマージを判断する。台帳の更新は是正コミットの**後に別コミット**で行う（是正コミットの SHA を書くため）。クローズ条件は未処理の行がゼロになること。受容記録の正本はこの台帳であり、他の場所に
分散させない。

## 5. ゲート

| 段階 | 実行するもの | 実行者 | 記録 |
|------|--------------|--------|------|
| 小修正（文言・スタイル・単一ファイル） | 該当するテストか構文チェックのみ | 実装した本人 | 実行コマンドと結果 |
| スライス完了 | `make gate-slice`（変更ファイルから該当スイートを自動選択） | 実装した本人 | 選ばれたスイートと結果 |
| マージ前 | `make gate-merge`（基本セット＝単体テスト全件＋契約テスト全件、＋変更領域の必須スイート） | メインセッション | コマンドと結果行を報告に必須で含める |
| リリース前 | `make gate-release`（フルゲート＝結合テスト・ブラウザ結合テスト・本番前チェック。オフラインキット検証は閉域キットを出荷するリリースだけ `VERIFY_KIT=1` で追加） | メインセッション | コマンドと結果行 |

`make gate-slice` は変更ファイルの対応表と、そのモジュールを import しているテストの逆引きの両方から
テストスイートを選ぶ（対応表だけでは共通モジュールの変更で利用側のテストが漏れる）。ただし次のいずれかを
見たら、選択を諦めて全件へ昇格し、理由を出力する。「対象なしで成功」にはしない。

- 対応表に無いファイルへの変更。
- 動的登録（レジストリ・設定キーの追加）を伴う変更。
- 設定・環境変数の変更。
- テストの削除。テスト削除は、退役した契約の明示（コミット本文に理由が書かれていること）が無ければ失敗にする。

`make gate-merge` の変更領域ごとの必須スイートは次のように対応させる。フロントエンドの変更には該当する
ブラウザテスト、取り込み・索引・世界の構築に関わる変更には結合テスト、API 層の変更には契約テストを、それぞれ
基本セットに加える。CI では基本セット（単体テスト全件＋契約テスト全件）だけを回し、領域スイートは手元
実行の証跡（コマンドと結果行）を報告に含める（`tests/api` は Neo4j/Postgres を使うテストを含み DB 要否を
機械的に仕分ける仕組みが無いため、基本セットには含めない。DB 不要な分だけ切り出す案は検討したが、ES/Neo4j
未接続下で `tests/api` 全体が接続待ちで極端に遅くなることを確認しており、マーカー付けは残課題とする）。

`make gate-merge`（`gate-ci` も同じ判定を共有する）の単体+契約テストには壁時計予算 5 分
（`SHERPA_UNIT_BUDGET_SEC`・既定 300 秒）を課す。pytest 自体が緑でも、予算を超えたらゲートは失敗として
扱う（超過分は機能追加より先に整理タスクを優先する対象になる。§6 の肥大化抑制と同じ確定値）。

コミット時の機械強制（hooks・pre-commit）は入れない。静的解析と文書ゲートは `make gate-*` と CI の中で走らせる。
CI は push・PR のたびに基本セットだけを二重確認し、赤が出たらメインセッションが直す。結合テスト・ブラウザ
結合テストは CI 化せず、手元の `make` で実行する。

赤が出たら、原因を語る前に次の2点を確認する。

1. 他のテスト実行が同時に走っていないか。
2. 作業ツリーから切り離した worktree の最新状態でも再現するか（共有 DB を使うテストは2本同時に走らせない）。

検証には3つの形がある。契約をテストで固定する・正解付きで計測する・実利用のフィードバックを得る。「実機で
数本流して通った」は配線の確認までであり、品質の根拠にはしない。受け入れ条件に「スモークで確認」とだけ書く
ことはしない。

## 6. テスト規範

**選ぶ**: 段階表（前節）に従い、毎回全件を回すことはしない。`make gate-slice` が変更ファイルから該当スイート
を選ぶ。

**新規か既存か**: まず既存のテストを走らせる。既存が赤になった場合、「契約が変わった（期待値を直す）」か
「回帰した（実装を直す）」かを明示し、どちらか片方だけを直す。新しいテストを追加するのは、実害の再現（レビュー
指摘・不具合・新しい契約）1件につき1本に限る。テストを残す前に「無いと落ちる」ことを確認する: 新しいテストを
残したまま対象の実装修正だけを一時的に戻して赤になり、実装修正を復元して緑になること（テストの方を外しても
修正済み実装では緑のままなので、逆向きの確認は意味を持たない）。実装の内部（呼び出し回数・内部関数名）は固定しない。

**肥大化の抑制**: 単体テスト全件の壁時計時間の上限は 5 分（確定値・目安ではない）。超えたら機能追加より先に統合・
削除を優先する。同じ形のテストはコピーせずパラメータ化する。退役した契約のテストは、その契約を撤去した
コミットで一緒に消す（退役した概念が復活しないことを確認する回帰テストだけは残す）。リリースごとにテストの
件数と、遅いテストの上位を棚卸しする（`make test-inventory`）。

**モックの規律**: モックを許すのは外部境界だけである。具体的には、LLM API、外部エージェント CLI の偽実行
ファイル、ブラウザ側の API モック、テスト用コーパスに限る。ファイルを扱うテストは一時ディレクトリ上の実物を
使い、データベース・検索エンジン・グラフストアは結合テストで実物を使う。禁止するのは、試験対象そのものの
置き換え、内部関数の monkeypatch による経路の強制、実装をそのまま写したモック、テストを通すためだけの
環境変数トグルである（どうしても必要な場合は撤去の期限を決めて残タスクに記録する）。敵対 RV の確認項目に
「テストが契約を固定しているか」「モックが境界に置かれているか」を含める。

## 7. 変更の分類（費用と場所）

実環境での試験期間中は、埋め込み・変換の再実行を誘発する変更（外部 API の費用が発生する変更）をブランチで
隔離し、試験結果を得てから本流への合流を判断する。該当するのは、人間向け・検索向けの変換結果の内容や書式、
変換の版を表す署名、埋め込みキャッシュのキーや形式、チャンク分割の変更である。費用が発生しない改善（クエリ側
のロジック・画面・ツール・文書）は本流で継続してよい。

グラフや台帳のスキーマの版を上げる変更は全件の再構築（時間はかかるが費用はゼロ）を誘発するため、規模が大きい
場合は着手前に一言添える。

費用が発生する計測（実 API を使うベンチマーク等）は、都度、上限額を決めたうえで事前承認を得る。

## 8. 作業の作法

- 作業は worktree で分離する。複数のエージェントが同じチェックアウトで同時に作業しない。検証とマージ判断は
  切り離した worktree で行う。
- Agent の worktree 隔離は `origin/main` を基点に作られるため、ローカル main を push していないと基点が古くなる。
  `scripts/git-hooks/post-checkout`（`make hooks` で有効化・clone ごとに 1 回）が、`.claude/worktrees/agent-*`
  の初回チェックアウト時に基点をローカル main へ揃える。レーン指示にも「着手前に `git merge-base main HEAD`
  を確認」を入れ、マージ前に基点を検査する（二重防御）。
- Claude Code のフックで基点確認と機密の端末印字禁止を機械化する。`scripts/claude-hooks/session-start.sh`
  （SessionStart）が起点・未コミット状態・worktree 一覧・ポート状況を1画面で出し、
  `scripts/claude-hooks/deny-secrets.sh`（PreToolUse・matcher `Bash`）が `.env` 系ファイルの表示・
  `printenv`／引数無し `env`・機密名の変数展開を機械的に拒否する（exit 2）。`.claude/settings.json` は
  gitignore 済みのため、clone ごとに以下を追記する。

  ```json
  {
    "hooks": {
      "SessionStart": [
        {
          "hooks": [
            { "type": "command", "command": "bash scripts/claude-hooks/session-start.sh" }
          ]
        }
      ],
      "PreToolUse": [
        {
          "matcher": "Bash",
          "hooks": [
            { "type": "command", "command": "bash scripts/claude-hooks/deny-secrets.sh" }
          ]
        }
      ]
    }
  }
  ```
- 実装状態を記す文書のチェック欄は実装に遅れることがある。状態を語る前にコードで確認する。
- 専門用語は判断を仰ぐ前に例で噛み砕く。コスト・規模・影響は明示する。「動かなくなる」のような主張はコードで
  裏を取ってから書く。「不要」「大きすぎる」「コストが高い」という指摘を受けたら、縮小する方向で検討する。
- 1つのテーマ・1つのユースケースへ過学習させない。複数の観点（レンズ）で検証する。
- コメント規律: コードコメントには現在の契約・不変条件・非自明な理由だけを残す。修正の経緯・レビューの番号・
  実装日は Git の履歴へ、他の場面でも再発しうる一般的な教訓は [17-開発の教訓.md](17-開発の教訓.md) へ書く。
- 秘密（鍵・パス・本文）はログにも報告の文言にも出さない。エラーは型と番号だけを記録する。

## 9. フォーク先での使い方

フォーク・クローンすると `CLAUDE.md`、本書、エージェント定義、`.claude/skills/rv/`（rv スキル）、
`.github/workflows/ci.yml`（push・PR ごとの CI）も同梱される。敵対レビューの
実装は環境にあるものを使い、外部エージェント CLI が使えない環境では Claude 実装のレビュアーを選ぶ。フォーク側
が拡張してよい面の詳細は [21-拡張の契約.md](21-拡張の契約.md)（触ってよい面／触らない面・命名・版署名・
`make verify-extension` の使い方）を参照する。入口は [EXTENDING.md](../EXTENDING.md)（リポ直下）。
配置と命名だけは本書で確定している。

- 拡張部品（アナライザ・頭脳 provider・変換アーム・MCP ツール）は本体と同じ場所に置く。別ディレクトリへの隔離は
  しない。
- ファイル名と登録名に自組織の接頭辞を付ける（例: `myfw_java_analyzer.py`・登録名 `myfw:java`）。接頭辞の無い
  登録名は本体の予約とみなし、フォーク側では使わない。
- 版署名は部品ごとに持つ（本体側の版上げでフォーク部品の署名部分が変わらないため。world 全体の再構築は現行どおり起きる）。

公開リポの更新はリリースの区切りで行う。①`CHANGELOG.md` の `[Unreleased]` を対象リリースの版へ確定する、
②公開 export を実行し公開 checkout へ commit/push する、③`vX.Y.Z` のタグを打ち（例: `v0.2.0`）、
`git push origin vX.Y.Z` でタグを push する（release.yml はタグ push で起動する）。フォーク側は
タグ単位で取り込む（追跡ブランチの継続 merge は前提にしない）。
