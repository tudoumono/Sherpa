# 取り込みモデル：ディレクトリの鏡（WYSIWYG）

> **位置づけ: 一次情報** — 取り込み/範囲/同一性は矛盾時に本書を優先。索引 [README.md](README.md)。

**決定 2026-06-28**（議論で確定）。本書は取り込み・範囲・同一性の**一次情報**であり、
旧「版（version）」中心モデルを置き換える。他の文書と矛盾する記述があれば本書を優先する。

## 0. ひとことで
> **「ここに置いたディレクトリ構造、そのまま KB（RAG＋グラフ）になります」**
利用者は**ディレクトリにファイルを置くだけ**。「版」を意識しない。KB は**そのフォルダ木の鏡**。

> **設計の核（決定2026-06-28・利用者確認）**: **保存・解析は統合／検索・表示はスコープで分離**。
> 4期更改・4期保守・5期更改は**別インデックス・別グラフに分断しない**（＝1つの統合知識領域）。
> 一方、検索・グラフ探索・AI分析時は**トップレベル領域単位でスコープを切替**えられる（全体／トップ単位／工程単位／横断比較）。
> これは**グラフだけでなく ES（全文・ベクトル・ハイブリッド）にも同様**に適用する。

## 1. 原則
1. **登録ディレクトリ全体＝1つの世界**（1グラフ＋1 ES インデックス）。例の `4期更改／4期保守／5期更改` は**全部つながった1世界**。
2. **範囲（scope）＝フォルダ木そのまま**。**どの階層でもフィルタ**でき、その部分木を1つの世界として検索/分析できる（`4期↔5期の関係`も `4期更改/03_開発だけ`も）。**グラフも ES も同じフィルタ**。
3. **即反映（ライブ鏡）**：[取り込み開始]で **更新＝置換／削除＝消える**。draft/公開ゲートは**なし**。
4. **「版」はアプリ概念から撤去**。世代は**トップフォルダ**で表現。**履歴・差分は Git**（検討事項・§6）。
5. **ブラウザ投入＝個人領域(workspace)のみ**（grep のみ・RAG 索引化しない不変条件）。**共有 KB は「ディレクトリを指す」だけ**。

## 2. 同一性とリンク（影響分析の芯）— 設計レビューで具体化
複製は**普通に起きる**前提（同じソースが複数フォルダに実体で存在しうる）。ゆえに「同名＝同ノード」を**大域では採らない**。

**用語**: `world_id`＝登録ディレクトリID／`rel_path`＝登録 root からの POSIX 相対パス／`generation`＝`rel_path` の第1セグメント（例 `4期更改`）。

### 2.1 canonical_id（`@版` を廃止）
- **ファイル由来＝パス同一性**（複製は別ノード）:
  - `module:{world_id}:{rel_path}#{PROGRAM-ID}` ／ `copybook:{world_id}:{rel_path}#{NAME}`
  - `dataitem:{world_id}:{rel_path}#{qualified-item}` ／ `batch:{world_id}:{rel_path}#{JOB}` ／ `document:{world_id}:{rel_path}`
- **業務/意味概念＝`generation`+名前でまとめる**（path-only にすると設計書ごとの言及が全部別ノード化し `REALIZES` 橋が弱る）:
  - `parameter:{world_id}:{generation}#{NAME}` ／ `function:{world_id}:{generation}#{NAME}`
- `name_of()`（`@version` 文字列パース）は**作り直し**。

### 2.2 名前解決（COPY/CALL/EXEC PGM）— 2パス・曖昧は明示
`analyze_dir` は今「名前だけで即 node/edge 生成」だが mirror では不可。**defs→refs→resolver** 型へ:
1. `safe_files()` で全列挙（`rel_path/generation/dir` 保持）。
2. **定義収集**（PROGRAM-ID・copybook stem・JCL job・DataItem）。
3. **参照解決**（COPY/CALL/EXEC PGM）。
4. 解決順＝**同フォルダ → 上位フォルダ → その generation root 内**。**世代をまたいで線を引かない**。
5. **候補が複数なら任意選択禁止**＝`ambiguous_reference` として flag/unresolved（**誤解決は影響分析の誤検出になる**＝最大リスク）。
6. edge の `doc` 来歴は **basename でなく `rel_path`**（`document:{world}:{rel_path}`）。

> **既知の近似限界**: 静的解析だけでは COPYLIB・JCL PROC/STEPLIB・動的 CALL・同一 generation 内の多重定義は曖昧が残る → 任意解決せず flag。厳密規則は実コーパスで詰める（MVP fixture は複製なし＝素直に動く）。

### 2.3 構造エッジ と 対応エッジ（両方を1グラフに）
2種類のエッジが**同じ1グラフ**に同居し、**ビュー（フィルタ）で見え方が変わる**:
- **構造エッジ**（`COPIES/INVOKES/CONTAINS/ACCESSES…`＝コード依存）: **同一 top_scope 内で最近傍解決**（§2.2）。世代をまたがない。**影響 traversal の本体**。
- **対応/意味エッジ**（`CORRESPONDS_TO`(同名)・`references`・`inherits_from` 等）: **top_scope をまたいでよい**（4期↔5期、保守→更改フィードバック等）。**全体ビューで見え、トップ単位ビューでは相手側を非表示**。**影響 traversal には入れない**（比較・流用把握用＝融合しない）。
- 例: `5期更改_基本設計書 -references-> 4期更改_基本設計書`／`5期更改_リリース手順 -inherits_from-> 4期更改_リリース手順`。全体ビューで横断が見え、`top_scope=4期更改` ビューでは 4期更改 の中だけ。

### 2.4 言及エッジ（`DOCUMENTS` via=`mention`）— 世代をまたいでよい制度化された例外
アナライザ（不変・静的解析）が Pass1 で作る定義索引（DefItem 全体）を**辞書**として、資料文書
（`branch=="office"`・設計書/テキスト等。ソース原文 `branch=="source"` は対象外）の本文と
決定的（LLM ゼロ）に突合し、一致すれば `Document -DOCUMENTS(via="mention")-> コードノード` を張る
（[05-グラフ語彙.md](05-グラフ語彙.md) §5）。

- **`CORRESPONDS_TO` と同族**＝§2.3 の「対応/意味エッジ」に分類する。**トップフォルダ（木/世代）を
  跨いでよい**——名前一致する定義が複数世代に存在すれば、その**全世代**のノードへ張る（K5）。
  §2.2「リンク（COPY/CALL）＝同世代内の最近傍」という規律は**コード参照解決**（構造エッジ）の
  規律であり、言及エッジには適用しない。
- **影響 traversal には乗らない**（`DOCUMENTS` は元々 `_IMPACT_REL` に含まれない＝§2.3 の対応/意味
  エッジと同じ扱い）。逆引き（このファイルに言及する文書＝仕様の在り処）専用。
- 曖昧の扱いは§2.2と揃える: **同一世代内に同名の定義が複数あれば、その世代分だけ曖昧として
  張らない**（任意選択しない）。名前が短い（既定4文字未満）ものは辞書に立てない。
- 辞書突合は `DefItem.cid_key`（修飾名。トークン化は `.` で分断するため修飾名自体は突合し得ない）
  だけでなく**表示名（単純名）でも**引く（S2-LEAFNAME）。曖昧規律は単純名にも同じく適用する
  ——同一世代内で単純名が衝突する定義が複数あれば、その世代は単純名では張らない。

## 3. 範囲（scope）＝フォルダフィルタ＝メタデータ
**ディレクトリ構造をそのまま検索スコープのメタデータにする**（利用者確認）。各**ドキュメント/チャンク/グラフノード/ESドキュメント**に同じ属性を持たせる:

| 属性 | 意味（例） |
|---|---|
| `world_id` | 登録した世界（例 `project_x`） |
| `top_scope` | トップレベル領域＝`rel_path` 第1セグメント（`4期更改`/`4期保守`/`5期更改`） |
| `phase` | 工程＝第2セグメント（`01_要件定義`/`02_設計`/`03_開発`…） |
| `category` | 活動＝第3セグメント（`01_資料`/`02_議事録`/`03_成果物`…） |
| `path` | 実ファイルの `rel_path`（同一性の基底＝§2.1） |
| `version` | Git commit hash 等（§6・履歴/差分の軸） |

- **検索対象は1つ**（world 全体）。**検索時に `top_scope`/`phase` で絞る**（`AND top_scope=4期更改`、`AND top_scope IN (4期更改,5期更改)` で比較）。
- **グラフも ES も同じメタデータ・同じ絞り方**（グラフを特別扱いしない）。グラフは traversal の **Cypher 自体に `world_id + top_scope/phase prefix`** を入れる（`scope.filter_items` の「後段で絞る」から変更）。ES は同名フィルタ。
- フォルダ木が**そのまま**範囲＝`版内/工程/活動` を**推定しない**（木が真）。**auto-scope の推定・共通マーカー・要確認(scope) は撤去**。`要確認` は「壊れた取り込み（変換失敗等）」のみ。
- **ビュー例**: 全体（横断が見える）／トップ単位（`4期更改` だけ・5期は非表示）／工程単位（`4期更改/03_開発` だけ）／横断比較（`4期更改` と `5期更改` の `02_設計` を比較）。
- **設定ファイル（重要度）は鏡の一部だが文書ではない**：各フォルダに置ける重要度設定ファイル（`_重要度.txt`）も鏡の一部（フォルダ木に置く・即反映）だが文書ではない（検索・RAG・グラフ・出典・共有に出ない）。設定を削除したときは祖先の設定へ継承し、祖先にも無ければ未設定に戻る。

## 4. 同期（mirror）
- **scan**：ディレクトリを走査し、台帳・グラフ・索引を**現状に一致**させる（add/update/delete）。
- **削除伝播**：ディレクトリから消えたファイルは KB（台帳/グラフ/ES/原本派生物）からも消える。
- **storage_mode（設計判断）**：**ライブ鏡は基本 `external_reference`（参照）寄り**（2TB の鏡性優先）。`managed_copy` は snapshot/sync の意味になる。`出典=原本DL` を厳密保証したいなら `managed_copy`。**外部 root 消失時は KB unavailable として fail-closed**。
- **full rebuild は MVP の鏡として許容**：`world_id` 単位で ledger replace ＋ Neo4j delete+reload ＋ ES delete/reindex（delete も反映）。ES は alias swap か一時的 eventual consistency を明記。
- **world レジストリ＝1 world に 1 参照元フォルダ（決定2026-06-28・実装済 `store.worlds`/`worlds.py`/`/worlds` API）**:
  - **別案件＝新 world として追加**（別 world_id・既存は無傷・保存統合/検索分離）。
  - **参照先パス変更＝rebind＝その world を全削除して新パスから作り直し**（差分でなく破棄→再作成）。
    `load_world` の delete+load を**1 tx**で atomic 置換し、失敗時はロールバックで旧グラフが残り台帳/バインドも旧へ戻す（**fail-closed**）。
  - **参照元が消失/マウント不可なら world unavailable（None）**＝fixtures/旧KB へは落とさない（別内容を同 world として誤読しない）。
  - 同じ root を複数 world に二重登録しない（`UNIQUE(root_path)`・1:1）。external_reference が既定（参照元をその場で鏡）。

## 4a. 派生物の三階層（フォルダ分離・2026-09-03）
登録ディレクトリ（原本・READ-ONLY）はそのまま鏡。**派生（`data/derived/{world}/`）側は役割ごとに3層でフォルダを分ける**（各層とも原本と同じ相対パス構造＝鏡の入れ子）:

| 層 | フォルダ | 位置づけ | 読み手 |
|---|---|---|---|
| 人間用 | `md/` | 人が読む写し（画面表示・原本DL の根拠） | 利用者への提示 |
| RAG 基準 | `rag/`（`{rel}.rag.md`＋証跡 `{rel}.rag_chunks.jsonl`） | **grep・ES・グラフ（意味層）の唯一の入力** | 検索・抽出 |
| 中間 | `ir/`（`{rel}.document/evidence/derived.json` 等） | 再生成可能な中間表現 | drift 判定・デバッグのみ（検索に出さない） |

このほか意味層（Phase2 抽出）の状態は `semantic/` に別途置かれる（人の承認操作を含むため他の派生物と扱いが異なる＝[41-運用Runbook.md](manual/41-運用Runbook.md)）。
3層は独立にステージング→公開し（1層の失敗が他層の公開を止めない）、削除伝播は3層すべてに及ぶ。互換層は持たない（旧配置は「未生成」扱いとなり、次回の world 全再作成で新配置へ収束する＝§4 の full rebuild と同じ鏡の作り直し）。

## 6. Git 管理（版・履歴・差分の軸）— 利用者方針（MVP 投入時期は未決・相性良）
- **版/履歴/差分は Git が担う**（アプリに版概念を持たない）。`version=commit hash` をノード/ESドキュメントにも持たせ、**検索結果をバージョンで切替**（現在／2026-06-01時点／リリース前 等）。
- **Git 管理対象を分ける**: `documents/`（原本＝4期更改/4期保守/5期更改…）＋ `extracted/`（MD化本文・chunk・metadata・グラフ中間データ）。**AI が読むのは抽出テキスト/Markdown に寄せる**。
- **Office/PDF はバイナリ差分が弱い** → `原本→テキスト抽出→MD→chunk→ES→グラフ` の流れにし、**差分・AI分析は抽出テキスト側**で行う（原本は保管用）。
- できること: 変更履歴／**AI が Git 差分を要約**（「認証が ID/PW→OAuth」「バッチ 23:00→01:00」等）／**4期↔5期の設計比較**（変更/流用/新規/廃止の整理）。

## 9. API パラメータの語彙（version → world・2 段移行・完了）
鏡モデルは「版」概念を撤去済み。**API パラメータは `world` のみ**（クエリ/body 共通・取込ディレクトリ＝world id）。
- **第1段（実施済・2026-07-02）**: 新しい `world` を受理し**優先**する。旧 `version` も互換のため当時は受理を継続（第2段で受理終了）、
  使用時に deprecation 警告（logger `sherpa`）を出した。応答キーも `world`（旧 `/versions` は `GET /world-options`＝
  `{"worlds":[...], "labels":{...}}` に改名）。両省略時は既定 world（`worlds.default_world()`＝現状 `v1`）。
- **第2段（実施済・2026-07-13）**: `version` の受理を終了した。クエリ/body の `version` は**未宣言パラメータとして
  黙って無視される**（FastAPI/Pydantic の既定動作・422 にはならない）。第1段の deprecation 警告メカニズム自体も
  撤去済み。`world` 省略時は従来どおり既定 world に解決される（挙動不変）。
- **DB 列 `version`**（`documents.version` 等）は歴史的名称のまま**不変**（マイグレーションツール未導入・語彙統一のスコープ外）。
  コード内部の識別子・引数・応答キーは `world` に統一済（SQL 文字列内のカラム名のみ `version` を維持）。
