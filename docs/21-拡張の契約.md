# 21-拡張の契約.md — フォーク先が拡張してよい面

> 位置づけ: **正典（拡張の契約・公開）**。[20-開発ハーネス.md](20-開発ハーネス.md) §9 から参照される。
> 矛盾する場合は取り込み／画面／グラフの正典（[03-鏡モデル.md](03-鏡モデル.md)・[04-画面の原則.md](04-画面の原則.md)・
> [05-グラフ語彙.md](05-グラフ語彙.md)）が優先する。実装＝`sherpa/ingest/analyzers/registry.py`・
> `scripts/verify_extension.py`。フォークの入口は [EXTENDING.md](../EXTENDING.md)（リポ直下）。

Sherpa は会社の共通アプリとして各プロダクトがフォーク／クローンし、各自の言語・フレームワーク向けに拡張していく
方針（決定 2026-09-09）。ライセンスは許可制の source-available で改変可・上流への還流は任意（義務ではない・歓迎）。

## 1. 触ってよい面／触らない面

**核**（鏡モデル・グラフ語彙・画面の原則・認証と隔離）は自己責任で改変してよいが、上流はその互換性を保証しない。
**拡張面**（下表の5つ）だけを上流が契約テストで守る。

| 拡張面 | 登録方法 | 入出力 |
|---|---|---|
| アナライザ | `sherpa/ingest/analyzers/registry.py`（`<prefix>_*.py` を発見して登録） | ファイル → 定義/参照候補（`DefResult`/`RefResult`・閉じた型・`via` で細分を開く） |
| FW プラグイン | `sherpa/ingest/analyzers/registry.py`（`<prefix>_*.py` のモジュール属性 `FW_PLUGINS` を発見して登録） | 本体の `DefResult`/`RefResult`＋ファイルの本文・パス → 追加の定義/参照候補と `Dropped`（足すだけ・§3a） |
| 頭脳 provider | `sherpa/providers/__init__.py`（`AGENT_PROVIDERS`・`get_provider`・`provider_info`） | `Ctx` → node/answer_delta/`_result` の event 列 |
| 変換アーム | `sherpa/ingest/office_md.py`・`sherpa/ingest/arms/`（`SHERPA_ARMS`・`_arms_sig`） | 原本 → 決定的 Markdown（人間向け＋rag.md） |
| MCP ツール | `sherpa/mcp_server.py`（ツール定義列）・`sherpa/providers/codex/mcp.py` | JSON 引数 → JSON 結果（読み取り専用・範囲遵守） |

核（`ingest/world_graph.py`／`ingest/world_neo4j.py`／`worlds.py`／`scope.py`・`docs/03`〜`05`）を直接書き換えるのは
フォークの自己責任範囲——upstream はその互換性を保証しない。upstream への取り込み（§5）を考えているなら、まず
拡張面に収まらないか検討する。

**解決範囲の設定**（COPY の取り込み元の場所 `copy_paths`・パスの別名 `path_aliases`）は拡張面ではなく**核の設定**で、資料フォルダごとに管理画面で持つ
（`worlds.resolve_settings`・`ingest/resolve_settings.py`）。アナライザは設定を読まず、共通層（`world_graph` の名前解決）が使う。設定の内容は資料フォルダの署名の材料になる。

## 2. 配置と命名

- 拡張部品は**本体と同じ場所**に置く（`ext/` のような隔離ディレクトリは作らない）。
- ファイル名は `<prefix>_*.py`（例: `myfw_java_analyzer.py`）。`prefix` は英小文字・数字・`_`（先頭は英小文字）。
  次の予約語は使えない（本体の言語名／内部モジュール名と衝突するため）:
  `cobol`・`copybook`・`jcl`・`java`・`c`・`csharp`・`sql`・`js`・`jsp`・`html`・`css`・`vb`・`shell`・`xml`・
  `yaml`・`properties`・`base`・`registry`（`registry.RESERVED_ANALYZER_PREFIXES` が単一の真実源）。
- 宣言的なルールファイルは `rules_<名前>.toml`（§3c・コードを書かない FW プラグイン）。
- FW プラグインも同じ `<prefix>_*.py` に置ける（`ANALYZER` と `FW_PLUGINS` の両方を持つファイルも可）。モジュール属性は `FW_PLUGINS`（`FwPlugin` のリスト）、登録名は `"<prefix>:<fw>"`（`prefix` はファイル名の接頭辞と一致・予約語は使えない）。
- 登録名（`ANALYZER.name`）は `"<prefix>:<kind>"` の形にし、**`prefix` はファイル名の `<prefix>` と一致**させる
  （例: ファイル `myfw_java.py` なら登録名は `myfw:java` や `myfw:java_batch` 等・`myfw_` で始まっていればよい）。
  一致しなければ発見時（import 時）に `registry.ExtensionAnalyzerError` で落ちる——黙って無視しない。

## 3. アナライザの契約（本スライスの実装対象）

`sherpa/ingest/analyzers/registry.py::discover_extension_analyzers()` が `sherpa/ingest/analyzers/` 配下の
`<prefix>_*.py`（`_` 始まり・上流モジュール・`registry` を除く）を発見し、モジュール属性 `ANALYZER`
（`sherpa.ingest.analyzers._base.Analyzer` のインスタンス）を持つものだけを契約検証のうえ登録する
（`ANALYZER` を持たないファイルは拡張アナライザを名乗っていないとみなし読み飛ばす）。登録順は**名前順で末尾**
（本体の優先順の後）。

検証する契約（違反は `ExtensionAnalyzerError`・黙って落とさない）:

1. `ANALYZER.name` が `"<prefix>:<kind>"` の形で、`prefix` がファイル名の接頭辞と一致する。
2. `prefix` が予約語（§2）でない。
3. `ANALYZER.extensions` は空でない `set`/`frozenset`（型が違えば違反・黙って `TypeError` の
   traceback にしない）で、各要素は `.` + 英小文字/数字のみの単一区切り（照合側 `registry._ext()`
   ＝`PurePosixPath.suffix` が返す形に合わせる——大文字宣言や `.d.ts` のような多段接尾辞は
   永久に担当なしになるため違反）。
4. `ANALYZER.extensions` が上流アナライザの拡張子と衝突しない。意図的に共有する場合だけ
   `ANALYZER.overrides = frozenset({...})` で明示する——ただし優先順は登録順のまま変わらないため、
   共有拡張子は**上流の `accepts()` が拒否したときだけ**拡張側に回る（`registry.resolve()`/`resolve_lazy()`
   の既存規則そのまま。優先度の並び替えはできない）。
5. 拡張アナライザ同士でも `ANALYZER.name`・`ANALYZER.extensions`（**全体**・`overrides` は除かない）が
   重複しない。`overrides` による除外は項目4の**上流との衝突判定だけ**に使う——ただし同じ上流拡張子を
   両方の拡張アナライザが `overrides` で明示的に共有していれば例外として許可する。
6. `ANALYZER.version` が `int`（`bool` を含め型が違えば違反）で `>= 1`。**拡張自身のクラスで宣言する**（上流クラスを継承して省略すると上流の版を継承し、署名の独立が破れるため違反）。
7. `ANALYZER.doctype`（種別表示名）は非空の文字列で宣言する（空だと台帳と取り込み画面の種別が空文字になる＝違反）。
8. 上流の担当拡張子には**資料側の拡張子**（`.md`/`.txt`/Office/PDF 等）も含む。これらを担当するには `overrides` の明示が要る（無言で資料の分類経路を奪わない）。
9. **秘匿ファイルの拡張子**（`.env`/`.key`/`.pem`/`.ppk`）は `overrides` でも担当できない（秘匿除外が無効化され本文が外部送信へ流れるため）。
10. `ANALYZER` を持つファイルは `<prefix>_*.py` の形（ファイル名に `_` を含む）——`ANALYZER` を宣言して
   いる以上、命名規約違反を黙って読み飛ばさない（読み飛ばすのは `ANALYZER` を持たない無関係なファイル
   だけ）。

アナライザが共通層へ返す値（`_base.py`）の契約:

- **`RefCandidate.source_symbol_id`**: 参照元の定義キー `(rel_path, cid_key)`（`cid_key` は `collect_defs` が返す children の `DefItem.key`
  ＝定義ノードの cid を組む値と同じ）。省略（`None`）はファイルの主体。**`collect_defs` が children として返した定義だけを指せる**
  （指せない・自ファイルでない場合、共通層は始点を主体へ倒し `flags` に `unknown_source_symbol` を残す）。
  定義ノードの無い言語（COBOL・JS・SQL・設定ファイル系）は常に省略。メソッド・段落の抽出は契約の対象外。
  保存・外部の応答では `{"file": rel_path, "key": cid_key}`（主体は `key: null`）の形で持つ（内部の組は保存しない）。
- **定義の識別子（`DefItem`）**: `name`＝表示名（単純名）、`cid_key`＝canonical ID の識別子部分かつ解決用の修飾名（省略時は `name`）、`extra`＝ノードへ足す欄。
  表示名・解決用の修飾名・canonical ID を混ぜない。`extras`（主体以外のトップレベル定義）の `cid` は `cid_key` で組むので、同名の別定義は `cid_key` で分ける
  （SQL の別 schema の同名の表＝`SCHEMA.NAME`。解決用の修飾名は `extra["qualified_name"]`）。**既存の定義の `cid` は変えない**（外部が控えた ID・重要度の指定が参照するため）。
  C#/VB は型の識別子が既に `Namespace.Type`（children の `cid_key`）なので変えない。
  参照が schema を書いたとき、`Table` を指す `RefCandidate.name` は `SCHEMA.NAME`（`_sql_scan.table_refs`）。
- **参照ごとの所属の規則**（アナライザが決める）: その参照の行を本体に含む最も内側の定義。C＝`{` 終端の関数定義（`#include` は常に主体）。
  VB＝`Sub`/`Function`/`Property`（`Declare` は宣言行だけ）→ 主体以外のトップレベル型（`.vb`）。C#/Java＝主体以外の型。
  主体の型の直下・定義の外は主体。
- **`RefResult.file_context`**（`FileContext(package, imports)`・`ImportItem(kind, name, alias, static, line)`）: そのファイルの
  `package`／`namespace` と `import`／`using` の一覧（`kind`＝`single`・`wildcard`・`alias`）。共通層が Pass 2 の解決器（`_link`）へ渡す。
  `Analyzer.requires_file_context = True` のアナライザ（Java・C#）は常に返す。返さなければ共通層が `flags` に `file_context_missing`
  （`analyzer`・`from`）を 1 ファイル 1 件残し、そのファイルの型名の参照（`type_ref`）は辺を張らず `unresolved` として申告する。
  VB.NET（`.vb`）は `Imports` を同じ形で返す（`requires_file_context` は付けない＝VB6/VBA/VBScript は返さず、名前だけの最近傍解決のまま）。
  資料フォルダに `.vbproj` があれば、共通層（`world_graph`）が `analyzers/_vb_project.py` で読み、ソース `.vb` に最も近い `.vbproj`（同じ最上位フォルダの中だけ・旧形式は `<Compile Include>` の列挙〔`;` 区切り・プロジェクトの外も可〕に含まれるソースだけ・SDK 形式は `bin/**`・`obj/**` と `Compile Remove` を除く全部・含む候補が複数なら当てず `dropped_syntax(vbproj_ambiguous)`・読めない `.vbproj` はその場所で止める）を当てる。プロジェクトに属するソースの型・手続きは、完全修飾名の索引に本当の名前（`<RootNamespace>.<namespace>.<型>`）だけで載せ（ノードの識別子は変えない）、そのソースの参照には package・namespace に Root を含めた連鎖と、プロジェクトの `<Import Include>`（と Root つきのワイルドカード import）を足す。`RootNamespace` は `.vbproj` → 上のフォルダの最も近い `Directory.Build.props` → プロジェクト名の順。`$(…)`・`Condition`・`<Import Project>` は評価せず `dropped_syntax(vbproj_unevaluated)`、読めない設定は `vbproj_unreadable`、フォルダの外へ出る Include は `vbproj_include_outside` で申告する。`.vbproj` は資料フォルダの 1 ファイルとして署名（`worker._sig`）に入るので、変更すると取り込み直しになる。
  `ImportItem.kind` は、型名の import が `single`、名前空間・package の import が `wildcard`（Java の `import p.*`・C# の `using N;`・VB の `Imports N`・`name` は修飾部のみ）、
  別名が `alias`（修飾名の先頭でも展開し、完全修飾名として解決する）。1 ファイルに namespace が複数あるときは `FileContext.namespaces`（`(開始行, 終了行, 名前)`）で、参照の行を含む namespace を文脈にする。`static` の import（`import static`・`using static`）は型の名前を持ち込まないので解決に使わない。
- **名前解決の指示**（`RefCandidate.extra`・共通層が消費して辺には残さない）:
  `qualified`＝`name` は完全修飾名（完全修飾名の索引の完全一致だけで解決し、無ければ辺を張らず `unresolved_qualifier`・短名へ倒さない）。
  `type_ref`＝`name` は型名（参照元の `file_context` の package／namespace・import／using の規則で解決する・`docs/05` §4 の解決順）。
  `path_exact`＝`via=include` の `include_path` は相対パスの完全一致でしか解決しない（無ければ basename の最近傍へ倒さず `unresolved_qualifier`）。C の `#include "x/y.h"` が使う。
- **解決用の完全修飾名**（`DefItem.qualified`）: ノードの cid・表示名とは別に、package／namespace 込みの名前を完全修飾名の索引へ登録する（省略時は `cid_key`）。
  Java の非 public 型・VB の名前空間なしの型など、cid を変えずに完全修飾名で引かせたい定義が使う。
  `Analyzer.resolves_parent_namespaces = True`（C#・VB.NET）は、型名の解決で参照元の namespace の親・グローバルも順に探す。

### 3a. FW プラグインの契約

本体のアナライザ（言語ごとに 1 本）が 1 ファイルを 1 回だけ解析し、その結果へ**適用できる FW プラグインを `(order, 登録名)` の昇順で重ねる**。
流れは「ソース・設定 → 本体のアナライザ（1 回）→ 基本の定義・参照 ＋ FW プラグイン（複数）→ 共通の名前解決 → グラフ保存」。
実装＝`registry.py`（`FwPlugin` は `_base.py`・`FW_PLUGINS`・`discover_fw_plugins`・`applicable_fw_plugins`・`apply_fw_defs`／`apply_fw_refs`）、共通層の呼び出し＝`world_graph.build_world`（Pass 1 が定義・Pass 2 が参照）。

- **登録**: `FwPlugin` のサブクラスを `FW_PLUGINS`（リスト）に入れる。属性は `name`（`"<prefix>:<fw>"`）・`languages`（対象のアナライザ名の集合・登録済みの名前のみ）・
  `config_kinds`（適用条件・空＝種別で絞らない）・`version`（1 以上の整数・**拡張自身のクラスで宣言**）・`order`（整数・小さいほど先）。
  上流のプラグインは `registry._UPSTREAM_FW_PLUGINS`（予約語の接頭辞を使える・ファイル名の規約の外）。
- **適用条件**: ファイルを担当した本体のアナライザ名が `languages` に入り、`config_kinds` が非空なら本体の `Analyzer.config_kind(text, rel_path)`（XML のルート要素・名前空間など、アナライザが判定した設定の種別。判定しなければ `None`）がその集合に入ること。
  対象外のファイル（別の FW の設定・無関係の XML・種別を判定できないファイル）には適用しない。
- **適用順**: 本体が先。続けて `(order, 登録名)` の昇順（登録順・ファイル名順に依らない）。
- **3 つの層**: ①構文を拾う（本体のアナライザ・Tree-sitter／XML）②名前・型の解決（共通層・`world_graph`）③FW の意味（プラグイン）。②を FW ごとに作らせないため、**プラグインは名前を自分で解決しない**。参照の候補（名前・種別・`via`・行・`type_ref`／`qualified` などの解決の指示）を返すだけで、解決は共通層が `file_context` と同じ規則（`docs/05` §4）で行う。
- **入出力**: 入力は `FwPlugin.collect_defs(text, rel_path, base: DefResult)`（1 パス目）／`extract_refs(text, rel_path, base_defs, base_refs, types)`（2 パス目・`base_defs` は本体の定義でプラグインの追加分を含まない）。
  どちらも本体の結果の**コピー**が渡る。出力は `PluginDefs(children, extras, dropped)`／`PluginRefs(refs, dropped)` だけ。グラフへ直接書かず、**本体の出力を消せず、他のプラグインの出力も見ない**。
  同じ定義（種別・識別子・行）・同じ参照（辺の種別・種別・名前・行・`via`・始点・向き）は共通層が 1 件にする（本体が先・先に適用したプラグインが先）。`Dropped` は理由に `"<登録名>: "` を前置して `flags`（`dropped_syntax`）へ出る。
- **型の継承・実装の関係**（`types: TypeRelations`・読み取り専用）: `types.subtypes(type_name, from_rel, file_context, line)` が、同じ資料フォルダ・同じ世代（最上位フォルダ）の中で、その型を継承・実装する型の**候補の列**を返す
  （`TypeLookup(status, targets, subtypes)`・`TypeCandidate(path, name, qualified, exact)`・パス・名前の昇順）。型名の解決は共通層の規則（別名→単一型 import→同じ package／namespace→ワイルドカード・最近傍・世代跨ぎなし）と同じで、
  複数あれば**複数のまま**返す（`status=ambiguous`・`exact=False`＝その宣言の継承元自体が曖昧だった）。1 つに決まった実装へ辺を張るには、`TypeCandidate.qualified` を `RefCandidate.name` に `extra={"qualified": True}` を付けて返す（共通層が完全修飾名で一意に解決する）。
  **呼び出しの段階**: 型の関係は 1 パス目（定義の収集）が終わらないと引けない。そのため `FwPlugin.uses_type_relations = True` のプラグインがあるときだけ、共通層が **1 パス目と 2 パス目の間に追加の段**（全ファイルの継承・実装の宣言＝本体の参照のうち `via` が `extends`／`implements` を集める）を走らせ、
  プラグインは 2 パス目の `extract_refs` で引く（1 パス目の `collect_defs` では引けない）。型の継承・実装は**同じ言語の中で引く前提**で、集めるのは宣言したプラグインの `languages` のアナライザのファイルだけ。集める段で本文を読めない・指紋が変わったファイルは、2 パス目と同じく取り込みを確定させない（blocked）。宣言していないプラグインが引くと例外（＝適用時の失敗として `plugin_failed`）。
- **決まらないときは申告し、任意に選ばない**: DI のように複数の候補から 1 つに決める処理で、決まらなければ `PluginRefs.ambiguous`（`PluginAmbiguity(kind, name, line, candidates, via, source_symbol_id, why)`）で申告する。辺は張らない。
  共通層が取り込みの記録の `flags`（`reason=ambiguous`・`candidates`＝候補の数・`why`＝理由〔任意〕）と、保存する未解決の申告（S1b の `unresolved`・`reason=ambiguous`・`candidates`・`candidate_paths`＝候補のパス・先頭 5 件・`why`）に載せる。
- **失敗の境界**: 登録・import の失敗（契約違反・未登録の言語名・重複・版の宣言なし・読み込みの例外）は起動／`make verify-extension` で `FwPluginError`（`ExtensionAnalyzerError` の派生）として**明示の失敗**にする（黙って読み飛ばさない）。
  **適用時の例外**はそのプラグインのそのファイルの出力を丸ごと捨て、本体の結果は残す。黙って本体だけに倒さず、次の全部に伝える:
  取り込みの記録の `flags`（`reason=plugin_failed`・`action=warn`・`plugin`・`files`・`from`〔最初のファイル〕・`why`〔段と例外の型・先頭 200 字〕を 1 プラグイン 1 件）と取り込み画面の状態の注意、
  グラフ（`:SherpaMeta.plugin_failures`＝同じ tx で保存・`world_neo4j.read_plugin_failures`）、Codex の道具（`graph_neighbors`・`graph_resolve`・`graph_impact`）の `coverage.limits[]`（`kind=plugin_failed`・`plugin`＝プラグイン名）、
  外部 API の検索は graph の `coverage.limits[]` の `{kind: plugin_failed}`（`complete:false`・結果が返るので `degraded[]` には入れない＝`degraded` は従来どおり失敗して結果なしだけ）、影響・原因調査の結果の `notes`（画面の注記）。
  欠けは、そのプラグインを直して取り込み直すまで残る。失敗は資料フォルダ単位で保存し、範囲（フォルダ）では絞らない。
- 拡張アナライザのモジュールの import・構文の失敗は `ExtensionAnalyzerError`（明示の失敗）として扱う（従来の素の例外から変わる・受容）。
- プラグインの辺は、同じ始点・種別・終点の他の辺と共通層の集約（根拠 `sources`）で 1 本になる（設計どおり・根拠は `sources` に残る）。起点なし等のエラー応答には `plugin_failed` を載せない。
- **署名**: `config_signature()` の第 3 要素に `(登録名, version, languages, config_kinds, order)`（適用順・宣言的なルールファイルのプラグインは末尾に §3c の材料）が載る。プラグインの版上げで変わるのはそのプラグインのタプルだけ（本体・他のプラグインの材料は不変）。全体の署名は変わるのでアナライザの版上げと同じ扱い（§4）。
- **上流のプラグイン `spring:java`（P2・`spring_java.py`）**: Java ソースの Spring／TERASOLUNA の注釈を本体 `JavaAnalyzer`（FW 非依存）から切り出したもの。`languages={"java"}`・適用条件は言語のみ。
  足すもの＝①`@Autowired`／`@Inject`／`@Resource` のフィールドの宣言型を `via=inject`（本体が返した同じ型・同じ行の `field_type` の参照を重ねる。辺の代表の `via` は `VIA_PRIORITY` で `inject` が先・根拠 `sources` は同じ位置の `field_type` を `inject` に畳む）
  ②`@RequestMapping` 系の URL キー（`Config`・`key:url:`・`key_kind=url`）③`@Value`・`@Qualifier`・`@Named`・`@Resource(name=)`・`getBean` の設定キー参照（`config_key`）。`getProperty`／`getString` は JDK 標準の呼び出しなので本体に残る。
  `Dropped` の理由は `"spring:java: "` が前置される（`config_spel`・`config_prefix`・`getBean` の `config_nonliteral`）。
  **DI の拾い方（版 3・`uses_type_relations`）**: 注入点＝①`@Autowired`／`@Inject`／`@Resource` のフィールド ②同じ注釈のセッター（全ての引数）③`@Autowired`／`@Inject` のコンストラクタ、注釈が無ければコンポーネント注釈（`@Component`・`@Service`・`@Repository`・`@Controller`・`@RestController`・`@Configuration`・`@ControllerAdvice`・`@Named`）の付いたクラスの単一コンストラクタ（Spring 4.3 以降・複数あれば対象外）。
  辺の行き先は宣言した型のまま（`via=inject`）。宣言した型がインターフェース／抽象クラスのとき、`types.subtypes` で実装（間の抽象型はたどる・具象だけ）を引き、決まる根拠があるときだけ実装へも `via=inject` の辺を `qualified` で足す: ①名前の指定（`@Qualifier`／`@Named`・`@Resource(name=)`）が実装の bean 名（明示名・無ければ `Introspector.decapitalize` のクラス名）か型の `@Qualifier` に 1 つだけ一致（`di_qualifier`）②`@Primary` が 1 つだけ（`di_primary`）③実装が 1 つだけ（`di_single_impl`）。
  実装の候補はコンポーネント注釈のある具象クラスだけ。宣言した型に型引数があれば、継承・実装の経路（間の抽象型を含む）で型パラメータへの型引数の置き換えを伝えて実装の型引数（単純名）と照合し（同じ単純名の親が複数あれば書かれた型名を解決して選ぶ）。可変長の引数も要素の型を注入点にする。
  照合できない形は `generic_unmatched`。明示名・`@Resource(name=)` が非リテラルなら名前では決めない。
  決まらなければ `PluginAmbiguity`（候補・`why`＝`no_evidence`・`qualifier_unmatched`・`qualifier_multiple`・`qualifier_not_literal`・`generic_unmatched`・`search_limit`・`qualifier_conflict`・`primary_multiple`・`declaration_ambiguous`）で申告する。宣言した型が具象クラスのとき・実装が無いときは実装の辺を足さない。
  **取り込み 1 回の作業領域**: `FwPlugin.uses_build_context = True` のプラグインは `collect_defs`／`extract_refs` が `ctx`（`build_world` 1 回ごとに作られるプラグイン専用の dict）を受け取る。1 パス目の事実を 2 パス目へ渡す口で（プラグインごとに呼び出しの浅い写しで動き、例外にならず成功したときだけ反映する。値は置き換えて使い、中身を直接変更しない）、`uses_build_context` は署名の材料に足さない（版を上げる単位は変わらない）、共有のインスタンスに資料フォルダの事実を持たせない（並行・連続の取り込みで混ざらない・失敗後に残らない）。
  複数の名前の指定は全部集め、互いに違う・非リテラルなら `qualifier_conflict`／`qualifier_not_literal`、実装の探索を上限で打ち切ったら `search_limit` で申告する（辺は張らない）。
  解決の根拠は `RefCandidate.extra["resolution_rule"]`（`world_graph.EDGE_RULES` の名前だけ・共通層が消費して辺の根拠の `rule` にする・未知の名前は `unknown_rule` を `flags` に出す）で渡す。bean の事実（コンポーネント注釈・明示名・`@Primary`・抽象か）は 1 パス目に自分の中へ集め、2 パス目で引く。

拡張アナライザ自身が守るべき既存の設計原則（アナライザ増設5箇条・[17-開発の教訓.md](17-開発の教訓.md)）:
①契約固定（`collect_defs`/`extract_refs` は `DefResult`/`RefResult` を返すだけ・任意解決は共通層に委ねる）
②型は閉じ語彙・`via` で開く（`docs/05-グラフ語彙.md` のノード/エッジ型を増やさない）
③FW 非依存（本体のアナライザは言語処理系・標準構文のみ。ベンダー方言・FW 固有の規則は FW プラグインへ置く）
④言語・形式ごとに本体のアナライザは 1 本（同じ言語/形式に複数アナライザを立てない）。FW 固有の規則は別の部品＝FW プラグイン（§3a）として本体の結果へ重ねて複数適用する
⑤黙って落とさない（未対応構文は `Dropped` で記録して落とす）。

フォーク側のモジュールは `sherpa.ingest.analyzers._base` を**絶対 import**する（`from sherpa.ingest.analyzers._base
import ...`）。発見時は独立モジュールとして読み込む（パッケージ文脈を持たない）ため、`from ._base import ...`
のような相対 import は使えない。

### 3b. 設定の種別（`Analyzer.config_kind`）と XML 設定の FW プラグイン

`config_kind(text, rel_path)` は本体のアナライザが設定ファイルの種別を返す（FW プラグインの `config_kinds` と照合する）。判定しなければ `None`（プラグインは適用されない）。
種別の名前は**閉じた集合**で、本体（`xml_config.CONFIG_KINDS`）が返し得る名前と各プラグインの `config_kinds` は同じ集合の中にあること（契約テストで固定）。

| アナライザ | 種別 | 判定（ルート要素のローカル名・namespace URI/prefix・DOCTYPE は問わない・構文エラーは `None`） | 適用される上流プラグイン |
|---|---|---|---|
| `xml_config` | `spring_beans` | `<beans>`（Spring Batch の要素を含む） | `xml:spring` |
| `xml_config` | `mybatis_mapper` | `<mapper>` | `xml:mybatis` |
| `xml_config` | `struts` | `<struts>` | `xml:struts` |

- 種別が `None` の XML（pom.xml・web.xml・一般の設定ファイル・MyBatis の `<configuration>`・壊れた XML）には FW プラグインを適用せず、本体は `Dropped("xml_not_config")`／`Dropped("xml_parse_error")` を返す。
  種別を足すときは、この表・`CONFIG_KINDS`・対象のプラグインを同じ変更で更新する（種別を返す＝本体が `Config` の主体を作る、なので、グラフが変わる）。
- 本体 `xml_config` が返すのは設定の種別・`Config` の主体（ファイル名）・汎用の読み取り（`parse_xml`＝標準の expat・外部実体は展開しない・要素ツリー）まで。
  キー単位の `Config`（bean id・文 id・action など）と参照（`bean_class`・`include`・`config_key`・`mapper_*`・`action_class`）は FW プラグインが足す（規則の一覧は `xml_config_fw.py` の冒頭）。
- 版: 本体 `xml_config` の `version` は据え置き（本体とプラグインを重ねた結果は移し替えの前後で同じ・グラフの差分は 0）。プラグインは各 `version=1` で、登録で `config_signature()` の第 3 要素が増えるため全体の署名は一度変わる（§4）。以後、プラグインの規則を変えるときはそのプラグインの `version` を上げる。
- プラグインの `Dropped`（`config_duplicate_key`・`config_placeholder_location`・`config_import_missing_resource`・`config_import_wildcard`・`mapper_type_alias`・`mapper_sql_dynamic_table`・`mapper_include`）は理由の頭に `xml:<fw>: ` が付いて `flags` に出る（§3a）。

### 3c. 宣言的なルールファイル（コードを書かずに足す単純な抽出）

FW プラグインのうち**単純な抽出**だけで済むものは、コードを書かずに TOML のルールファイルで足せる（実装＝`analyzers/_rules.py`・発見＝`discover_fw_plugins`）。

- **置き場所と登録**: `sherpa/ingest/analyzers/rules_<名前>.toml`（拡張アナライザと同じ場所）。1 ファイル＝1 つの FW プラグイン（登録名 `rules:<名前>`）。ファイルに `name`・`version`（1 以上）・`order`（既定 100）・`languages`・`config_kinds`（省略可）を書く。
  `languages` は `java`（Tree-sitter のクエリ）と `xml_config`（要素と属性の指定）だけ。`config_kinds` を書けるのは `languages=["xml_config"]` のときだけ（Java は設定の種別を持たず、書くと適用されなくなる）。
- **ルール**: `[[rule]]` に `id`（ファイル内で一意）・`version`（ルールの版）・`language`・`emit`。
  - Java: `query`（Tree-sitter のクエリ）。捕捉 `@value`（文字列リテラル・必須）と任意の `@at`（行を取るノード）。述語（`#eq?` など）と補助の捕捉は自由。
  - XML: `element`（ローカル名）・`attribute`、任意で `namespace`（URI）・`root`（ルート要素のローカル名）。属性が無い要素は `Dropped("rule_missing_attribute:<id>")` で申告する。
  - `emit="def"`: キー単位の `Config` 定義（`key_kind` 必須・`cid_key=key:<key_kind>:<値>`）。`emit="ref"`: 参照の候補（`edge_type`・`kind`・`via`・任意の `key_kind`・`name_form`＝`plain`／`qualified`／`type_ref`）。
  出せる語彙は閉じた集合の中だけ（`edge_type`＝`EDGE_TYPES`・`kind`＝`NODE_LABELS`・`via`＝`KNOWN_VIA`・`key_kind`＝`property`／`bean`／`action`／`mapper`／`url`／`env`）。
- **できること・できないこと**: 単純な抽出（この注釈の付いたメソッドを API の入口にする・この注釈の値を設定キーの参照にする・この要素の属性をクラス名の参照にする）まで。名前の解決はしない（参照の候補を返すだけ・解決は共通層）。
  DI の注入先の決定・Mapper と SQL の対応づけ・型の継承の参照などの**判断はプラグインのコード**（§3a）で書く。
- **組み合わせの表**: `emit="ref"` の `(edge_type, kind)` は `via` ごとの許される組み合わせ（`_rules.ALLOWED_REFS`・`docs/05` §2 の辺と既存のアナライザが出している組み合わせ）の中だけ（例: `bean_class`＝`INVOKES`＋`Module`・`config_key`＝`ACCESSES`＋`Config`・`exec_sql`＝`ACCESSES`＋`Table`）。外れは登録時に失敗。`mention`・`mapper_namespace`・`config_value` はルールでは出せない。`version`（ファイル・ルールとも）は必須。
- **同じキーの重複**: 同じ (種別, キー) の `Config` 定義を別の行・別のプラグイン（`xml:spring` の bean id など）が出したときは、先に出た定義を残し、後のものは `Dropped("plugin_duplicate_def")`（理由の頭に出したプラグイン名）で申告して捨てる（同じ cid のノードを上書きしない）。
- **反映**: ルールファイルの追加・変更・削除は worker の再起動で反映される（登録と署名は起動時に読む）。再起動すると署名が変わり、資料フォルダは全件の取り込みになる。
- **読み込みと署名の注意**: UTF-8 の BOM の付いた TOML は読み込みで失敗する（BOM なしで保存する）。署名の材料のハッシュはファイルのバイト列そのもの（改行コードの違い・末尾の空白も署名を変える）。
  `include` など相対パスの厳密な解決が要る `via` はルールでは出せない（プラグインのコードで書く）。
- **ルールが当たらなければ何も出ない**: クエリ・要素の指定が対象に当たらなくても登録は成功し、何も出ない（検出はしない）。ルールごとに確認用の例のソースを置いて、期待どおり出ることをテストで確かめることを勧める（`fixtures/analyzer_rules/` が例）。
- **置き場所の外は読まない**: `rules_*.toml` のシンボリックリンクは拒否し、解決した後も置き場所の直下にあること。
- **失敗**: TOML の誤り・クエリの構文の誤り・未知の語彙・名前とファイル名の不一致・id の重複・`@value` の欠落（`@value` は `(string_literal) @value` の形だけ）は登録時（起動と `make verify-extension`）に `FwPluginError`（`NG:`）。適用時の例外は §3a の `plugin_failed`。
- **署名**: そのプラグインのタプルの末尾に `(ルールファイルの sha256, ((ルール ID, ルールの版), …))` が載る。ルールの 1 行を変えると `version` を上げ忘れても署名が変わり、資料フォルダは全件の取り込みになる（§4）。ほかのプラグイン・本体の材料は不変。
- **例**: `fixtures/analyzer_rules/rules_acme.toml`（架空の `@AcmeApi("/x")` を API の入口に・`<acme:service class>` をクラス名の参照に）。上流には登録しない。契約テスト＝`tests/unit/test_analyzer_rules.py`。

## 4. 版（部品ごとの署名）

`Analyzer.version`（既定1・上流のアナライザは C・C# が 4・Java が 5〈2＝参照元の定義キーと `file_context`・3＝名前の解決を言語の規則に従わせる・4＝読み取りを Tree-sitter（`tree-sitter-c`・`tree-sitter-c-sharp`・`tree-sitter-java`）へ置き換え・Java の 5＝Spring の注釈の処理を FW プラグイン `spring:java` へ移した〉・VB が 4〈4＝`.vbproj` の Root Namespace・プロジェクトの Import を名前の照合に使う〉・XML 設定が 3〈FW の規則を FW プラグインへ移した P3 でも据え置き＝本体＋プラグインの合成結果は不変〉・JSP／JS／Shell が 3〈2＝文字列の中身の誤抽出の除外・引用符つきヒアドキュメント・3＝読み取りを Tree-sitter へ置き換え〉・CSS／HTML が 2〈読み取りの置き換え＝CSS は Tree-sitter・HTML は標準の `html.parser`〉・コピーブックが 2〈入れ子の COPY〉・COBOL が 3〈2＝静的カーソル・`EXTRACT(… FROM 列)` ほか・3＝表の schema の区別〉・SQL が 4〈4＝`CREATE UNLOGGED|TEMP TABLE`・括弧つき／`WITH` 始まりの CTAS を表として受ける〉・他は 1）が `registry.config_signature()` の材料
JS の申告: 文字列の中のコードの断片＝`js_string_code`・取り込み先が実行時に決まる `import(p)`／`require(p)`＝`js_dynamic_import`・中身の解析を上限（2,000 字・200 回）で打ち切った件数＝`js_string_code_limit`（ファイルにつき 1 件）。構文エラー `syntax_error` は共通部品 `_ts` が全言語で先頭 20 件＋「ほか N 件」に収める。
`(name, version, extensions)` に部品ごとに畳み込まれる（FW プラグインは §3a の `(登録名, version, languages, config_kinds, order)` が第 3 要素に載り、プラグインごとに独立）。核の分類契約版（`CODE_ANALYZERS_SCHEMA_VERSION`）とは
別枠——**保証範囲は署名の独立まで**:

- ある部品の `version` を上げても、他の部品の材料タプル `(name, version, extensions)` はそれぞれ独立のまま不変。
  上流の核や他部品の版上げが、あなたの拡張部品の署名部分を変えることはない。
- ただし `config_signature()` **全体**の値は登録済み全部品のタプルの並びであり、いずれか1つが変われば全体は
  変わる。世代署名（`ingest/worker.py::_sig`・`es_index.needs_reindex`）はこの全体値を材料に含むため、
  **資料フォルダ全体の再構築は現行どおり起きる**（費用ゼロ・時間のみ＝LLM 抽出を使わない決定的解析のため）。
- **やらないこと（今回のスライスでは）**: ファイル単位の解析キャッシュ・部分再構築（「段2」・判断待ち）。
  署名が独立していることと、解析呼び出し自体が省略されることは別の保証であり、後者は別スライス。

核の契約（分類・グラフ語彙）を変える場合は無条件に全再構築（抑えない・上の独立性の対象外）。

## 5. `make verify-extension`

`scripts/verify_extension.py`（`make verify-extension`）が拡張面ごとに「確認した契約」または「未確認」を出力する
（提案書 §9 の表の順: アナライザ／FW プラグイン／頭脳 provider／変換アーム／MCP ツール）。

- **アナライザ**: 発見結果が `_ANALYZERS` の登録内容と一致すること・全登録アナライザの
  `accepts` が例外なく `bool` を返すこと・`collect_defs`/`extract_refs` が例外なく
  `DefResult`/`RefResult` の**インスタンス**（`isinstance`・型名の文字列比較ではない）を返すこと・
  `config_signature()` に全部品が載ることを実際に検査する。発見（`registry` の import）自体が
  契約違反で失敗した場合も traceback で落とさず `NG:` 行を出す。違反があれば `NG:` 行を出し、
  終了コードを非ゼロにする。
- **FW プラグイン**: 発見結果が `FW_PLUGINS` の拡張プラグイン構成と一致すること・登録名の重複／アナライザ名との衝突がないこと・`languages` が登録済みのアナライザ名であること・
  適用順が `(order, 登録名)` の昇順で決定的なこと・`config_signature()` に `(登録名, version, languages, config_kinds, order)` が載ること・`collect_defs`／`extract_refs` が `PluginDefs`／`PluginRefs` を返すことを検査する。
  ルールファイル（§3c）のプラグインは署名の末尾の材料も検査する。発見の失敗（`FwPluginError`）もアナライザ面と同じく `NG:` 行を出して非ゼロで終える。
- **頭脳 provider／変換アーム／MCP ツール**: 本スライスでは登録簿の実在と件数だけを表示し、
  「未確認（契約テストは既存の…テストが担う）」と明示する。**保証済みとは言わない**——これらの面の契約テストは
  `tests/unit/test_agents_seams.py`・`test_agents_surface.py`（provider）・`test_office_md*`（アーム）・
  `test_mcp_*`・`test_codex_mcp_concurrency`（MCP ツール）が既に担っている。3面それぞれの専用契約テスト
  （追加アーム/provider/ツールの登録→既存契約テストが通る・未登録名の fail-loud）は将来スライスの対象。
  アナライザ面の発見自体が契約違反（`ExtensionAnalyzerError`）で失敗したときは、この3面は評価せず
  「未確認（アナライザ面の違反により未評価）」とだけ出す——`registry` に依存する import（provider/
  アーム/MCP ツールの登録簿）を辿ると同じ発見処理が再度走り、同じ例外を再発させ traceback で落ちうる
  ため。

読み方: 出力の各面の見出し直後にある行が「確認した契約」（アナライザのみ）または「登録簿の実在」（他3面）。
`NG:` 行が1つでもあれば契約違反——是正してから再実行する。

## 6. 上流の取り込み

公開リポにリリース区切りでタグ（`vX.Y.Z`）＋ CHANGELOG を付ける（[20-開発ハーネス.md](20-開発ハーネス.md) §9・
決定 2026-09-09）。フォークはタグ単位で取り込む（追跡ブランチの継続 merge は前提にしない）。上流への還流
（フォーク側の拡張を本体へ Pull Request する）は任意——歓迎するが義務ではない。還流する場合は本書の契約
（命名・版・§3 の5箇条）に従っていること。

## 7. 上流の単体テストとフォークの拡張の共存

上流の単体テスト（`tests/unit/**`）は「上流の構成」（`registry._UPSTREAM_ANALYZERS`）を検証するもの。
フォークが本章の規約に従って正規の拡張アナライザを登録しても、上流のテストが赤にならないことを方式で保証する
——個別のテストを都度潰さない。`tests/conftest.py` の fixture `upstream_only_registry` が
`registry._ANALYZERS`（と、import 時に一度だけ束縛されキャッシュ同然になる `sherpa.layer.CODE_EXT`）を
上流限定に固定し、上流構成の固定値（拡張子の集合・優先順・「候補は既定 accepts のみ」等）を前提にするテスト
モジュールへ `pytestmark = pytest.mark.usefixtures("upstream_only_registry")`（またはテスト単位の
`@pytest.mark.usefixtures(...)`）で適用する。フォークの拡張が実際に発見・登録されることを検証するテスト
（`tests/unit/test_analyzer_extensions.py`・`tests/unit/analyzers/test_registry.py` の登録順/合併集合の
契約テスト）はこの fixture を使わず実登録簿を見る。フォークは自分の拡張のテストを `tests/unit/test_<prefix>_
*.py` のような専用ファイルに置き、上流のテストファイル自体は書き換えない——`make verify-extension` が実登録簿
（フォークの拡張込み）で契約を検査する。
