# GraphRAG オントロジー — 影響範囲分析の抽出スキーマ

> 同一性・スコープの一次情報は [03-鏡モデル.md](03-鏡モデル.md)（登録ディレクトリ＝1つの資料フォルダ・範囲＝フォルダ prefix・
> 同一性＝パス・即反映）。本書はそのグラフ層の語彙（ノード/エッジ）と抽出方針を規定する。
> 実装: `sherpa/ingest/model.py`（クローズド語彙の定義）／`sherpa/ingest/world_graph.py`（構築）／
> `sherpa/ingest/world_neo4j.py`（Neo4j 反映・影響 traversal）。

> 看板機能「影響範囲分析」（[12-ユースケース.md](12-ユースケース.md) UC-1）の精度の源。

## 0. 設計思想（最優先）

役割分担を1つの基準で切る:

- **事前計算（グラフ）に残すのは決定的（再現100%）に計算できる構造だけ**。「この変数を変えたら
  影響するソースを漏れなく」は毎回1万ファイルを grep できない以上、事前計算しかできない仕事
  （網羅性＝recall）。
- **意味を読む仕事（文書の文意・業務語とコード名の対応）はクエリ時のエージェント**（LLM＋ツール）
  に任せる。その場で読めば常に最新で、聞かれた分しかコストがかからない。
- 帰結: グラフは**静的解析（アナライザ・不変・[17-開発の教訓.md](17-開発の教訓.md) の5箇条）が出す
  骨格構造**と、**アナライザの定義索引を辞書として文書テキストと機械的に突合した言及**の2つだけで
  構成する。LLM でグラフへ意味を書き込む機構（旧・意味層フル抽出／業務語↔コード自動橋渡し）は
  持たない——全ノードは常に静的解析由来（「確実／要確認」
  のような信頼度判定は存在しない）。

## 1. ノードラベル（クローズド・7種）

`NODE_LABELS`（`sherpa/ingest/model.py`）:

| ラベル | 説明 / 例 | 抽出元 |
|--------|-----------|--------|
| `Module` | プログラム/クラス/関数（COBOL PROGRAM-ID, `TAXCALC`） | 静的（CALL/PROGRAM-ID） |
| `Copybook` | COBOL コピーブック（共通データ定義）／網羅性の源 | 静的（COPY） |
| `Batch` | ジョブ／ジョブネット（日次締め）。JCL のジョブ/ステップ | 静的（JCL） |
| `DataItem` | カラム/コピーブック項目（`TAX-RATE`） | 静的（コピーブック定義） |
| `Table` | RDB テーブル/VSAM/データセット（schema を書いた DDL は解決用の修飾名 `qualified_name` を持つ・下の「識別子の使い分け」） | 静的（DDL＝`SqlDdlAnalyzer` の `CREATE TABLE`。VSAM/データセットは未着工のまま・提案書「アナライザ拡張」（2026-09-05）§4(a)/(g)＝A1・A10） |
| `Document` | 取り込み対象の資料（設計書・帳票定義書等）。`documents` 台帳と 1:1（根拠・DL） | 取り込み時に確定 |
| `Config` | 設定ファイル（.properties/YAML/XML 設定）。Bean 定義・Mapper・struts.xml 等の「コードでない構成情報」の受け皿（K13 確定後の唯一の追加・A6・提案書「アナライザ拡張」（2026-09-05）§4(e)） | 静的（設定ファイルアナライザ・実装済み＝共通層の契約＋アナライザ本体（properties/YAML/XML・アナライザ拡張 S3'/S3b）） |

業務概念（旧: `Parameter`/`BusinessRule`/`Function`/`Screen`/`Report`/`Standard`/`Incident`）は**撤去済み**
（§7 退役リスト参照）。業務語の入口はクエリ時のエージェントが担う（§5）。

## 2. エッジ型（クローズド・5種＋世代跨ぎの対応1種）

`EDGE_TYPES`（`sherpa/ingest/model.py`）+ `CORRESPONDS_TO`（Neo4j 反映時のみ許容・`world_neo4j.WORLD_EDGE_TYPES`）。

規約: **`A -[依存]-> B` は「A が B に依存する」**。影響分析は incoming（逆向き）を推移的にたどる
＝「B が変わると、B に依存する全部が影響」。

| エッジ | 向き（依存元 → 依存先） | 例 | 影響たどり |
|--------|------------------------|----|-----------|
| `COPIES` | Module → Copybook | COBOL COPY | ○ |
| `CONTAINS` | Copybook → DataItem / Module → Module（同一ファイルの入れ子）／**Table → DataItem**（DDL の列定義・S2）／**Config → Config**（設定キー単位 children・properties/YAML の裸キー＋XML（Spring `<bean>`/`<property>`/`<alias>`・MyBatis 文 id/`<resultMap>`・Struts `<action>`/`<constant>`）・S3'・実装済み＝cid は `#key:<裸キー>`）／**Batch → Config**（シェル/バッチの `export`/`set` 等のキー代入→env キー・波3 レーンB・実装済み）／**Module → Config**（Java の `@RequestMapping`/`@GetMapping`等の URL キー定義・波3 統合・実装済み） | 構造内包の一般形 | ○ |
| `INVOKES` | Batch/Module → Module／**Config → Module**（`via=bean_class/mapper_type/action_class`・A6/A7）／**Module → Config**（`via=mapper_namespace`・A8＝MyBatis Mapper インターフェースからこの Mapper 定義への依存として、`RefCandidate.reverse` で解決先（Module）→primary（Config）の向きに反転して張る）／**Batch → Batch**（JCL の `EXEC PROC=`/カタログド実行→`via=exec_proc`・`INCLUDE MEMBER=`→`via=include_member`・S5a・実装済み／シェル/バッチの他スクリプト呼び出し→`via=include`・波3 レーンB・実装済み）／**Module → Module**（EXEC CICS の `XCTL`/`LINK` の `PROGRAM(...)` 引用リテラル→`via=cics_xctl/cics_link`・S5a・実装済み／JSP/HTML の include・`<script src>`・`<iframe src>`（HTML）・`<link href>`・JS の `import`/`export … from`/`require`・CSS の `@import`→`via=include`・波3 レーンA・実装済み）／**Batch → Module**（シェル/バッチの `java`/`node` 起動・実行ファイル単独行呼び出し→`via=call`・波3 レーンB・実装済み） | **実行・利用依存の一般形**: CALL・ジョブ実行・継承/実装・宣言型参照・設定ファイル経由の依存。細分はエッジ属性 `via` で持つ——**エッジ型は増やさない**（型は閉じ属性で開く）。既知値は `analyzers._base.KNOWN_VIA` が一次情報（`inject`・`config_key`（注釈由来）・`key:url:` の URL キーは Java の FW プラグイン `spring:java` が出す・docs/21 §3a）（`call`/`extends`/`implements`/`field_type`/`inject`/`include`/`import`/`copy`/`mention`/`bean_class`/`mapper_type`/`mapper_namespace`/`action_class`/`config_value`/`config_key`/`exec_sql`/`exec_proc`/`include_member`/`cics_xctl`/`cics_link`/`mapper_sql`/`vba_sql`・`config_key`/`exec_sql`/`mapper_sql`/`vba_sql` は下記 `ACCESSES` 行で使う値） | ○ |
| `ACCESSES` | Module → Table/DataItem（**Module → Table** は COBOL `EXEC SQL`→`via=exec_sql`・S2 で producer 追加。VB6/VBA の SQL 文字列連結→`via=vba_sql`・波3 レーンC・実装済み。DataItem 側は引き続き計画枠）／**Module → Config**（`via=config_key`・A9＝同一 top_scope 内の同名 `Config` キー**全件**へ張る特例・ambiguous 判定を経由しない。Config キーは種別（`extra["key_kind"]`＝`property`/`bean`/`action`/`mapper`/`url`/`env`・裁定2026-09-06）で名前空間を分ける——`config_key_index` は `(label, key_kind, 裸キー)` で引くため、たまたま同じ裸キー文字列を持つ bean と property 等は誤って同一視されない）／**Batch → Config**（`via=config_key`・シェル/バッチの環境変数参照→env キー・波3 レーンB・実装済み）／**Config → Config**（`via=config_key`・Spring Batch の `ref`/bean 間参照・波3 レーンB・実装済み）／**Config → Table**（`via=mapper_sql`・S4'・実装済み＝MyBatis Mapper XML の `<select|insert|update|delete|sql>` 本文から `_sql_scan` で抽出。定義ノードを持たない言語（XML 設定など）では参照側 src がファイルの主体のため、Mapper 利用プログラムまでは `Module -[mapper_namespace,reverse]-> Config -[mapper_sql]-> Table` の2ホップで届く） | DB/ファイル読み書き・設定キー参照 | `Table`（`via=exec_sql`）は実装済み（アナライザ拡張 S2）。`Table`（`via=mapper_sql`）も実装済み（S4'）。`Table`（`via=vba_sql`）も実装済み（波3 レーンC）。いずれも schema を書いた参照は同じ schema の定義にだけ張る（`SCHEMA.NAME`・無ければ unresolved／書かない参照で複数 schema の同名があれば ambiguous）。いずれも DDL の無い資料フォルダでは unresolved のまま（`Table` ノードを作らない・§4(g) 既定案）。`Config` 系（`config_key`）は共通層の契約実装済み（アナライザ拡張 S3a）・producer（設定キー文字列リテラルの検知）は S3' で追加 |
| `DOCUMENTS` | Document → 任意ノード | 資料が対象を記述／言及する（**根拠**） | ×（根拠として添付。`via="mention"` は下記§5の言及エッジ） |
| `CORRESPONDS_TO` | 同名ノード間（世代を跨ぐ） | 世代違いの対応表示 | ×（producer 未実装・語彙のみ） |

> 影響 traversal（`world_neo4j._IMPACT_REL`）は **`COPIES\|CONTAINS\|INVOKES\|ACCESSES`** のみを辿る
> 決定的な構造たどり。`DOCUMENTS`/`CORRESPONDS_TO` は根拠添付・対応表示の**専用エッジ**で traversal には乗らない。

**辺の始点（参照元の定義）**: 構造エッジ（`COPIES`/`INVOKES`/`ACCESSES`）の始点は、既定ではそのファイルの主体ノード。
定義ノードを持つ言語（C の関数・VB の `Sub`/`Function`/`Property`・C#/Java の型）は、参照を含む定義ノードが始点になる
（アナライザが参照ごとに `source_symbol_id`＝`(rel_path, cid_key)` を返し、共通層が `children` の定義ノードへ引き当てる。
引き当てられなければ主体へ倒して `flags` に `unknown_source_symbol` を残す）。`cid` は変えない。
主体の直下・関数の外の参照（C の `#include`・ファイル直下の宣言など）は主体が始点。メソッド・COBOL の段落・SQL は対象外（`docs/21` §3）。
ファイル単位で見るときは辺の両端の `path` で畳める（影響たどりの `affected.path` は始点が定義でも変わらない）。

**トップフォルダ（システムの境界）をまたがない**: 構造リンク（COPIES/CONTAINS/INVOKES/ACCESSES）も、
`DOCUMENTS`（`via="mention"`）も、同一 top_scope 内だけで張る（[03-鏡モデル.md](03-鏡モデル.md) §2.2・§2.4）。
`CORRESPONDS_TO`（同名の対応表示）は語彙に定義があるだけで、作る処理は無い。

## 3. 共通プロパティ

**ノード**: `cid`（canonical_id）, `label`, `name`, `world_id`, `path`, `value`（定数値等・任意）,
`status`（`active` | `deprecated`＝明示廃止 | `hidden_candidate`＝隠し検出の低信頼候補）,
`top_scope`/`phase`/`category`（範囲メタ・フォルダから導出）。`Table`（SQL の DDL で schema を書いた定義）は `schema`・`qualified_name`（`SCHEMA.NAME`）も持ち、Neo4j にも保存する（無いノードは書かない）。

`cid` はパス修飾（同一性＝パス・[03-鏡モデル.md](03-鏡モデル.md)）:
```
{label.lower()}:{world_id}:{rel_path}#{name}          // ファイル由来（Module/Copybook/Batch/DataItem/Table/Config）
document:{world_id}:{rel_path}                          // Document（同一性＝パスのみ・表題は使わない）
```

**識別子の使い分け**（表示名・解決用の修飾名・canonical ID は別の用途）:

| 呼び名 | 何か | 用途 |
|---|---|---|
| 表示名 | ノードの `name`（単純名。`CUSTOMER`） | 画面・回答の表示、言及辞書の語 |
| 解決用の修飾名 | ノードの `qualified_name`（SQL の `Table` で schema を書いた定義だけ・`A.CUSTOMER`）。参照側の `SCHEMA.NAME` と突き合わせる | 参照の解決（`world_graph._resolve_table`）。`cid` には含めない |
| canonical ID | `cid`（上の式）。外部の利用者が控える・重要度の指定などが参照する | 同一性。**既存の `cid` は変えない** |

- SQL の `Table`: 1 件目（同じファイルで最初）の `cid` は schema の有無に関わらず `...#NAME` のまま。同じファイルに同名で schema が違う表がある 2 件目以降だけ別ノードで、`cid` は `...#SCHEMA.NAME`（列は `...#SCHEMA.NAME.COLUMN`）。表示名は `NAME`。同じ schema＋名前の重複と、schema の無い 2 件目以降の同名は、`cid` を分けられないので `dropped_syntax`（`table_name_collision`）で申告して持たない。
- 参照側（COBOL の `EXEC SQL`・MyBatis の SQL・VBA の SQL 文字列。`_sql_scan.table_refs` が返す名前）: schema を書いていれば `SCHEMA.NAME` で、同じ世代にその schema の定義があればそれだけに張る。無ければ schema の記載が無い DDL の表だけを候補にして修飾なしと同じ規則（1 つなら最近傍・同距離の複数は ambiguous）で張る。schema を明示した別の schema の同名へは張らず、どちらも無ければ未解決。表名は引用符の外の `.` だけで区切る（`"T.X"` は 1 つの名前）。3 部名 `DB.SCHEMA.T` は先頭の DB を捨てて schema=SCHEMA・名前=T（参照・DDL とも）、4 部以上は表にせず参照は unresolved・DDL は `dropped_syntax`（`table_name_unsupported`）。MyBatis の `${…}` を含む表名は解決せず `dropped_syntax`（`mapper_sql_dynamic_table`）。書いていなければ、同名が複数 schema にあるとき `ambiguous` として申告し（任意に選ばない）、1 つだけなら今までどおり最近傍へ張る。
- C#/VB: 型のノードの識別子は変えない。表示名は単純名、型の children の `cid_key` と解決用の修飾名は `Namespace.Type`（`using`／`Imports` を解決に使うのは ANA-14 S3）。

**未解決の申告（ノードの保存属性・語彙は増やさない）**: ファイルの主体のノードに、そのファイルが書いた参照のうち辺を張れなかったもの（`unresolved`＝同名なし・`ambiguous`＝同距離の候補が複数・`cross_scope`＝別世代にしか無い、ほか解決器が足す理由）を持つ。`unresolved`（JSON 文字列・各項目 `{line, reason, kind, name, via, from_def{file, key|null}, candidates?}`・1 ファイル 50 件まで・`line`→理由→名前の順）・`unresolved_names`（名前の配列・検索用・上限で切らない）・`unresolved_overflow_count`（保存の上限を超えた件数）。`from_def` は参照元の定義（`key` が定義ノードのキー・定義ノードの無い言語と定義の外は `null`＝主体）。同じ書き込み（`load_world` の 1 トランザクション）で入り、メタ（`:SherpaMeta`）の `unresolved_stored` が「保存あり」を示す。保存形式の版は `GRAPH_STORAGE_VERSION`（`GRAPH_SCHEMA_ERA` の材料・`worker._sig` には入れない）。主体の無いファイル（`no_primary_definition`）と COPY の循環（`copy_cycle`）は保存先のノードが 1 つに決まらないため保存せず、取り込み記録の `flags` だけに残す。

**エッジ**: `via`（INVOKES/ACCESSES/CONTAINS/DOCUMENTS の細分・§2。`ACCESSES` は `via=config_key`）, `status`, `sources`（根拠・下記）。

来歴・根拠（`sources[]`）は**静的由来のみ**（LLM 由来は無い）。辺とノードの欄:

| 場所 | 欄 | 中身 |
|---|---|---|
| 辺 | `doc`・`line`・`via` | 代表の根拠（`sources` の先頭）と同じ値（既存の読み手のため）。言及の辺は `doc`＝言及元の文書・`line`＝0 |
| 辺 | `sources`（JSON 文字列・配列） | 根拠。1 本の辺 `(始点, 型, 終点)` は 1 本のまま、同じ 2 ノードを結ぶ複数の参照を根拠として並べる（CONTAINS など参照の無い辺は持たない） |
| 辺 | `sources_overflow_count` | 上限（1 辺 20 件）を超えて保存しなかった根拠の件数（超過が無ければ欄なし） |
| ノード | `sources`・`sources_overflow_count` | 出所のリスト（辺の根拠とは別の欄・コード由来のノードは持たない） |

辺の根拠 1 件の欄（`sources[]`・旧 `source[]` の `doc_id`・`file`・`line`・`evidence_text` を引き継ぐ）:

| 欄 | 型 | 必須 | 意味 |
|---|---|---|---|
| `via` | 文字列 | 辺が `via` を持つとき | 関係の種類（§2 の `KNOWN_VIA` の値）。COBOL の COPY など辺が `via` を持たないときは省く |
| `doc_id` | 文字列 | 必須 | 参照元の文書（`rel_path`） |
| `file` | 文字列 | 必須 | 参照元のファイルのパス（コード由来は `doc_id` と同じ） |
| `line` | 整数 | 必須 | 参照の行（言及の辺は 0） |
| `rule` | 文字列 | 任意 | 接続を決めた解決規則の名前。閉じた一覧（`world_graph.EDGE_RULES`）: `alias`・`single_import`・`same_package`・`wildcard`・`qualified_name`・`path_exact`・`path_suffix`・`config_key_all`・`schema_exact`・`schema_unqualified`・`table_name`・`nearest_name`・`copy_path_setting`（最近傍で決まらない COPY を資料フォルダの設定 `copy_paths` で決めた）・`path_alias_setting`（`#include` の別名を設定 `path_aliases` で置き換えて決めた）・`dictionary_match`（言及）・`di_qualifier`・`di_primary`・`di_single_impl`（DI の注入先の実装を決めた根拠・下記） |
| `from_def` | `{file, key}` | 任意 | 参照元の定義（`key` が定義ノードのキー・定義ノードの無い言語と定義の外は `null`＝主体） |
| `locator` | 文字列 | 任意 | 文書内の位置。言及の辺で、言及を見つけた本文の行（直前の見出しがあれば添える） |
| `evidence_text` | 文字列 | 任意 | 根拠の抜粋 |

**DI の注入先の実装**（`via=inject`・FW プラグイン `spring:java`）: 注入の辺の行き先は宣言した型（インターフェース）のまま。実装への辺は、決まる根拠があるときだけ足す——名前の指定（`@Qualifier`・`@Named`・`@Resource(name=)`）が実装の bean 名（`@Component("x")` などの明示名・無ければクラス名の先頭小文字）か型の `@Qualifier` に 1 つだけ一致（`di_qualifier`）／`@Primary` が 1 つだけ（`di_primary`）／実装が 1 つだけ（`di_single_impl`）。この順に判断し、決まらなければ辺を張らず候補と理由（`why`）つきの `ambiguous` として申告する（`unresolved`）。

根拠は `(doc_id, line, via, rule, from_def, locator)` が同じものを 1 件にまとめ（同じ位置に `via=inject` の根拠があれば同じ位置の `via=field_type` の根拠は畳む＝注入は宣言型の格上げ）、`via` の優先順位（`VIA_PRIORITY`）→文書→行の順に並べる。先頭の件が辺の代表（`doc`・`line`・`via`）と一致する。読み取り（影響・近傍・外部 API）は先頭の数件（既定 3・最大 10）と、返さなかった件数（`sources_overflow_count`）を返し、`rule` は先頭の根拠から読む。旧世代の辺の単独の `source`・`evidence`・`rule` は書かない（保存形式の版 `GRAPH_STORAGE_VERSION`＝2 で、旧世代のグラフは読み取りが拒否され、取り込みの作り直しで新しい形になる）。
ソース（COBOL/JCL/Copybook）も必ず `documents` 台帳に1行登録し（doctype=cobol/jcl/copybook）、
`doc_id`＋`line` で原ファイルに解決して DL する。

影響分析は **`active` を既定**、`deprecated`/`hidden_candidate` は除外（`include_deprecated=true` で参照可）。

## 4. 取り込み（静的解析のみ・3パス）

**トラック S（骨格＝Pass1/Pass2）**: COBOL/JCL/コピーブックを**確定的にパース**して構造ノード/エッジを
生成する（対応済み方言・構文に対して再現性100%。未対応方言・未対応構文は自動フォールバックしない
——不可視な劣化として対応表で可視化するに留める・この方針は変更しない）。

| ソース構文 | 生成 |
|-----------|------|
| `PROGRAM-ID` | `Module` ノード |
| `COPY xxx` | `Module -COPIES-> Copybook`（コピーブックの中の入れ子の `COPY` は `Copybook -COPIES-> Copybook`）。文字列リテラルの中の語は拾わない |
| コピーブック項目定義（01/05レベル） | `Copybook -CONTAINS-> DataItem` |
| `CALL 'PROG'` | `Module -INVOKES(via=call)-> Module`（`DISPLAY "CALL 'X'"` のような文字列リテラルの内側の `CALL` は呼び出しにしない） |
| JCL ジョブ/ステップ | `Batch` ＋ `Batch -INVOKES-> Module` |
| `EXEC SQL ... END-EXEC`（`MERGE INTO` 含む） | 実装済み（アナライザ拡張 S2）＝`Module -ACCESSES(via=exec_sql)-> Table`（`DECLARE … CURSOR FOR SELECT …` の静的カーソルも表を読む。準備済みの文の名前を指すカーソル・`EXECUTE IMMEDIATE` は `dropped_syntax(exec_sql_dynamic)`。`EXTRACT(… FROM 列)` などの関数の `FROM` は表にしない）。`SELECT/READ/WRITE`／FILE SECTION は引き続き計画枠 |

**参照解決の結果（Pass2・ANA-09）**: 参照 1 件は、同じ最上位フォルダ（世代）の中だけで解決し、結果は次のどれかになる。
辺を張るのは「解決」だけで、それ以外は辺を張らずに `flags`（取り込み記録）へ理由を残す。「確実／要確認」の印は付けない（辺は張るか張らないかの 2 値）。

| 結果 | 辺 | `flags` の `reason` |
|---|---|---|
| 解決（一意に決まった） | 張る | なし |
| 曖昧（同距離・同じ修飾名の候補が複数・ワイルドカードの複数一致） | 張らない | `ambiguous` |
| 世代跨ぎ（別の最上位フォルダにしか無い） | 張らない | `cross_scope` |
| 未解決（その名前の定義が無い・名前は他にあるが参照元から見える範囲に無い） | 張らない | `unresolved` |
| **明示した修飾に一致する定義が無い**（完全修飾名・単一型 import・別名・`#include "相対パス"`） | 張らない（**短名・basename の最近傍へ倒さない**） | `unresolved_qualifier`（`name` は明示した修飾名・パス） |
| `config_key` | 同じ世代の同名キー**全件**へ張る（曖昧にしない） | 無ければ `unresolved` |

名前の解決の順序（明示した修飾を最近傍に優先する。フォルダの近さは**同じ完全修飾名の候補が複数あるときの並べ替えにだけ**使い、別の名前を選ぶ根拠にしない）:

- **Java**: ① 単一型 `import`（その完全修飾名だけ・実在しなければ未解決）② 同じ package ③ ワイルドカード `import p.*`（一意なら張る・複数なら曖昧）。完全修飾名で書かれた参照（`new a.b.X()`）はその名前だけで解決する。`static` import は型の名前を持ち込まない（解決に使わない）。入れ子の型（`Outer.Inner`）は外側の型 `Outer` へ寄せる。`java.lang`・JDK の型は対象外。
- **C#・VB.NET**: ① 別名（`using A = N.T`・`Imports A = N.T`）② 参照元の namespace→親の namespace→グローバル（内側が先）③ `using N;`・`Imports N`（N の型。複数一致なら曖昧）。`using static` は型の名前を持ち込まない。別名は修飾名の先頭（`A.Target`）でも展開する。`global using` は同じ最上位フォルダの全ファイルの `using` に足す（世代をまたがない）。修飾付きの型名（`A.B.T`）は enclosing namespace の下も探し、見つからなければ外側の型（`A.B`）へ寄せる。VB6/VBA/VBScript は文脈を持たず、名前だけの最近傍解決のまま。 VB.NET は資料フォルダの `.vbproj` があれば、そのプロジェクトのソースの型・手続きを本当の完全修飾名（`<RootNamespace>.<namespace>.<型>`）で引く（同じプロジェクトからは Root なしの名前でも引け、別のプロジェクトの型は Root つきの名前でだけ引ける）。プロジェクト全体の `Import` はファイルの `Imports` と同じに扱う（ANA-18）。
- **C**: `#include "x/y.h"`（パス区切りあり）は参照元からの相対パスの完全一致だけ（無ければ未解決・別フォルダの同名へ倒さない）。`#include "y.h"`（区切りなし）は名前の最近傍・`#include <…>` は対象外。
- **完全修飾名を渡す参照**（Spring `<bean class>`・MyBatis `namespace`・Struts `<action class>`・JSP `useBean`・`java` 起動の FQCN など）: 完全修飾名の索引の完全一致だけ。無ければ `unresolved_qualifier`。

recall との関係（§0・§6）: 解決を厳しくすると、今までつながっていた「近いだけの別 package・別 namespace の同名」への辺は無くなる（誤接続の除去）。
その分の取りこぼしは、上の `flags`（未解決・曖昧）と `dropped_syntax`（読み飛ばした構文）に残り、黙って落とさない。

**トラック M（言及＝Pass3・§5）**: Pass1 の定義索引をそのまま辞書として資料文書の本文と突合し、
`Document -DOCUMENTS(via="mention")-> コードノード` を張る（LLM ゼロ）。

**マージなし**: 旧「静的＋LLMの2トラックを名寄せで統合」は撤去。骨格（S）と言及（M）は最初から
同一グラフの別エッジ種別として共存し、統合処理を必要としない。

## 5. 言及エッジ（辞書突合）— 業務語↔コードの入口

業務パラメータ↔コード項目の橋渡し（旧 `REALIZES`・LLM 提案→承認）は撤去済み。代わりに:

1. **辞書**: Pass1 が作る `(label, name) -> [rel_path...]` の定義索引を**そのまま**辞書として使う
   （予約語除外は不要——辞書の材料は定義そのものなので、名付けられたものしか入らない）。
2. **突合**: 文書テキストを識別子形トークン（`[A-Za-z0-9_-]+` の最大連続・1パス）に分解し、
   辞書と**トークン全体一致**で照合する（部分文字列検索はしない）。
   - **完全一致・大文字小文字を区別**（識別子は転記される値のため。`normalize_code_name` の
     `upper()` は使わない——`DATA`/`data` のような誤リンクは逆引きを汚染するため fail-closed）。
   - **長さ下限4文字**（`world_graph._MENTION_MIN_LEN`）。
   - **辞書内で一意な名前だけ張る**（同じトップフォルダの中に同名複数定義＝曖昧＝張らない。名前解決 `_resolve_nearest`
     と同じ流儀）。**言及元の文書と同じトップフォルダの定義にだけ張る**（別のトップフォルダの同名へは張らない）。
3. **入口**: 「消費税率を変えたい」のような業務語のクエリは、エージェントが文書を grep してコード名
   （`TAX-RATE` 等）を発見し、そのコード名でグラフへ入る——事前橋渡しへの依存を下げる。

実装: `sherpa/ingest/world_graph.py::_mention_pass`（`build_world` の Pass3・`MENTION_SCHEMA_VERSION`
で仕様版を管理）。対象文書は `branch=="office"`（資料文書）のみ、`branch=="source"` は対象外。

## 6. 影響分析クエリ（recall優先・経路を返す）

```cypher
MATCH (start:Entity {cid: $cid, world_id: $world})
MATCH path = (affected:Entity)
  -[r:COPIES|CONTAINS|INVOKES|ACCESSES*1..8]->(start)
WHERE ( $include_deprecated OR coalesce(affected.status,'active') = 'active' )
  AND ( $include_deprecated OR all(e IN r WHERE coalesce(e.status,'active') = 'active') )
RETURN labels(affected)[0]                          AS 種別,
       affected.name                                AS 対象,
       [n IN nodes(path) | n.name]                  AS 経路    // ← なぜ影響するか
```
- 各 `affected` に `Document -DOCUMENTS->`（`via="mention"`含む）で**根拠設計書＋DLリンク**を添付できる
  （traversal には乗せない・別クエリで根拠添付のみ）。
- 深さ上限は recall とノイズのバランスで調整。
- **「確実／要確認」のような信頼度による分岐は無い**（全ノードが静的解析由来＝同格）。
  grep 共起による「推定影響（presumed）」は本 traversal とは別枠の補助表示として残る。
- **「関連なし」と「調べきれなかった」を区別して返す（`coverage`・段階 1 の S1a）**: 影響たどり・近傍の探索は、時間切れ・
  行数の天井・深さの上限で先に辺が残ること・件数（`k`・カード数）の上限・文書探索の打ち切りを、`coverage`
  （`complete`・`limits[].kind`・`omitted`・`depth{requested, truncated}`）で返す。辺が無いことを「依存なし」と取り違えない
  ための申告で、recall 優先の方針（辺を落とさない）と対をなす。深さの先の判定は、実際の影響クエリと同じ条件
  （資料フォルダ・範囲・status・向き・辺の型）の存在確認で行い、`depth`＋1 で新しく届く影響先があるときだけ `truncated`
  とする。語彙（ラベル・エッジ型）は増やさない。契約は [design/interfaces.md](design/interfaces.md)（`C-EXT-SEARCH-01`・
  `run_tool` の `graph_neighbors`）。
- **Codex の影響調査の 2 段（`graph_resolve`・`graph_impact`）**: `graph_resolve` が名前・種別・所属パスの一部から起点の候補（`canonical_id`・
  種別・所属パス・表示名・修飾名）を、同名もまとめずに並べる。`graph_impact` は起点の `canonical_id` だけを受け取り（名前の曖昧さを持ち込まない）、
  **構造の辺（`COPIES`・`CONTAINS`・`INVOKES`・`ACCESSES`）だけを逆向きに**たどる（上の影響分析クエリと同じ条件）。
  `DOCUMENTS`（言及）は影響に数えず、関連文書として別に返す。深さ・件数の上限で未探索が残るときは `coverage` で申告する。
  コード同士の閉じた辺だけなので、探す対象がソースに限られている間も使える。契約は [design/interfaces.md](design/interfaces.md)。

## 9. 残論点（実装時に詰める）

1. **静的解析パーサの選定**（COBOL 方言・JCL）。未対応方言・未対応構文の可視化強化。
2. **`Table`/`ACCESSES` の残存する検出限界・`CORRESPONDS_TO`（世代対応の producer）の着工判断。**
   `Module -[ACCESSES(via=exec_sql)]-> Table`（COBOL EXEC SQL・S2）・`Config -[ACCESSES(via=mapper_sql)]->
   Table`（MyBatis SQL 本文・S4'）・SQL/DDL の `CREATE TABLE`/CTAS（S2）は実装済み。未対応のまま
   残るのは COBOL の `SELECT`/`READ`/`WRITE`（FILE SECTION 経由のファイル入出力）と `Table ->
   DataItem`（列単位の ACCESSES）——いずれも計画枠のまま。`CORRESPONDS_TO` は語彙のみ先置き・
   producer 実装なし。
3. **言及エッジの一意判定しきい値**（長さ下限4文字・大文字小文字区別）の実地チューニング。
4. **リフレクション型（クラス名が文字列リテラル）の値側トークン突合**（将来対応）。
5. **設定ファイル（.properties/YAML/XML）アナライザ・Java FW4種の残存する検出限界。**
   `Config` ノード・共通層契約（`RefCandidate.reverse`／完全修飾名2段解決／エッジ集約／`config_key`
   全件接続・アナライザ拡張 S3a・A6〜A9）・アナライザ本体（XML/properties/YAML・S3b）・Java FW4種
   （Spring/MyBatis/Struts/TERASOLUNA 5.x・波2 S3b/S4'）は実装済み。**XML 設定の FW の規則（Spring の `<bean>`・`<import>`・
   Spring Batch／MyBatis の mapper・SQL・型／Struts の action）は FW プラグイン `xml:spring`・`xml:mybatis`・`xml:struts`
   （`xml_config_fw.py`・ANA-15 P3）が出し、本体の `xml_config` は設定の種別の判定（`config_kind`）と `Config` の主体だけを返す**
   （TERASOLUNA 5.x の XML は Spring の beans として `xml:spring` が扱う）。移し替えの前後で、同じ入力から同じ `(始点, 型, 終点, via)` の辺が出る
   （`via` の表・辺は変わらない）。プラグインの `Dropped` は理由の頭に `xml:<fw>: ` が付く（`flags` の `why`）。残る検出限界: SpEL 式・非リテラル
   値（`${...}`/`#{...}` 等の動的参照）は `config_value`/`mapper_type_alias` 等の `Dropped` で申告する
   だけで接続しない・YAML の非対応構文（複数ドキュメント/アンカー等）は `Dropped("yaml_unsupported")`。
   **Config キーは種別（`key_kind`）で名前空間を分ける**（裁定2026-09-06）: properties/YAML のキーは
   常に `"property"`、画面テンプレート（JSP/HTML）/JS の action 名/URL パスは `"action"`/`"url"`
   （producer ごとに固定）、XML 設定のキーは `"property"`/`"bean"`/`"action"`/`"mapper"`
   （bean id/alias・action・MyBatis 文 id 等・XML 設定の FW プラグイン `xml_config_fw.py` が値ごとに付ける）。java.py の
   `@Value`/`getProperty`/`getString` は `"property"`、
   `getBean`/`@Qualifier`/`@Named`/`@Resource(name=...)` は `"bean"`。共通層（A9・
   `world_graph._link_config_key_all`）は `(label, key_kind, 裸キー)` で候補を引くため、同種別の
   キー全件にのみ接続する——参照/定義のどちらかに `key_kind` が無い場合は `None` 同士だけ一致する
   （後方互換）。
   **完全修飾名2段解決はパス同一性の例外ではない**——同一 `cid_key` の定義が同一 top_scope 内に複数
   （複製・並行ビルド等）存在する場合は `_resolve_nearest` と同じ規律でパス距離の最近傍を採る。
   等距離なら任意選択せず `ambiguous` を申告する（`world_graph._resolve_qualified`）。
